# Roadmap

Pending work for Kratos MDPA Preview, prioritizing full meshio++ integration, a clearer UI shared with CAD-Preview, and practical mesh preparation and results-analysis workflows. Existing foundations include MMG remeshing, meshio++ WASM, replayable edit histories, Python problemtypes, field visualization, time-series playback, tracked Kratos runs, and a headless MCP server.

**meshio++ is adopted at the locked 16.27.0 baseline.** Historical binding failures, missing side channels, format defects, and build omissions are no longer exclusions from this roadmap — `@meshioplusplus/wasm` is pinned at `^16.27.0`, the locked baseline for this integration, and the extension's packaged runtime already declares and uses it. What remains is connecting its capabilities to the extension end to end, preserving Kratos semantics, and verifying the resulting workflows — the items below, not the dependency adoption itself. Keeping that pin current as upstream releases is its own standing item, Tier 0.

This page is aspirational, not a release commitment. All numbered items are **pending** except the completed work recorded in `CHANGELOG.md`. Effort is approximate: **S** = a day or two, **M** = roughly a week, **L** = multi-week. Completed features belong in `CHANGELOG.md` and implementation details in `CLAUDE.md`; remove completed items here. No tracker issues have been assigned to the items below yet.

**Renumbered 2026-10-05 to close gaps 6, 9–13, 15 and 20 — items are now 0–14 contiguous.** Old→new: 7→6, 8→7, 14→8, 16→9, 17→10, 18→11, 19→12, 21→13, 22→14 (0–5 unchanged). Pre-2026-10-05 references, including `CHANGELOG.md` history, use the old numbers — see the mapping above.

## Research baseline

Reviewed `/home/vicente/src/meshioplusplus` and the published WASM artifacts on **2026-09-29**, including releases 16.23.0–16.25.0 (re-probed 2026-09-30 against 16.27.0: same inventory, see Tier 0), `bindings/wasm/js_bindings.cpp`, and `src/wasm/index.d.ts`. The extension now declares `@meshioplusplus/wasm: ^16.27.0`; sequential and OpenMP builds were loaded and probed alongside the previous packaged runtime.

**16.25.0 keeps the WASM format inventory stable and adds operation exports.** The live probe found 76 readers, 68 writers, and 37 options-aware readers in both 16.22.0 and 16.25.0; no format key was added or removed, and `hasCgnslib` remains true. New bindings cover feature edges, Hausdorff distance, region editing, periodic-node matching, quality gates, agglomeration options, and sequence blending/resampling. Operation results are integrated through fidelity-checked adapters; agglomeration stays unavailable for editable Kratos models because polyhedral cells exceed the model representation. The 16.25.0 declarations are additive for the functions this extension uses. The host now decodes bzip2 libMesh inputs because the published WASM artifact does not link bzip2.

The three boundary *behaviour* changes are all no-ops here, and each for a different reason worth recording. (1) `val_to_mesh` now feeds polygon/polyhedron blocks to the stored CSR directly, which is internal and semantically identical for what `modelToMeshio` emits. (2) `writeMesh`/`convert`/`convert_surface`/`convert_surface_ops` switched from `resolve_format` to `resolve_write_format`, so a write no longer lets **the file it replaces** choose its format — the fix for upstream's `.dat`→`marc` misresolution. It cannot reach us because `writeMeshioBytes` always passes an explicit key from `MESHIO_WRITE_FORMAT` and throws when it has none, so upstream never resolves by name on any path the extension owns. (3) `encoding: 'raw_appended'` for `vtu` works at runtime but is **absent from the shipped `index.d.ts`**, and `.vtu` is written by our own `vtkXmlWriter` anyway, so it is a new option rather than a missing capability. Separately, `ensight`'s `fortran: true` write option exists in the C++ and Python APIs but is **not exposed in the WASM binding** (`unknown key 'fortran' in the write options`), so there is no decision to make.

**The performance work landed largely where this extension does not call.** 16.15.0–16.21.0 are a large parallelisation and I/O campaign that claims byte-identical operation output. Timed here on a 48,000-tet mesh (16 threads, OpenMP backend, median of 3) across the routed oracles: `reorder` 1.61×, `estimateError` 1.13×, `hessian` 1.10×, `smooth` 1.06×, but `curvature` 0.83×, `surfaceWatertightCheck` 0.87× and `partitionLabels` 0.95× — **mixed, and no reason to claim a speedup in the release notes.** The reason is legible in the changelog: 16.16.0's shared facet/edge tables and 16.19.0's per-operation parallel phases target `extract_surface`, `refine`, `convert_cells(elevate)`, `optimize_volume` and `decimate`, and this extension **replaced every one of those with a native implementation** (`extractSkin.ts`, `refineMesh.ts`, `simplexify.ts`, `meshing.ts`) precisely because the meshio++ path was lossy. The large text-reader gains (Tecplot 2.1×, SU2 3.5×, the C++ `mdpa` reader 3.2×) are real but unmeasurable here: the committed `.tec`/`.dat`/`.msh` fixtures are a few kilobytes, so a 384 KB Exodus read is ~1 ms either way. Whether they matter is a question about a user's file size, not about this bump.

**One fix does reach a routed path silently.** 16.17.0 corrected Exodus `hexahedron20`/`hexahedron27` **node ordering** (SEACAS lists the vertical mid-edges before the top ring, and the Hex27 body centre before the face centres) and added `wedge15`/`pyramid13`. `.e`/`.exo`/`.ex2` are routed, so a file written by another Exodus writer now reads correctly where meshio++ previously scrambled those cells. The same release fixed the same class of bug in Kratos `.mdpa` and taught its reader `Prism3D15`/`Pyramid3D13`; that half is **not reachable** — `mdpa` is parsed natively here — and `geometryMap.ts` already carried `3:13`, `3:15`, `3:18`, `3:27` plus the `prism:15`/`pyramid:13` family fallbacks, so no mapping work was owed.

## Delivery rules

- **Keep the kernel current first.** Tier 0 precedes everything else: each tier's scope is measured against a specific meshio++ release, so a stale pin makes later estimates and acceptance checks describe the wrong artifact.
- **Prioritize integration and usability before breadth.** Tier 1 establishes a reliable shared foundation; later tiers add workflows on top. Independent UI work can proceed alongside kernel integration.
- **Full integration means access to the useful kernel surface through a consistent adapter.** It does not require deleting working native implementations or exposing duplicate buttons for equivalent algorithms. Choose a backend per operation on fidelity, performance, and maintenance cost.
- **Preserve the extension's data contract.** Original node and entity IDs, independent Elements/Conditions/Geometries ID spaces, Properties, constraints, SubModelParts, field components, and source-cell correspondence must survive wherever the operation permits. For topology-changing operations, define generated IDs, field transfer, and metadata handling explicitly.
- **MCP parity ships with every headless capability.** Update `src/mcp/tools.ts`, `src/mcp/register.ts`, `src/test/mcpTools.test.ts`, and the tool documentation in the same implementation change. UI-only work is exempt; a UI wrapper around a new analysis or edit is not.
- **Acceptance checks are part of each estimate.** Use real format fixtures, numerical invariants, cancellation and undo/redo tests, and packaged-extension checks where appropriate. Retest the target package as normal integration work rather than leaving features indefinitely labelled “needs live-WASM verification.”

## Tier 0 — Keep meshio++ up to date

Admission criterion: upkeep that every other tier depends on, because each tier below is scoped against a specific meshio++ release. Unlike the numbered items further down, this tier is **standing work**: it is never removed when a bump lands, only its status line is refreshed.

### 0. Track upstream meshio++ releases — S per release, recurring

**Standing work — last bumped 2026-09-30, 16.25.0 → 16.27.0 (16.26.0 was never published for WASM), verified against both published WASM variants.** The extension declares `@meshioplusplus/wasm: ^16.27.0` and the lockfile resolves the latest published release. Live counts are unchanged from 16.25.0: 76 readers, 68 writers, 37 options-aware readers, `hasCgnslib` true, the same reader and writer keys in both variants. The typings differ only by additive `MdpaInfo` fields for Kratos blocks, unreachable here because `.mdpa` is parsed natively. The single behaviour change is that **XDMF header metadata now reports its block regions** (16.25.0 answered none), still header-only; `meshio.test.ts` pins it beside Gmsh. `transientAudit.test.ts` passes unedited, so no timeline classification changed. The packaged `.vsix` is 28.85 MB. The former item 15 is complete: structural formats and Marc/Radioss writers route through explicit format handling, and new operation bindings are exposed through the editor and MCP.

The previous bump (2026-09-25, 15.4.0 → 16.14.0) was the first to cross a major version and the largest this tier has recorded; its classification is below. Its four buckets are backed by measurement, not by the changelog's prose: the binding diff is additive-only, two already-routed readers flipped options-awareness, one kernel fix (16.14.0's `conservative_interpolate` mass loss) removes a defect this extension would otherwise have inherited silently, and all 22 new reader keys are either routed or carry a recorded reason — with `mcpTools.test.ts` refusing the unexamined fallback so the next bump fails a test rather than a user.

The detection is now automated. `.github/workflows/meshio-watch.yml` runs weekly, compares the declared range against `npm view @meshioplusplus/wasm version`, and files or updates one issue when the latest release falls outside it. It reports rather than acts, because the work a major bump needs (classify, route, re-audit) is exactly what a version comparison and a Dependabot PR cannot do.

For each release, read the upstream changelog entry and classify what it touches for the WASM build before bumping:

- **Formats:** a new or changed reader/writer key (14.0.0 adds `vtkhdf`, with partition selection and transient `Steps`). Decide explicitly whether to route it, and extend `MESHIO_READER_KEYS`/`MESHIO_WRITER_KEYS`, `MESHIO_READ_CANDIDATES`, `EXPORT_MENU_GROUPS`, `SUPPORTED_MESH_EXTENSIONS` and the timeline lists. A key that the live artifact reports but nothing routes is listed as deliberately absent with a reason, never left unexamined.
- **Boundary and ABI:** option structs or dtypes crossing the wasm boundary (14.0.0 grows `ReadOptions` with `piece`, 13 → 14). Re-check `readMeshSelective`/`readMetadata` options handling, integer array types (`BigInt64Array`), and the `*_components` maps.
- **Behavior changes that alter what the extension already relies on:** 13.0.0 changes fallback semantics in the Python shims and pins C++ streams to the classic locale; whether any of that reaches the WASM build is to be measured, not assumed.
- **Fixes that retire a workaround:** upstream fixes (for example 12.1.0's MED and Gmsh higher-order node-ordering permutations, VTU polyhedron mixed-node-count `cell_data`) may make a local compensation redundant or wrong. Remove the workaround and its stale note in the same change.
- **Timeline admission:** re-test the readers still outside `IN_FILE_TIMELINE_EXTENSIONS` (Gmsh, UNV, the solver-result readers, and anything new) against the admission rule, which follows capability rather than reader options: an in-file timeline needs distinct time values that `readMetadata` can enumerate without a full read (`fellBackToFullRead: false`). A reader that merely accepts a `timeStep` option stays static, as `ansysinp` shows. Admit a reader only with a committed fixture that proves distinct step selection, and record each decision in `src/test/fixtures/transient/README.md`.

Then, per bump: update `package.json`/`package-lock.json`, confirm both `dist/meshio/` variants (sequential and `_mt`) still load and that `locateFile` stays name-aware, re-run the transient audit and the per-format options-awareness pins so a changed capability fails a test rather than a user, refresh `mesh_capabilities` expectations, and record the `.vsix` size change. Update the "Research baseline" date and the pinned version in the introduction, and add a `CHANGELOG.md` entry naming the version and the notable capability changes.


**KKSS embedding follow-up (S per upgrade):**

- **Evidence:** KKSS copies this extension's `dist/meshio` tree beside its application and MCP bundles. In the 2026-09-25 audit, mesh locked **16.14.0** and CAD independently locked 16.7.0; KKSS's bundled mesh/CAD MCP and MMG worker checks passed with the shared tree. Those exercised paths establish a tested baseline, not compatibility with every API or future version.
- **First useful increment:** mesh owns a documented staged-runtime contract and repeatable artifact checks for MCP, meshio++ loaders/WASM variants, and the MMG worker/WASM pair. KKSS owns copying those artifacts into its layout and testing its shared CAD/mesh runtime on every dependency update. Keep runtime separation an explicit response to a demonstrated conflict.
- **Verification:** load and execute from staged artifacts with development package resolution unavailable; check companion lookup, binary/version identity, and actionable missing-artifact errors. Repeat both engines' real operations in KKSS after either lockfile changes; see item 6 for the workflow matrix.
- **Done when:** an upgrade cannot pass packaging checks with a missing worker/kernel or an incompatible shared runtime, and the checked versions and layout are recorded with the result.

Automate the detection so it does not depend on remembering: **shipped** as `.github/workflows/meshio-watch.yml`, a scheduled job comparing the declared range with `npm view @meshioplusplus/wasm version` and reporting when the latest release is outside it, since that is the one case Dependabot's grouping misses.

**Acceptance:** the pinned version equals the latest published release (or a documented reason for staying behind is recorded here), the full test suite passes against it, every reader/writer key the live artifact reports is either routed or listed as deliberately absent, and no roadmap item cites a superseded version as its baseline. **MCP:** no new tool by itself; any newly routed format or operation must appear through `mesh_capabilities` and the existing info/convert tools in the same change.

### 2. Run expensive meshio++ work in cancellable workers — L

**Pending.** Extend the existing MMG worker pattern to costly meshio++ reads, analyses, and operations. ### 11. VTK-wasm as an experimental alternative renderer — decided

**Decided (2026-09-26): vtk.js stays the renderer; VTK-wasm ships as an experimental, opt-in alternative and will not replace it.** The item began as "replace vtk.js with VTK-wasm" and was worked as a gated migration (the [migration record](./vtk-wasm-migration.md) holds every gate, measurement and evidence file). Phases 0–4 passed: the three blockers of the 2026-09-18 [spike](./vtk-wasm-spike.md) were resolved for the pinned VTK **9.7.20260920** build (they were largely loading artifacts, plus a deterministic glue rewrite that removes Embind's dynamic code), the webview reaches its renderer only through a backend boundary (pixel-identical on vtk.js), the runtime ships verified in the `.vsix` with its licences (+13 MB), and the packaged extension boots VTK-wasm in real VS Code 1.138/1.139 under a CSP that adds only `'wasm-unsafe-eval'` and a scoped `connect-src`, falling back to vtk.js with an explanation when it cannot start. Measured on a software rasterizer, VTK-wasm meets every proposed performance and memory budget. The remaining differences are rendering style rather than defects — thin-line rasterization on dense edge overlays, VTK's own annotation actors, and a coplanar translucent wireframe the order-independent pass drops — and none justifies switching a working default. So the default switch and the vtk.js removal are **not pursued**, and hosts without JSPI keep vtk.js by construction.

**What remains supported:** `kratos.preview.renderer: "vtkwasm"` (tagged experimental) selects the backend for newly opened previews; the boundary (`webview/render/backend.ts`), the asset pipeline (`npm run vtkwasm:prepare`, verified at package time), the upstream watch workflow and the parity/smoke tooling (`scripts/render-parity/`, `scripts/vtk-wasm/g4-*.mjs`) stay, so the alternative keeps working and a future re-evaluation starts from measurements rather than from scratch. Revisit only with a concrete reason vtk.js cannot serve — a feature it lacks, or a real-GPU result (the checklist is in the migration record) showing VTK-wasm materially better. Rendering remains a separate runtime concern from the meshio++ kernel, and several limits belong to the webview runtime rather than to either backend: translucency under a software WebGL rasterizer, recording from a drawing buffer that is not preserved, browser codec availability, and the webview CSP. A kernel upgrade does not fix them, and neither does a backend swap. Address them where they surface (item 6 for rendering budgets, the recorder for capture) rather than as a reason to switch renderers.

**MCP:** none. The renderer is UI-only; the headless numerical tools are renderer-independent and keep their contracts.

### 13. Graceful solver stop on Windows — M

**Pending.** Current boundary: keep solver ownership and transport honest. On Windows, `stop`/`stopPid` (`src/problemtype/runProcess.ts`) go straight to TerminateProcess, so a stopped run gets no `KeyboardInterrupt`, no finalizers, and possibly a truncated last result file. A Ctrl+Break rung was tried and reverted after it froze `windows-latest` CI. Three facts rule out the console route: `GenerateConsoleCtrlEvent`'s process-group scoping fails under the nested pwsh → cmd → node chain; Node's `spawn` cannot request `CREATE_NEW_CONSOLE` (a `cmd /c start` wrapper returns the wrong pid); and `CTRL_BREAK_EVENT` reaches CPython as `SIGBREAK`, which does not raise `KeyboardInterrupt`.

**First useful increment:** a cooperative stop that needs no console, and so works on every platform. The generated `MainKratos.py` already wraps the analysis stage (`AnalysisStageWithFlush` in `src/problemtype/mainKratosTemplate.ts`). Make it check for a per-run stop sentinel beside the `<stem>.kratosrun.json` sidecar between solution steps, and end the loop through the stage's normal `Finalize`. The stop ladder writes the sentinel first, waits, and only then escalates to TerminateProcess. The sidecar records which rung ended the run, and a script generated before this change is escalated as today.

**Acceptance:** on `windows-latest` CI, a real Python child run through the extension's spawn path and through MCP `case_stop` finalizes and closes its last output file, and the run reads `cancelled`, not `failed`. A child that ignores the sentinel is still killed within the ladder's bound. A run whose process was lost is reported as `orphaned`/`detached`, never with an invented exit code. **MCP:** `case_stop` and `case_run` share the sentinel contract through `runFile.ts`; the MCP server still only starts detached runs and reads their logs.
