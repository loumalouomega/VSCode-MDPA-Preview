# Roadmap

Pending work for Kratos MDPA Preview, prioritizing full meshio++ integration, a clearer UI shared with CAD-Preview, and practical mesh preparation and results-analysis workflows. Existing foundations include MMG remeshing, meshio++ WASM, replayable edit histories, Python problemtypes, field visualization, time-series playback, tracked Kratos runs, and a headless MCP server.

**meshio++ is adopted at the locked 19.0.0 baseline.** Historical binding failures, missing side channels, format defects, and build omissions are no longer exclusions from this roadmap — `@meshioplusplus/wasm` is pinned at `^19.0.0`, the locked baseline for this integration, and the extension's packaged runtime declares and uses it (both artifact pairs: the lean build for every ordinary format, the full one for the CAD reads, the fitted STEP export and the codec fallbacks — see Tier 0's standing note). What remains is connecting its capabilities to the extension end to end, preserving Kratos semantics, and verifying the resulting workflows — the items below, not the dependency adoption itself. Keeping that pin current as upstream releases is its own standing item, Tier 0.

## Research baseline

Reviewed `/home/vicente/src/meshioplusplus` and the published WASM artifacts on **2026-09-29**, including releases 16.23.0–16.25.0 (re-probed 2026-09-30 against 16.27.0, 2026-10-09 against 16.32.0, 2026-10-19 against 17.8.0 and 2026-10-22 against 17.11.0: same inventory, see Tier 0), `bindings/wasm/js_bindings.cpp`, and `src/wasm/index.d.ts`. The extension now declares `@meshioplusplus/wasm: ^17.13.0`; sequential and OpenMP builds were loaded and probed alongside the previous packaged runtime.

**16.25.0 keeps the WASM format inventory stable and adds operation exports.** The live probe found 76 readers, 68 writers, and 37 options-aware readers in both 16.22.0 and 16.25.0; no format key was added or removed, and `hasCgnslib` remains true. New bindings cover feature edges, Hausdorff distance, region editing, periodic-node matching, quality gates, agglomeration options, and sequence blending/resampling. Operation results are integrated through fidelity-checked adapters; agglomeration stays unavailable for editable Kratos models because polyhedral cells exceed the model representation. The 16.25.0 declarations are additive for the functions this extension uses. The host now decodes bzip2 libMesh inputs because the published WASM artifact does not link bzip2.

The three boundary *behaviour* changes are all no-ops here, and each for a different reason worth recording. (1) `val_to_mesh` now feeds polygon/polyhedron blocks to the stored CSR directly, which is internal and semantically identical for what `modelToMeshio` emits. (2) `writeMesh`/`convert`/`convert_surface`/`convert_surface_ops` switched from `resolve_format` to `resolve_write_format`, so a write no longer lets **the file it replaces** choose its format — the fix for upstream's `.dat`→`marc` misresolution. It cannot reach us because `writeMeshioBytes` always passes an explicit key from `MESHIO_WRITE_FORMAT` and throws when it has none, so upstream never resolves by name on any path the extension owns. (3) `encoding: 'raw_appended'` for `vtu` works at runtime but is **absent from the shipped `index.d.ts`**, and `.vtu` is written by our own `vtkXmlWriter` anyway, so it is a new option rather than a missing capability. Separately, `ensight`'s `fortran: true` write option exists in the C++ and Python APIs but is **not exposed in the WASM binding** (`unknown key 'fortran' in the write options`), so there is no decision to make.

**The performance work landed largely where this extension does not call.** 16.15.0–16.21.0 are a large parallelisation and I/O campaign that claims byte-identical operation output. Timed here on a 48,000-tet mesh (16 threads, OpenMP backend, median of 3) across the routed oracles: `reorder` 1.61×, `estimateError` 1.13×, `hessian` 1.10×, `smooth` 1.06×, but `curvature` 0.83×, `surfaceWatertightCheck` 0.87× and `partitionLabels` 0.95× — **mixed, and no reason to claim a speedup in the release notes.** The reason is legible in the changelog: 16.16.0's shared facet/edge tables and 16.19.0's per-operation parallel phases target `extract_surface`, `refine`, `convert_cells(elevate)`, `optimize_volume` and `decimate`, and this extension **replaced every one of those with a native implementation** (`extractSkin.ts`, `refineMesh.ts`, `simplexify.ts`, `meshing.ts`) precisely because the meshio++ path was lossy. The large text-reader gains (Tecplot 2.1×, SU2 3.5×, the C++ `mdpa` reader 3.2×) are real but unmeasurable here: the committed `.tec`/`.dat`/`.msh` fixtures are a few kilobytes, so a 384 KB Exodus read is ~1 ms either way. Whether they matter is a question about a user's file size, not about this bump.

**One fix does reach a routed path silently.** 16.17.0 corrected Exodus `hexahedron20`/`hexahedron27` **node ordering** (SEACAS lists the vertical mid-edges before the top ring, and the Hex27 body centre before the face centres) and added `wedge15`/`pyramid13`. `.e`/`.exo`/`.ex2` are routed, so a file written by another Exodus writer now reads correctly where meshio++ previously scrambled those cells. The same release fixed the same class of bug in Kratos `.mdpa` and taught its reader `Prism3D15`/`Pyramid3D13`; that half is **not reachable** — `mdpa` is parsed natively here — and `geometryMap.ts` already carried `3:13`, `3:15`, `3:18`, `3:27` plus the `prism:15`/`pyramid:13` family fallbacks, so no mapping work was owed.

Reviewed `/home/vicente/src/meshioplusplus` on **2026-09-25**, including its changelog through 16.14.0, `bindings/wasm/js_bindings.cpp`, and capability documentation. The extension declares `@meshioplusplus/wasm: ^16.14.0`. **This is the first bump to cross a major version** — 16 releases from the 15.4.0 baseline, and the measurement below is against the *published* artifact (downloaded and loaded side by side with the installed 15.4.0), not against the changelog's prose.

The WASM boundary is unchanged and that is the load-bearing finding: `git diff v15.4.0..HEAD` over `bindings/wasm/js_bindings.cpp` and `index.d.ts` is **additive only** — one new export (`tensorInvariants`), zero removals, zero signature changes. The v16.0.0 C++ ABI break (`CellType::Custom` moving 76→77 with `Triangle7` appended) is irrelevant to a prebuilt-WASM consumer, so this is a routing exercise, not a compatibility one. The one boundary *behaviour* change is `read_with_info`/`readMeshSelective` for `unv` now taking `ReadOptions`.

Live capability probe, 15.4.0 → 16.14.0: **54 → 76 readers, 57 → 66 writers, 21 → 37 options-aware readers**, no key removed, `hasCgnslib` still true. 16.13.0's `vtx`/`szplt` are **absent from the WASM build entirely** (they need optional ADIOS2/TecIO, which this build does not link), so they need no routing decision. The bundled `dist/meshio/` grows 17.42 MB → 22.47 MB, **+5.05 MB across both variants**.

**22 new reader keys at the 16.14.0 audit.** Eleven are solver *results*: `abaqus_fil`, `ansys_rst`, `ansys_rst_cyclic`, `lsdyna_binout`, `lsdyna_d3plot`, `marc_t19`, `nastran_h5`, `nastran_op2`, `radioss_anim`, `radioss_th`, `xplt`. Seven carry a real extension and are routed (`.fil`, `.rst`/`.rth`, `.d3plot`, `.t19`, `.h5`, `.op2`, `.xplt`); the other four are found upstream by **file name, not extension**, so no extension this extension offers can reach them and they stay `inputFormat`-only. **None is admitted to the in-file timelines**: every one reports `fellBackToFullRead: true`, the `frd` bar. The other eleven were structural CAE formats (`code_aster`, `elmer`, `febio`, `femap`, `libmesh`, `marc`, `mfem`, `mphbin`, `patran`, `radioss`, `z88`). Those were deferred at that audit and are now integrated under the former task 15, completed 2026-09-29; writer formats without a unique extension remain discoverable through MCP's named-writer inventory.

Behaviour changes touching code this extension already runs, all re-measured rather than assumed: the Fluent `ansys` **writer** was rewritten (16.9.0, now emits Fluent's own face-based layout its own reader accepts — the round trip survives, the row-for-row connectivity guarantee does not, and the test now says which); `conservative_interpolate` **lost up to 0.7% of mass** between aligned meshes until 16.14.0 fixed it, which is now pinned positively; UNV's group entity types were **swapped** and its `hexahedron20`/`wedge15` mid-edge order corrected (15.6.0); the Nastran bulk deck is now read **natively** (16.2.0), so `.bdf`/`.fem`/`.nas` open at all where they previously needed a Python twin wasm does not have; MED gained `HEXA27`/`PENTA18` and `triangle7` became a real cell type (16.0.0, `wedge18` and `triangle7` are now mapped to drawable VTK types); COMSOL's quadratic node order was **corrected** (16.1.0); and a non-transient **multi-zone Tecplot file now reads all its zones** instead of silently discarding all but the first (15.5.0).

The transient audit was re-run against 16.14.0 (`src/test/fixtures/transient/README.md`): **no existing classification changed.** Two already-routed readers flipped options-awareness: `unv` (genuinely, and still not admitted) and `ansysinp` (which registers a `ReadOptions` overload for a format with no time axis — the sharpest case of the flag not being capability). `mcpTools.test.ts` now **refuses** any unrouted key left on the `UNEXAMINED_REASON` fallback, so the next release's new formats fail a test until each is routed or its reason is written down. `.github/workflows/meshio-watch.yml` reports a major-version lag on a schedule, because a caret range never crosses a major and Dependabot's minor/patch group structurally cannot propose it.

## Delivery rules

- **Keep the kernel current first.** Tier 0 precedes everything else: each tier's scope is measured against a specific meshio++ release, so a stale pin makes later estimates and acceptance checks describe the wrong artifact.
- **Prioritize integration and usability before breadth.** Tier 1 establishes a reliable shared foundation; later tiers add workflows on top. Independent UI work can proceed alongside kernel integration.
- **Full integration means access to the useful kernel surface through a consistent adapter.** It does not require deleting working native implementations or exposing duplicate buttons for equivalent algorithms. Choose a backend per operation on fidelity, performance, and maintenance cost.
- **Preserve the extension's data contract.** Original node and entity IDs, independent Elements/Conditions/Geometries ID spaces, Properties, constraints, SubModelParts, field components, and source-cell correspondence must survive wherever the operation permits. For topology-changing operations, define generated IDs, field transfer, and metadata handling explicitly.
- **MCP parity ships with every headless capability.** Update `src/mcp/tools.ts`, `src/mcp/register.ts`, `src/test/mcpTools.test.ts`, and the tool documentation in the same implementation change. UI-only work is exempt; a UI wrapper around a new analysis or edit is not.
- **Acceptance checks are part of each estimate.** Use real format fixtures, numerical invariants, cancellation and undo/redo tests, and packaged-extension checks where appropriate. Retest the target package as normal integration work rather than leaving features indefinitely labelled “needs live-WASM verification.”

### 12. VTK-wasm as an experimental alternative renderer — decided

**Decided (2026-09-26): vtk.js stays the renderer; VTK-wasm ships as an experimental, opt-in alternative and will not replace it.** The item began as "replace vtk.js with VTK-wasm" and was worked as a gated migration (the [migration record](./vtk-wasm-migration.md) holds every gate, measurement and evidence file). Phases 0–4 passed: the three blockers of the 2026-09-18 [spike](./vtk-wasm-spike.md) were resolved for the pinned VTK **9.7.20260920** build (they were largely loading artifacts, plus a deterministic glue rewrite that removes Embind's dynamic code), the webview reaches its renderer only through a backend boundary (pixel-identical on vtk.js), the runtime ships verified in the `.vsix` with its licences (+13 MB), and the packaged extension boots VTK-wasm in real VS Code 1.138/1.139 under a CSP that adds only `'wasm-unsafe-eval'` and a scoped `connect-src`, falling back to vtk.js with an explanation when it cannot start. Measured on a software rasterizer, VTK-wasm meets every proposed performance and memory budget. The remaining differences are rendering style rather than defects — thin-line rasterization on dense edge overlays, VTK's own annotation actors, and a coplanar translucent wireframe the order-independent pass drops — and none justifies switching a working default. So the default switch and the vtk.js removal are **not pursued**, and hosts without JSPI keep vtk.js by construction.

**What remains supported:** `kratos.preview.renderer: "vtkwasm"` (tagged experimental) selects the backend for newly opened previews; the boundary (`webview/render/backend.ts`), the asset pipeline (`npm run vtkwasm:prepare`, verified at package time), the upstream watch workflow and the parity/smoke tooling (`scripts/render-parity/`, `scripts/vtk-wasm/g4-*.mjs`) stay, so the alternative keeps working and a future re-evaluation starts from measurements rather than from scratch. Revisit only with a concrete reason vtk.js cannot serve — a feature it lacks, or a real-GPU result (the checklist is in the migration record) showing VTK-wasm materially better. Rendering remains a separate runtime concern from the meshio++ kernel, and several limits belong to the webview runtime rather than to either backend: translucency under a software WebGL rasterizer, recording from a drawing buffer that is not preserved, browser codec availability, and the webview CSP. A kernel upgrade does not fix them, and neither does a backend swap. Address them where they surface (item 2 for large-mesh rendering budgets, the recorder for capture) rather than as a reason to switch renderers.

**MCP:** none. The renderer is UI-only; the headless numerical tools are renderer-independent and keep their contracts.

### 77. Optimization and ROM options left out "until asked" — M

**Pending — added 2026-11-10 (recovered from Non-goals; depends on item 18's solver verification).** The standing exclusion lists four things kept out until someone asked: the shape control's `mesh_moving_analysis` (`doc/guide/optimization.md`), the ANN-enhanced ROM decoder (`doc/guide/reduced-order-models.md`), the older ShapeOptimizationApplication, and optimization primals other than structural. Take them in order of cost. First `mesh_moving_analysis`, because without it a shape optimization of anything but a small change tangles the interior mesh, and item 46's mesh-quality series can show whether it helped. Second a thermal primal for the optimization problemtype, which reuses the convection-diffusion generator. Third the ANN decoder, only if the application's Python dependencies are present in the user's environment, probed and reported like any other missing application. The older ShapeOptimizationApplication stays out: Kratos' own optimization application supersedes it.

**Acceptance:** a shape optimization case with mesh motion enabled reports no inverted element through item 46's series where the run without it does; each added option is refused by name when its application is missing. **MCP:** `case_generate`/`case_optimization`/`case_rom` take the options through the state.

## Non-goals / known constraints

Standing exclusions, gathered here on 2026-10-31 from `CLAUDE.md`, the guides and the out-of-scope lines of the items above (this file had no such section, while `CLAUDE.md` cited one). Each says what would change our mind; where a narrower version is now worth doing, it names the item that recovers it. **Re-read 2026-11-10** against the 19.0.0 kernel and the items added that day: three entries turned into work (items 75, 76 and 77) and are reworded below to say what remains excluded; the others were kept, each for the reason it states.

- **Run progress or convergence inferred from solver stdout.** Progress comes from `vtk_output/` and convergence from solver-published records (`kkss-convergence-v2.jsonl`), never from log lines; stdout is shown verbatim and used only as a "last output" tooltip. A log format is not a contract, and a parsed line that changes between Kratos versions would turn into a wrong verdict silently. *Would change our mind:* nothing for verdicts. Narrower versions that respect the rule: monitors refreshed from written frames (delivered 2026-11-03, former roadmap item 26), item 17 (solver-written monitors) and item 70 (a terminal-launched run tracked through the records its own driver writes).
- **Adopting meshio++'s returned mesh for operations whose round trip is lossy.** `modelToMeshio`/`meshioToModel` lose entity kinds, Properties ids and original entity ids, so operations use meshio++ as an oracle (Group A) or are native (Group B); only explicitly adopting operations (`ADOPTING_OPS`) take the returned mesh and rebuild what it drops. *Would change our mind:* a meshio++ release that carries per-cell source indices and kinds through every operation, measured by the export-fidelity matrix. **Being re-measured:** item 76 probes each operation against 19.0.0 and moves the ones that now carry a complete back-map into the adopting set.
- **In-place surface decimation.** It rewrites topology with no back-map, drops side regions and blends integer tags as floats. The lossy-by-intent version shipped as the `mesh_derive` `decimate` copy (`deriveMesh.ts`), which is why this stays excluded only as an *edit*. *Would change our mind:* a decimator that reports a parent map. Item 76 checks whether the current binding does.
- **Python-only meshio++ capabilities advertised as bundled.** Point budgets, proximity graphs, PMSH/Zarr/CAE/USD time-series exports and PhysicsNeMo inference are not in the WASM build. They are reachable only through item 11's optional companion, and `mesh_capabilities` names the backend that provides each one. *Would change our mind:* a WASM binding for one of them.
- **Readers gated on vendor libraries the WASM build cannot link** (`vtx` needs ADIOS2, `szplt` needs TecIO). *Would change our mind:* a dependency-free or freely redistributable path.
- **Routing `medit_sol` (17.23.0) as a mesh.** A SolAtVertices file carries values with no geometry, so it would open as nothing and a write would drop the mesh (`UNROUTED_READER_REASONS`). **Recovered 2026-11-10 as item 75:** the companion rule (a `.sol` read as fields of its sibling `.mesh`, vertex counts matching exactly) is the narrower version; a `.sol` with no mesh beside it stays unopenable.
- **`agglomerate`, `subdivide` and other polyhedral-output operations.** The editable model decomposes polyhedra on read, so their output cannot be kept; item 10 owns the native polyhedral path that would admit them. **`retagRegions`** stays unrouted because SubModelParts keep no native region tags. **`fitPrimitives`** is exposed as the `mesh_fit_primitives` report (2026-11-01); it is not an editing operation.
- **Solvers and coupling outside Kratos's own applications.** CoSimIO and non-Kratos participants, embedded FSI, and the IBQN/randomized-SVD accelerators stay out until a fixture proves them; MPI/Trilinos generation is recovered by item 32. **Recovered 2026-11-10 as item 77:** the shape control's `mesh_moving_analysis`, a thermal optimization primal and the ANN-enhanced ROM decoder, in that order and after item 18's solver verification; the older ShapeOptimizationApplication stays out because Kratos' own optimization application supersedes it. Structural contact, thermo-mechanical coupling, DEM and MPM are Kratos' own applications and were never excluded, only absent: items 55, 68 and 69.
- **Translating machine-facing contracts.** MCP tool, parameter and result names, recipes, sidecars, `.mdpa` keywords and exported numbers stay English and `.`-decimal in every locale (item 15).
- **Switching the default renderer to VTK-wasm.** Decided in item 12: VTK-wasm stays experimental and opt-in, revisited only for a feature vtk.js lacks or a real-GPU measurement.
- **MCP tools for embedded editors and launchers.** The Flowgraph node editor, the Kratos sidebar, What's New and the command line are ways of reaching capabilities MCP already exposes by path, so they have no headless mirror. Rendering a picture of a view (item 64) is not such a mirror: no other tool can produce an image, and it drives no editor.
