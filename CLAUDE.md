# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run compile        # dev build (includes source maps)
npm run package        # production build (minified, no source maps)
npm run typecheck      # type-check only — never use tsc to emit shipped code
npm test               # compile tests then run with Node's built-in test runner
npm run build:icons    # regenerate src/toolbarIcons.ts from icons/tikz-ui/*.tex (needs pdflatex + pdftocairo)
npm run install-ext    # build + copy into ~/.vscode-server/extensions/ (bash install.sh)
npm run reinstall      # bump patch version, package a .vsix, install via `code --install-extension`, prune stale versions (bash scripts/reinstall-local.sh) — also available as the "Reinstall extension (local/Remote-SSH)" VS Code task
npm run mcp            # run the standalone MCP server (node dist/mcpServer.js; needs a compile first) — register with: claude mcp add kratos-mdpa -- node <abs repo>/dist/mcpServer.js
```

**esbuild owns all emit** — `tsc` is only for type-checking and test compilation. Do not run `tsc` to build the extension.

To run a single test file:
```bash
npm run build:tests && node --test out/test/mdpaParser.test.js
```

The documentation site is a **separate, isolated npm package** under `doc/` (its own `package.json`/`package-lock.json`, `"type": "module"`) so VitePress never touches the extension build or the packaged `.vsix`. Run its commands from inside `doc/`:
```bash
cd doc && npm install       # first time only
npm run docs:dev            # local dev server with HMR
npm run docs:build          # production build → doc/.vitepress/dist (fails on dead links)
npm run docs:preview        # serve the built site
```

## Architecture

**MCP server sync rule**: `src/mcp/tools.ts` mirrors the extension's mesh/problemtype capabilities as MCP tools. Whenever an extension feature is added or modified — a new/changed op in `operations.ts`, a new mesh format/writer, a new mesh inspection/quality capability, a problemtype-pipeline change, a new sidebar/palette action — update the MCP server in the same change: the tool surface in `src/mcp/tools.ts`/`src/mcp/register.ts`, its tests in `src/test/mcpTools.test.ts`, and the tool tables here and in README.md. (The Flowgraph embedding is deliberately **UI-only** — an interactive iframe editor with no headless equivalent — so it is intentionally **not** exposed as an MCP tool; the `flowgraph` builtin still appears via `problemtype_list`/`problemtype_describe`. The **Kratos sidebar** — its activity-bar container, welcome buttons, Recent Meshes list and empty-preview launcher — is exempt for the same reason: it is a way of *reaching* capabilities the MCP server already exposes by path, so there is nothing headless to mirror.)

**Flowgraph embedding** (`src/flowgraphServer.ts` + `src/flowgraphController.ts` + `webview/flowgraphPane.ts` + `src/flowgraphMessages.ts` + `flowgraph-bridge/vscode-bridge.js` + `src/problemtype/builtins/flowgraph.ts`): the **Flowgraph (node editor)** built-in problemtype (`view: "flowgraph"`) embeds the AGPL-3.0 [`@kratos-flowgraph/flowgraph`](https://www.npmjs.com/package/@kratos-flowgraph/flowgraph) litegraph editor. It is a Node/Express+EJS server app, not an importable browser bundle, so it is **run, not bundled**: `flowgraphServer.ts` (a third esbuild entry → `dist/flowgraphServer.js`) serves flowgraph's copied `public/`+`views/` (in `dist/flowgraph/`) on an ephemeral port — its own tiny Express wrapper (no `config` package, no `/upload_json`/`/run_simulation` routes; the EJS engine is registered explicitly via `app.engine("ejs", ejs.__express)` so esbuild bundles it past Express's dynamic `require`). `flowgraphController.ts` (the only new vscode-importing host module; one shared, ref-counted instance owned by `extension.ts`, injected into both preview providers) forks the server on the first `flowgraphStart`, resolves `vscode.env.asExternalUri` and hands the webview a `flowgraphReady{url,origin}`; the webview embeds it in an `<iframe>` in a split pane (`webview/flowgraphPane.ts`, split of `#viewport` into `#vtk-sub` + `#flowgraph-pane`, horizontal default, orientation toggle). Because the iframe is a **separate http origin** (its own absent CSP), flowgraph's jQuery/CDN/eval run unmodified; the webview CSP only relaxes `frame-src` (scoped to `http://localhost:*`/`127.0.0.1:*`/`https:` since the tunneled origin is resolved after the CSP is baked). The **two-way ProjectParameters bridge** rides cross-origin postMessage (`flowgraphMessages.ts` is the shared contract; `vscode-bridge.js`, injected into the served page, speaks the iframe half): on open, `PtController.getProjectParametersJson()` (compute-only, no disk writes) seeds the graph via `graph.configure_project_parameters`; flowgraph's Generate posts the exported ProjectParameters back, which `PtController.applyExternalProjectParameters` writes next to the mdpa. MDPA-provider only (problemtypes are MDPA-only); the VTK provider ships the same (inert) chrome so the shared `webview/main.ts` stays uniform.

The extension has two completely separate runtimes that communicate only via `postMessage`:

### Extension host (Node.js, `src/`)
- `extension.ts` — registers two custom editors (`kratos.mdpaPreview` for `.mdpa`, `kratos.vtkPreview` for the mesh formats `.vtk`/`.vtu`/`.vtp`/`.vti`/`.vts`/`.vtr`/`.vtm`/`.stl`/`.obj`/`.ply`) and commands. A shared `postToActive` helper forwards panel-level commands (reset camera, field, screenshot, etc.) to whichever provider currently has an active panel. `contributes.keybindings` gates the reference chord set (Ctrl+O/S/Shift+S/E and Ctrl+Alt+S/O/P) to the two preview tabs via `activeCustomEditorId`, so no global binding is clobbered. The `kratos.mesh.*` commands (open/save/saveAs/export) route through `dispatchMenu` (which calls each provider's `dispatchMenu`) for Command-Palette parity with the in-webview File menu. `activate` also builds the `RecentMeshStore` and registers the Kratos activity-bar container's views (see `src/sidebarViews.ts`) plus the `kratos.preview.openEmpty` command, both of which work with no file and no active panel — as `kratos.mesh.open` and `kratos.problem.load` already did. `activate` ends with a fire-and-forget `showWhatsNewIfNeeded(context)` (see `src/whatsNew.ts`); activation is gated on `onStartupFinished` so the check runs on every session.
- `src/whatsNew.ts` (vscode glue) + `src/whatsNewCore.ts` (pure) — the version-gated **"What's New"** popup. On startup `showWhatsNewIfNeeded` compares `context.extension.packageJSON.version` against the `"lastShownVersion"` globalState key (same one-time-gate pattern as `meshExport.ts`'s overwrite warning): on an upgrade it reads root `CHANGELOG.md` (`context.extensionPath`, `fs.existsSync`-guarded), shows the entries newer than the last-seen version in a static (no-script) `createWebviewPanel`, then advances the marker; a fresh install (undefined marker) is set silently with no popup, and a downgrade/missing-changelog just advances the marker. Honors the `kratos.showWhatsNew` setting (default true). `showWhatsNewCommand` backs the manual **Kratos MDPA: Show What's New** command (`kratos.mdpa.whatsNew`) and shows the full changelog. `whatsNewCore.ts` is the vscode-free, Node-testable core: `parseChangelog` (Keep-a-Changelog `## [x.y.z] - date` sections, excluding the intro + trailing link-def block), `compareSemver`, `selectNewEntries` (strictly-newer; `[]` for undefined lastShown), and `changelogToHtml` (HTML-escaped mini-markdown → bullets/`**bold**`/`` `code` ``/`[text](url)` links, never a `<script>`). Intentionally **not** an MCP tool — UI-only, like the Flowgraph embedding. Unit tests: `src/test/whatsNewCore.test.ts`.
- **The Kratos sidebar** (`package.json`'s `viewsContainers`/`views`/`viewsWelcome` + `src/sidebarViews.ts` + `src/recentMeshes.ts` + `src/recentMeshesCore.ts` + `src/emptyPreview.ts` + `images/kratos-activitybar.svg`) — the activity-bar entry point, and the answer to "how do I open this extension without opening a file?". Both preview providers are custom editors, so before this the only routes in were the editor-title button, the Explorer context menu and the palette; `kratos.mesh.open`/`kratos.problem.load` already needed neither a file nor an active panel, they were simply **undiscoverable** (their keybindings are gated on `activeCustomEditorId`). Four decisions are load-bearing:
  - **Two views, not one.** `viewsWelcome` renders only while its view has no children, so the action buttons and the recent-mesh rows cannot share a view — the buttons would vanish the moment a first mesh was remembered. Hence `kratos.start` (an always-empty tree whose only job is to host the welcome buttons) and `kratos.recentMeshes` beside it.
  - **"Kratos Runs" in both places means two view ids over one provider.** VS Code view ids are globally unique and a view cannot sit in two containers, so `runTreeView.ts` calls `createTreeView` twice (`kratos.runs` in the Explorer, `kratos.runsSidebar` in the container) against a single `RunTreeProvider` — not view-bound, so one `onDidChangeTreeData` drives both. The cost is a manifest one and it is silent when missed: every `menus` entry for a run command must name **both** ids, parenthesised (`(view == kratos.runs || view == kratos.runsSidebar) && …`) because `&&` binds tighter than `||`. `src/test/packageContributes.test.ts` asserts it.
  - **The icon must not live in `icons/svg-ui/`.** An activity-bar container needs a real SVG *file* (VS Code resolves `viewsContainers.icon` from the manifest and renders it as a CSS mask), and `icons/build-toolbar-icons.mjs` globs that directory wholesale into the generated `src/toolbarIcons.ts`, which is inlined into **both** bundles — so a container icon placed there would add a bogus `ToolbarIconId` and ~2 KB to each. It lives at `images/kratos-activitybar.svg` with a `!images/kratos-activitybar.svg` negation in `.vscodeignore`, mirroring the existing `!images/icon.png`; without that negation `images/**` excludes it and the button ships **blank**. The artwork is the marketplace L-tromino from `icons/tikz-icon/icon.tex` (vertex box exactly 54x54, so `y_svg = 54 - y_tikz`), redrawn **stroke-only** because a mask flattens the teal *fills* into a featureless blob, minus the magnifier badge (it silts up at 24 px) and minus the `rotate=-7` (the box is pre-stroke, hence `viewBox="-3 -3 60 60"`).
  - **The empty preview is a launcher shell, not a session.** See `src/emptyPreview.ts` and the two matching non-goals in `doc/roadmap.md`.
  `recentMeshesCore.ts` is the pure list (newest-first, deduped by resolved path — case-folded on **win32 only**, since folding everywhere would merge two genuinely distinct meshes on Linux — capped at 10, tolerant of whatever globalState holds); `recentMeshes.ts` is the globalState glue that prunes vanished files **on read** rather than via a watcher and drives the `kratos.hasRecentMeshes` context key the way `RunManager` drives `kratos.hasRuns`. Recording hooks into each provider's `resolveCustomEditor` right after `document.uri.fsPath` — the one choke point every route to a preview already passes through. Unit tests: `src/test/recentMeshes.test.ts`, `src/test/packageContributes.test.ts`.
- `src/meshDocument.ts` (vscode glue) + `src/parser/opsBackup.ts` (pure) — the **unsaved-edits contract**: both providers implement `vscode.CustomEditorProvider<T>`, so a mesh edit is real unsaved work — dirty dot, "save changes?" prompt on close, hot exit, and `Ctrl+Z`. Before this they were `CustomReadonlyEditorProvider`s, so closing a tab discarded the whole `OperationHistory` **silently**: VS Code was never told there was anything to save, so its prompt and Hot Exit could not fire, and `Ctrl+Z` was inert while the extension *did* rebind `Ctrl+S`/`Ctrl+O`/`Ctrl+E` in the same scope. Four decisions are load-bearing:
  - **`CustomDocumentContentChangeEvent`, never `CustomDocumentEditEvent`** (the API forbids mixing them). The edit-event flavour hands VS Code ownership of the undo stack, which would make `OperationHistory.cursor` a second cursor that must stay in lockstep with it — and of the fourteen sites that move ops/cursor, five have no faithful encoding: `clear()` and the three `load()` sites cannot truncate or replace VS Code's stack without new `snapshotState`/`restoreState` core API, `revertTo(n)` degrades into |c−n| awaited replays, and one unguarded fire on a noop (`applyNew` does **not** record one) desyncs the two permanently. **This repo has no VS Code integration harness**, so none of that could be tested — the same doctrine that pushed `timelineKindFor` below the vscode line. So `opHistoryCore.ts` is untouched, every sidebar behaviour is unchanged, and `Ctrl+Z`/`Ctrl+Shift+Z` ship as `kratos.mesh.undo`/`redo` gated on `activeCustomEditorId` like the eight bindings already there. The stated cost: the marker is a **one-way latch**, cleared only by a save or File ▸ Revert File, so undoing back to zero ops leaves it set — over-prompting rather than under-prompting.
  - **Hooks on the document, not state hoisted onto it.** `saveCustomDocument` and its three siblings are handed only a document, while `history`/`lastModel`/`exportCtx()` live inside `resolveCustomEditor`'s several-hundred-line closure — the closure `emptyPreview.ts` and its roadmap non-goal already declined to dismantle. `resolveCustomEditor` instead publishes a `MeshEditorHooks` object onto the document, the idiom this codebase already uses for `activeMenuHandler`/`activeReloadHandler`/`activePtController`, the `exportCtx()` thunk itself, and `vtkEditorProvider`'s `panelsByPath` `{reveal, goToLatest}`. One hooks object per document is sound only because both providers register with `supportsMultipleEditorsPerDocument: false`. The hooks are deliberately **not** cleared in `onDidDispose` (unlike the `active*` fields right beside them): closing a dirty tab makes VS Code call `saveCustomDocument` *during* teardown, and nothing they close over needs a live webview.
  - **A refused save must not resolve.** `saveMesh` returns early without writing and without throwing in four places (`.foam`, a non-exportable extension, a declined overwrite modal, `serializeToPath`'s `wouldOverwriteOpenFoamCase` backstop) — and VS Code clears the dirty marker whenever `saveCustomDocument` resolves, so routing those through unchanged would report success on an unwritten file, i.e. the data-loss bug arriving through its own fix. `serializeModelToPath`/`serializeToPath`/`saveMesh`/`saveMeshAs`/`runMenu` were widened to `Promise<boolean>` (booleans rather than throws: each site already shows its own warning, and a rejected `saveCustomDocument` would report twice), and `saveDocument` throws on false. Both save routes must end at `saveCustomDocument` since only VS Code can clear the dot, so `kratos.mesh.save` and each provider's `menuSave` branch go through **`vscode.workspace.save(uri)`** — not `workbench.action.files.save`, because it names the editor and therefore works when the click came from the webview's File menu and focus is nowhere near the tab. **Auto-save is refused**, which is the one behaviour becoming a real editor makes newly dangerous and was found by driving the packaged extension in headless code-server: with `files.autoSave` on (the default in that VS Code 1.135 build), a translate op popped the overwrite modal one second later, and since that modal is a ONE-TIME `globalState` gate, accepting it once makes every later automatic save silent — so "click an operation to see what it does" becomes "rewrite the mesh you opened". `MeshPreviewDocument.saveRequested` is a latch set by the extension's own save routes and consumed by `saveDocument`, which refuses an unrequested in-place save while `files.autoSave` is non-`off` and `kratos.preview.autoSave` is false. Refusing keeps the marker, which is exactly right — the work IS unsaved. With auto-save off nothing is refused, so the close prompt's Save button and Save All reach the write path untouched. `Ctrl+Shift+S` **keeps** the extension's own Save As (format-aware `.vtu` fallback, the `.foam` guard, and no editor swap), while `saveCustomDocumentAs` is still implemented over the new `saveMeshToPath` so VS Code's own Save As is safe rather than destructive.
  - **The backup is the ops recipe, not the mesh.** `backupCustomDocument` fires ~1 s after editing stops, so re-serializing a multi-GB mesh into `storagePath` on every idle tick is untenable — and the recipe is already this extension's representation of unsaved work (`saveOps` writes it, `parseOpsJson` reads it, a problem archive carries it), so the format keeps one definition. `opsBackup.ts` is the `fs`+serializer half, in `parser/` so `tsconfig.test.json` picks it up (`src/test/opsBackup.test.ts`) — the `opHistoryCore`/`opHistory` split. Restore rides `openContext.backupId` into `document.restoredOps` and is consumed at the existing `takePendingOps` sites. Three rules there: **the backup wins** over a pending Load-problem recipe (it is strictly newer *and* already contains it, since a Load-problem replay goes through the same history the backup was serialized from — replaying both double-applies everything), and the pending one is consumed anyway to honour its one-shot contract; **`restoredOps` is itself one-shot** (`takeRestoredOps()`), because VTK's `applyPendingOps` runs on **every** frame post and `load()` resets the cursor to the end of the stack, so a recipe left in place would silently undo the user's undos on every arrow-key press; and `backupOps` **refuses while `restoredOps` is unconsumed**, since a summarized document has no base and would otherwise serialize an empty history over the very backup those ops came from. An empty stack the user genuinely undid back to *is* written faithfully and reads back as nothing to restore. The summary branch warns that a restored recipe is waiting rather than dropping it silently. Fire sites: `opApply.ts`'s new `OpRunnerDeps.onHistoryChanged` (guarded by `!outcome.noop` / `appliedCount > 0`, and called on the batch failure path too since a batch can commit before it throws) plus the sidebar `opUndo`/`opRedo`/`opRevertTo`/`loadOps` handlers; **never** from `rebase`/`replayOntoBase`/`adoptFrame`/`setBase`/`revert`, which is what keeps a solver rewriting a file and a timeline scrub from claiming unsaved work. Each provider's `markDirty()` fires only when `appliedCount() > 0`, so a clamped undo at cursor 0 and a Clear that empties the stack never claim it either. Intentionally **not** an MCP tool — the edit history is already exposed through `mesh_transform`, and dirty markers/hot exit are UI-only, the Flowgraph/What's-New exemption class. Manifest tests: `src/test/packageContributes.test.ts` (which asserted nothing about keybindings before this).
- `src/emptyPreview.ts` — the standalone, file-less preview behind **Open Empty Preview**. A single `createWebviewPanel` (revealed rather than duplicated) carrying the same chrome over an empty viewport. It is deliberately a **launcher**: its only working actions are File ▸ Open and Load problem…, which it calls **directly** rather than through `runMenu` — `runMenu` discards the opened uri, and the uri is the whole point, since a *cancelled* dialog must leave the shell standing while a successful one disposes it (a shell that stayed would sit behind the real preview as a second, permanently empty tab that looks like a bug). Every other message answers with one "Open a mesh first" info line. `openMesh()`/`loadProblem()` were widened from `Promise<void>` to `Promise<vscode.Uri | undefined>` for this.
- `src/previewHtml.ts` (vscode glue) + `buildPreviewHtml`/`getNonce` in `src/webviewChrome.ts` (pure) — the **one `<html>` skeleton** behind the MDPA provider, the VTK provider and the empty panel. It used to be a private `getHtml` duplicated in both providers, byte-identical apart from `<title>` and an MDPA-only `data-flowgraph-orientation` (and `getNonce` duplicated verbatim beside it, and a third copy of `webviewChrome.ts`'s own `ic()` helper named `icon()`). `buildPreviewHtml` takes already-resolved **strings**, not a `vscode.Webview`: that keeps `webviewChrome.ts` vscode-free (the webview bundle and `scripts/screenshots/build-harness.mjs` both import from it) and makes the document Node-testable, while a structural `{asWebviewUri}` would have bought nothing since resolving a media file still needs `vscode.Uri.joinPath` at the call site. `previewHtml.ts` does that resolution and also owns `previewWebviewOptions` (`media/` is the only `localResourceRoots`). **`startEmpty`** emits `data-start-empty="1"` plus the `#empty-hint` overlay: the webview normally leaves `#app` hidden behind `LOADING_HTML` until `hideLoading()` runs, which only happens on a `model`/`vtkFrame`/`error` message, so with no file the panel would sit on the spinner forever — `webview/main.ts` reads the attribute next to its `ready` post. An **attribute rather than a message** because a host round trip would flash the spinner first, and a new message case would touch both providers' switches for the benefit of a panel that loads nothing. Unit tests: `src/test/previewHtml.test.ts`, whose "MDPA and VTK differ ONLY by title and orientation" assertion is the anti-drift guard the hoist exists for.

- `src/meshAnalysis.ts` — host side of the webview's two READ-ONLY analyses (`runMeshAnalysis`). Both questions — "is this boundary closed?" (`watertight.ts`) and "what does this field integrate to?" (`fieldIntegrate.ts`) — are answered by meshio++, whose wasm is **host-only** (the package is `external` and lives in `dist/meshio/`, unreachable from the webview bundle). Every other analysis panel in this extension computes in the webview from a pure module; these two cannot, so they take one message round trip. **One** request/response pair (`meshAnalysis`/`meshAnalysisResult`) covers both rather than two, because the shape is identical and a third analysis should be a new `kind`. That rule is about **single-shot analyses of the CURRENTLY loaded model**, which is all `runMeshAnalysis(msg, lastModel)` is handed: the time-series scan is deliberately NOT one of these — it walks many files, streams progress and cancels, so it has its own `fieldSeries`/`fieldSeriesProgress`/`fieldSeriesResult`/`fieldSeriesCancel` family in the shape of `applyOp`/`opProgress`/`opCancel`. Neither modifies the model, so neither is an `OpRecord` and neither leaves an undo entry. An error becomes a `message` on the reply rather than a rejection.
- `src/meshExport.ts` — shared host-side File-menu handlers used by both providers: `openMesh` (showOpenDialog → `vscode.openWith` the matching viewType), `saveMesh` (re-serialise to the source's own format and overwrite it, one-time `globalState`-gated overwrite warning), `saveMeshAs`, `saveMeshToPath` (the dialog-free half of Save As, so `saveCustomDocumentAs` inherits `serializeToPath`'s OpenFOAM backstop without that function becoming public — see `src/meshDocument.ts` for why these four all return `Promise<boolean>` now), `exportMesh`, `exportSubModelPart` (slices one SubModelPart out via `extractSubModelPart` and writes it to a chosen format), `exportSkin(ctx, targetExt?)` (extracts the boundary via `extractSkinModel` — `extractSkin.ts` — and writes it; `showQuickPick`s a format when `targetExt` is omitted, driving the Advanced-menu **Export skin…** entry / `kratos.mesh.exportSkin`), `exportDataTable(ctx, kind, format?, opts?)` (the Data table's CSV/XLSX export — see the Data table section below; it does **not** go through `serializeModelToPath`, which is the mesh-writer path and would reject a `.csv`, and it rebuilds the table from `ctx.model` using the `kind`+`opts` the panel sends rather than receiving its rows, since a real mesh's CSV has no business crossing postMessage), `exportSeriesCsv(ctx, csv, suffix)` (saves the time-series CSV the webview built — see the fieldSeries section for why that direction is reversed), `pickMergeMeshFile()` (a multi-select `showOpenDialog` for the mergeMesh sidebar form's file field, listing `.mdpa` first, returning `string[]` since `mergeMesh` merges N files in one op — see `pickMeshFile`/`mergeMeshPicked` in the message protocol table), and `runMenu(msg, getCtx, extContext)` routing a `MenuMessage`. All serialization funnels through `serializeModelToPath`; the webview only posts the command (`menuOpen`/`menuSave`/`menuSaveAs`/`menuExport`/`menuExportPart`/`menuExportSkin`/`menuExportTable`/`menuExportSeries`, plus `menuSaveProblem`/`menuLoadProblem` routed to `src/problemArchive.ts` — load, like open, needs no ExportContext). Each provider caches the last parsed model (`lastModel`) and registers a per-panel `activeMenuHandler` so palette commands reach the active preview; `ExportContext.ops` carries the applied edit ops for Save problem. (Mesh operations no longer live here — see `src/opHistory.ts` / `src/parser/operations.ts`.)
- `src/problemArchive.ts` — host side of File ▸ **Save problem… / Load problem…** (`menuSaveProblem`/`menuLoadProblem`, also the `kratos.problem.{save,load}` palette commands — load needs no active panel). Save collects via the shared `collectProblemFiles` and writes `<stem>.kratosproblem.zip`; Load picks a zip + destination folder, extracts (modal overwrite confirm; unsafe entry names skipped; the manifest itself is not extracted), registers the parsed ops recipe in the module's **pending-ops map** and opens the mesh with `vscode.openWith` in the matching preview. Both providers call `takePendingOps(fsPath)` right after `history.setBase` and replay via their local `replayWithProgress` (the same cancellable notification the `loadOps` path uses); the case state is restored by the panel's normal `<stem>.kratoscase.json` loading.
- `src/problemFiles.ts` — shared vscode-free disk collector `collectProblemFiles(meshFsPath, opsJson?)`: the mesh's pristine bytes + the caller-supplied recipe text (stored as `<stem>.ops.json`) + `<stem>.kratoscase.json` + the generated case files that exist (ProjectParameters.json, MainKratos.py, `<stem>_case.mdpa`, and the materials file(s) found by `materialsFileNamesFrom`). Used by `problemArchive.ts` (live-history ops) and the MCP `problem_pack` tool (recipe file ops).
- `src/parser/problemZip.ts` — pure problem-archive core: the `kratosproblem.json` `ProblemManifest` (mesh/ops/case/generated entry names), `buildProblemZip`, `parseProblemZip` (recipe-style tolerance — a missing/malformed manifest degrades to extension-based `detectMeshEntry` with warnings, ops fall back to the conventional `<stem>.ops.json`), `isSafeEntryName` (zip-slip guard, same policy as the .vtm child-path check) and `materialsFileNamesFrom` (deep search of ProjectParameters.json for `materials_filename` values — the name is problemtype-specific). Tests: `src/test/problemZip.test.ts`.
- `src/parser/zip.ts` — pure, dependency-free ZIP writer/reader on `node:zlib` (`createZip`/`readZip`): store + deflate, UTF-8 names, CRC-32 verified; encrypted/ZIP64/other-method archives rejected with descriptive errors. Interop-tested against a committed Python-`zipfile` fixture (`src/test/fixtures/zip/`). Tests: `src/test/zip.test.ts`.
- `src/parser/opHistoryCore.ts` + `src/opHistory.ts` — the **operation history** (undo/redo/partial-revert + JSON recipe I/O) shared by the Edit + Mesh Modification sidebar sections. The class is **pure** and lives in `parser/` so the whole stateful layer is Node-testable (`src/test/opHistoryCore.test.ts`); `src/opHistory.ts` is the vscode glue — the recipe save/load dialogs plus the shared `replayWithProgress(rerender, title?)` (a cancellable notification, previously duplicated byte-for-byte in both providers) — and re-exports the class so no import site changed. Same core/glue split as `whatsNewCore.ts`/`whatsNew.ts`. `OperationHistory` is a **replay-from-base** stack: `setBase(model)` for a genuinely NEW document (resets the stack), **`rebase(model)`** for a re-read of the SAME one (**keeps** ops+cursor, drops snapshots — they were computed against the old base), **`replayOntoBase(opts)`** (replays the applied prefix onto the new base and records a per-op `OpStatus`), `appliedCount()`, `hasSkipped()`, **async** `applyNew(rec)` (truncates the redo tail, records unless the op is a noop), **async** `applyMany(recs, opts?)` (**"combine several operations into one apply"** — a thin loop calling `applyNew` once per record, so each step still lands as its own independently-undoable entry rather than one opaque unit; a noop step doesn't stop the sequence, mirroring `replayOntoBase`'s "only an abort halts a replay" rule, and a genuine throw from one step propagates while every EARLIER step's commit stands, since each `applyNew` call is its own atomic push-or-not — a batch is a sequence of independently atomic steps, not one all-or-nothing transaction; takes an `onStepProgress?(index,total,rec)` hook for a "Step i/N: <label>…" line and returns `{outcomes, appliedCount, noopCount, stoppedEarly}`), `undo`/`redo`/`clear`/`revertTo(n)`, **async** `current()` = `replayOpsAsync(base, ops[0..cursor))`, `load(records)`, and `state()` for the webview. Prefixes ending in an MMG op are **snapshotted** (`Map<prefixLen, OpApplied>`) so undo/redo of later ops never re-runs the remesher; `current()` replays from the nearest snapshot ≤ cursor (snapshots past the cursor are invalidated on truncation; cleared on `setBase`/`load`/`clear`, so loading a recipe re-runs MMG). Op params are entered in the sidebar (interactive forms) and ride along on the `applyOp` message — the host builds the record with `opRecordFromMessage` (no native prompts). `saveOps`/`loadOps` are the showSaveDialog/showOpenDialog + `fs` recipe writers/readers. Each provider owns one instance; `lastModel` always equals `current().model`, so File ▸ Save/Export serialize the edited mesh. Pure replay/dispatch/JSON live in `src/parser/operations.ts`.
  **The `setBase`/`rebase` distinction is the fix for a data-loss defect**: `setBase` was called on *every* parse, so an external file change — or merely stepping a VTK timeline once — silently discarded the entire edit stack with no prompt and nothing to undo back to. Every re-parse path now rebases and replays instead. `OpStatus` is `"applied" | "noop" | "skipped"` and deliberately has no `"failed"` member: `applyOpAsync` never throws for a data problem — a real failure and a legitimate nothing-to-do both return `{noop:true, message}` — so `noop` carries the op's own message as the row's tooltip rather than claiming a distinction the layer below cannot make. `OpStateMsg.ops` entries carry `status?`/`note?` and the message gains `hasSkipped`, which is what reveals the sidebar's **Re-apply skipped operations** button.
- `src/opApply.ts` — `createOpRunner(deps)`, the vscode-facing "apply an operation" runner shared by both preview providers: `applyOperation(msg)` is the in-flight guard + inline-progress + rerender block that used to be duplicated byte-for-byte in `mdpaEditorProvider.ts`/`vtkEditorProvider.ts`, lifted verbatim (same `opInFlight`/`opAbort` guard, same `opProgress` messages, unchanged behaviour). `applyBatch(msg)` is new — runs `history.applyMany` for the operation queue (see `webview/opQueue.ts`), sharing the SAME guard state as `applyOperation` (only one of a single op or a batch can run per panel at a time) but genuinely different on failure: unlike `applyOperation`'s catch block, which never needs to re-render since a single op either fully committed or nothing did, `applyBatch`'s catch block **does** re-render, because a batch can commit several steps before a later one throws. Reports progress as `{op:"batch", message:"Step i/N: <label>…"}` via the same `opProgress` message shape every other async op already uses. ## Additional mesh operations (`src/parser/{smoothMesh,reorderMesh,renumberMesh,partitionMesh,linearize,refineMesh,simplexify,cropMesh,fieldCalc,extractSkin,mergeMesh,cellDecomposition}.ts`)

Surface meshio++'s bundled operations plus a few native ones, added to the Mesh Modification sidebar / `mesh_transform` / `mesh_extract_skin` on top of the original op set. The instruction that shaped this: **where an operation conflicts with something the extension already does natively, keep the native one** (ruled out `transform`, `clean`, `convertCells "elevate"`, `attachQuality`, `stats`, `isosurface`, `split by regions`, `dataInfo` — all superseded by existing features).

The finding that shapes the split into two groups: routing our model through `modelToMeshio`/`meshioToModel` is lossy — `propertyIds`, the Elements/Conditions/Geometries **kind** of a block, and every original entity id are gone on the way back. Two of the losses that originally motivated the split have since been closed and the rationale is **narrower than it was**: `modelToMeshio` now emits `regions`, so SubModelParts do cross (see below), and meshio++ 9.9.0's `*_components` maps fixed the boundary bug whereby **a vector field was silently corrupted by any operation that changes the point count** (a `(n,3)` array re-entered C++ as `(3n,1)`, failed the operation's `rows == num_points` test and took a pass-through branch, returning stale values of the wrong length). What remains — kinds, property ids, entity ids — is enough on its own, so the split stands. Hence:

- **Group A — meshio++ as an oracle** (`smoothMesh.ts`, `reorderMesh.ts`, `partitionMesh.ts`, `gradientField.ts`, `hessianField.ts`, `errorEstimate.ts`, `sdfField.ts`, `transferField.ts`): the wasm computes something whose shape survives losslessly — moved coordinates (same count/order), a node permutation, a per-cell label array, a per-node derivative, or a plain array of numbers keyed to our own points — and we apply that result onto our OWN `MdpaModel`; meshio++'s returned mesh is never adopted. All eight are async (`ASYNC_OPS`), inheriting the MMG-style progress/cancel UI automatically. The last two additionally read a SECOND mesh off disk, so they follow `mergeMesh.ts`'s split: the pure module takes an already-parsed model and `operations.ts` owns path -> model via `parseMergeSource`, with an unreadable file a noop rather than a throw.
  - `src/parser/smoothMesh.ts` — `smoothModel(model, params, diagnostics)`: Taubin (default, shrink-free) or Laplacian smoothing via meshio++'s `smooth`. Sends geometry only (no fields/regions — nothing else is read), copies the moved coordinates back onto a clone, and **throws if the returned point count doesn't match** (a safety invariant — smoothing must never add/remove points). Reports `numNodesMoved`/`maxDisplacement`/`numSkippedInversion`. Unit tests: `src/test/oracleOps.test.ts`.
  - `src/parser/reorderMesh.ts` — `reorderModel(model, method, diagnostics)`: `rcm` (bandwidth), `morton`/`hilbert` (spatial locality) via meshio++'s `reorder`. Never touches the returned mesh — applies the returned `nodePermutation` (old→new index map) natively, and reports `bandwidthBefore`/`bandwidthAfter` via `computeBandwidth`. **It permutes STORAGE ORDER only** (`nodeIds` and `coords`, `reorderMesh.ts:85-97`): every node keeps its own id and its own coordinates, which is precisely *why* connectivity, SubModelPart id lists and field records — all keyed by id, never by index — stay valid untouched, and the module's own header says renumbering the ids "is deliberately not done here". Renumbering the ids is the separate, native, **synchronous** `renumber` op (`renumberMesh.ts`), and `reorder` then `renumber` is the full RCM renumbering. Unit tests: `src/test/oracleOps.test.ts`.
  - `src/parser/partitionMesh.ts` — `partitionModel(model, params, diagnostics)`: domain decomposition via meshio++'s `partitionLabels`, attached as an Elemental `PARTITION_INDEX` field (a real Kratos variable) covering every cell kind (Elements/Conditions/Geometries — `KIND_ORDER`), optionally also creating one `Partition_N` SubModelPart per part (`createParts`). **The WASM build has no KaHIP**: `"kahip"` throws by name, `"auto"` resolves to `"sfc"` — only the Hilbert space-filling-curve method is available, so parts are balanced by cell count, not edge cut. Unit tests: `src/test/oracleOps.test.ts`.
  - `src/parser/gradientField.ts` — `gradientFieldModel(model, params, diagnostics)`: the gradient / divergence / curl of a NODAL field via meshio++'s `gradient` (>= 9.10.0), attached as a new Nodal `FieldData`. Asked for **`location: "point"`**, which is the whole reason it qualifies as an oracle — the result is one tuple per EXISTING node in the input's own order, the same invariant `smoothMesh.ts` relies on for coordinates — and the result is **rejected outright if the tuple count does not match**. Widths ride the returned `point_data_components` rather than being assumed: a scalar's gradient has 3 components, a 3-vector's 9 (row-major `[component][derivative]`), divergence 1 and curl 3 (both requiring a 2- or 3-component field). An **Elemental** source is refused by name and pointed at `averageField` — a piecewise-constant field has no derivative, and the extension already owns the conversion. `numSkipped` (cells that came back NaN rather than approximated) and `numFallback` (least-squares neighbourhoods that fell back to Green-Gauss) are surfaced in the outcome message rather than hidden, since a partly-NaN field looks clean in the field picker and is not. Re-running replaces its own output instead of stacking a duplicate, the rule `partitionMesh.ts` follows. Unit tests: `src/test/oracleOps.test.ts`.
  - `src/parser/hessianField.ts` — `hessianFieldModel(model, params, diagnostics)`: the **Hessian** (second derivative) of a SCALAR nodal field via meshio++'s `hessian` (>= 10.9.0), attached as a 9-component Nodal `FieldData` (the flattened row-major 3x3, `H[i][j]` at `i*3+j`). Near line-for-line `gradientField.ts`, including the `location: "point"` request and the **reject-on-count-mismatch** guard, because it is the same shape one order further. Two constraints are enforced HERE rather than discovered at the binding: a **vector** source is refused pointing at "split it and run once per component" (upstream raises on array width, which does not say what to do), and an **Elemental** source is refused pointing at `averageField`. The caveat that rides the outcome message: `hessian` is a composition of two `gradient` calls, so it is exact for a field that is at most linear — whose Hessian is exactly zero everywhere, the one mesh-shape-independent guarantee, and what `oracleOps.test.ts` asserts — but a genuinely approximate curvature estimate on an irregular mesh. Unit tests: `src/test/oracleOps.test.ts`.
  - `src/parser/errorEstimate.ts` — `estimateErrorModel(model, params, diagnostics)`: the **Zienkiewicz-Zhu** recovery-based error indicator of a nodal field via meshio++'s `estimateError` (>= 10.10.0), attached as a per-cell Elemental `FieldData` (default `ERROR_INDICATOR`). Modelled on `partitionMesh.ts`, not `gradientField.ts`, because the result is one value per CELL in block-major order — so it reuses that module's `KIND_ORDER`/`orderedBlocks` walk and its `flat.length !== total` guard to lay the values back onto our own blocks. `marking` (`absolute`/`fraction`/`dorfler`) attaches a second `ERROR_MARKED` 0/1 Elemental field rather than folding the flag into the indicator, which makes it immediately usable by the Field panel's `threshold` mode and exportable like any other Elemental data. Upstream's own default names (`error:zz`) are **not** used: `mdpaWriter.ts` emits variable names verbatim and a colon is not a legal Kratos variable. A cell that cannot be evaluated reads NaN in the indicator and **0, never NaN**, in the marking array; `globalError`/`numSkipped`/`numMarked` ride the outcome message. Unit tests: `src/test/oracleOps.test.ts`.
  - `src/parser/sdfField.ts` — `sdfFieldModel(model, surface, params, diagnostics)`: the **signed distance** from every node to an external surface mesh via meshio++'s `sampleDistance` (>= 10.4.0), as a Nodal `FieldData` (default `SDF_DISTANCE`, negative inside). The **purest oracle shape in the codebase**: `sampleDistance` takes a flat coordinate array and returns one double per point, so our own mesh never crosses the wasm boundary at all — only the surface is converted, and there is no `modelToMeshio` round trip to lose anything to. `distanceToSurface` would do the same job by attaching the field to a converted copy of our mesh and is deliberately unused, because that copy IS the lossy round trip. It earns its place by pairing with the existing **`levelset`** op, which splits a mesh along the isosurface of a nodal field but had no way to get one from an imported geometry: `sdfDistance` then `levelset` is "cut this mesh along that surface" with no new machinery. Unit tests: `src/test/oracleOps.test.ts`.
  - `src/parser/transferField.ts` — `transferFieldModel(model, source, params, diagnostics)`: **mass-preserving cross-mesh field transfer** via meshio++'s `conservativeInterpolate` (>= 10.7.0) — over the region the two meshes share `sum(value * measure)` is equal on both sides, which `interpolate`'s barycentric mode does not guarantee. Two things are load-bearing and were **measured, not assumed**: (a) upstream simplexifies BOTH meshes internally, so the returned mesh's CELL set need not be ours (point count is invariant under simplexification, cell count is not) — hence an array is adopted only when its tuple count still matches our node or cell count, and every other is **dropped and named in a diagnostic**, `gradientField.ts`'s count guard applied per array rather than per call; and (b) `point_data` is transferred by a point->cell->clip->point composition, so a varying nodal field comes back **SMOOTHED, not resampled**, even between two identical meshes — a constant survives exactly, and the total is what is preserved. `onConflict` is upstream's own `error`/`overwrite`/`suffix` (a guessed fourth spelling fails loudly, which is how the real vocabulary was found), defaulted to `overwrite` so re-running updates rather than fails. Unit tests: `src/test/oracleOps.test.ts`.
- **Group B — native**, reusing primitives the extension already owns (edge/face tables, block/field slicing, `sizeExpr.ts`'s evaluator) rather than repairing a lossy round-trip:
  - `src/parser/cellDecomposition.ts` — the volume/surface→tetrahedra/triangle decomposition tables (`TET_TETS`/`PYRAMID_TETS`/`WEDGE_TETS`/`HEX_TETS`/`TRI_TRIS`/`QUAD_TRIS`, `decompositionFor(cellType)`), extracted out of `isoSurface.ts` (which used them for marching tetrahedra) so `simplexify.ts` can reuse the identical tables.
  - `src/parser/polyhedronDecompose.ts` — `decomposePolyhedronBlock(block, points, dim, firstNewIndex)`: a general polyhedron has no VTK cell type and no Kratos element, so a polyhedral block (CGNS `NGON_n`/`NFACE_n`, MED `POE`, VTU `VTK_POLYHEDRON`, OpenFOAM) is split into tetrahedra on READ instead of opening empty. Each face is fanned about its own **corner average** and each resulting triangle joined to the cell's corner average — a triangular face gives 1 tet, an n-gon gives n. Fanning about the corner average rather than the face's first listed node is what makes the volume exact for a cell with NON-PLANAR faces (a first-node fan depends on which corner the file listed first, so two cells sharing a warped quad can disagree and leave a sliver) and is also meshio++'s own 9.16.0 convention, so a decomposed cell measures the same here as upstream's `stats`. Face apexes are deduplicated across the block by sorted node-id key (the shared-entity trick `linearToQuadratic.ts` uses for mid-edge nodes) so two cells sharing a face do not tear apart; a cell apex is interior and never shared. Every tet is oriented to positive volume, since source winding is whatever the writer chose. **Zero imports**, so both `meshioConvert.ts` and `vtkXmlParser.ts` can call in without a cycle. Unit tests: `src/test/polyhedronDecompose.test.ts`.
  - `src/parser/linearize.ts` — `linearize(model)`, the missing inverse of `linearToQuadratic.ts`: drops mid-side nodes via a `QUADRATIC_TO_LINEAR` lookup, renames blocks/types/strides, then `removeOrphanNodes`. Unit tests: `src/test/linearize.test.ts`.
  - `src/parser/refineMesh.ts` — `refineModel(model, levels=1)` (capped at `MAX_LEVELS=4`): uniform subdivision (line→2, tri/quad→4, tet/hex/wedge→8) via per-cell-type local-index child templates (`childTemplates(cellType)`), sharing `linearToQuadratic.ts`'s shared-edge/face dedup approach (`nodeFor(parentNodeIds)` keyed by sorted-parent-id string) so a shared edge/face midpoint is one node, never a hanging node. Interpolates Nodal fields exactly at new nodes (mean of generating parents), replicates Elemental/Conditional fields to children, extends SubModelPart node membership. Unit tests: `src/test/refineMesh.test.ts` (incl. rigorous tetrahedral-decomposition volume-conservation checks for hex/wedge/tet).
  **Both `refineMesh.ts` and `simplexify.ts` key their parent→children map PER KIND** (`Record<EntityKind, Map<number, number[]>>`), and that is a correctness requirement rather than tidiness: Elements, Conditions and Geometries each have their own id space, so `Element 1` and `Condition 1` coexist in every ordinary Kratos mesh and one map keyed by bare id let the last block visited overwrite the others — handing an Elemental field and a SubModelPart's `elementIds` the CONDITION's children while the real element children silently lost their values. Both also replicate **all four** entity id lists including `geometryIds`, which rode the `{...part}` spread unchanged while the Geometries blocks were being split; `constraintIds` correctly stays on the spread, since neither op removes a node. The child-id counter stays GLOBAL across the three spaces — gappy per kind, never colliding, and making it per-kind would churn every condition and geometry child id for no correctness gain. Tests: the id-space cases in `refineMesh.test.ts`/`simplexify.test.ts`, whose fixtures carry an element, a condition and a geometry all numbered 1 (a single-block fixture cannot see the bug).
- `src/parser/simplexify.ts` — `simplexifyModel(model)`: hex→6 tets, wedge→3, pyramid→2, quad→2 tris (via `cellDecomposition.ts`); the first child keeps the parent's id, siblings get fresh ids past `maxEntityId(model)`, replicating Elemental/Conditional fields and SubModelPart membership. A mesh with nothing to split (already all-simplex) is a noop with `skippedBlocks` naming why. Unit tests: `src/test/simplexify.test.ts`.
  - `src/parser/cropMesh.ts` — `cropModel(model, params)`: keeps cells whose nodes are inside a bbox or on the normal side of a plane (`mode: "all"|"any"`), reusing `sliceBlock`/`sliceField` (exported from `subModelPartExtract.ts`) to rebuild blocks/fields around the survivors, narrows SubModelPart node lists by the inside-test (not cell survival) and entity lists by the keep sets, then `removeOrphanNodes`. Throws if nothing survives or a plane's normal is the zero vector. Unit tests: `src/test/cropMesh.test.ts`.
  - `src/parser/fieldCalc.ts` — `fieldCalcModel(model, params)`: a new field from a formula evaluated by `sizeExpr.ts`'s own recursive-descent parser (never `eval` — expressions arrive from saved recipes, i.e. untrusted disk input), with the scope extended from the MMG sizing names to `x,y,z` plus every existing field at the target location (a vector field split into `name_x`/`name_y`/`name_z`; **all lowercased**, working around `sizeExpr.ts`'s own lowercasing of bare identifiers, so an UPPERCASE Kratos variable like `TEMP` is still reachable). A bad formula is rejected before anything is applied; NaN (an unavailable field) drops the row, Infinity (e.g. `1/0`) is kept. `averageField(model, params)` moves a field between Nodal and Elemental/Conditional by averaging: `nodalToElemental` = mean over a cell's own nodes, `elementalToNodal` = mean over incident cells (uniform, not measure-weighted). Unit tests: `src/test/fieldCalc.test.ts`.
  - `src/parser/extractSkin.ts` — `extractSkinModel(model)`: the boundary skin of the volume cells (+ any pre-existing surface cells) as a standalone `MdpaModel`, via the same boundary-face walk as `meshNormals.ts`/`writerCommon.ts`'s `surfaceTriangles` (a face seen by exactly one cell is boundary). Ships as an **export** (like `extractSubModelPart`), never an in-place edit — a skin is a different mesh with fresh entity ids. SubModelParts narrow to node membership only (element/condition/**constraint** ids cannot follow — the new blocks have no correspondence, and a surviving `constraintIds` list would name constraints the skin defines nowhere, which it did until this was fixed); only Nodal fields carry over. Native rather than meshio++'s `extractSurface`/`extractSkin` because those drop every region on the way out. Reachable from the Advanced toolbar menu (**Export skin…**) and the `mesh_extract_skin` MCP tool. Unit tests: `src/test/extractSkin.test.ts`.
  - `src/parser/renumberMesh.ts` — `renumberModel(model, params)` behind the sync `renumber` op: compacts ids into a gapless run from `start` (default 1) for `target` `"all"`/`"nodes"`/`"entities"`, in the order the mesh already stores them (`nodeIds` order for nodes; block array order then within-block order for entities — both match `mdpaWriter`'s emission order, and block order is deliberately *not* `KIND_ORDER`, since renumbering must not imply a block reordering). **Elements, Conditions and Geometries are numbered independently**: Kratos gives each kind its own id space, so an `Element 1` beside a `Condition 1` is the faithful shape, and nothing downstream assumes global uniqueness (`buildCellLayout` keeps three separate id→cell maps, `FieldData.kind` selects the space, `mesh_find_entity` takes an `entityType`). Rewrites `nodeIds`, block `connectivity` + per-kind `entityIds`, every SubModelPart id list (recursively, sorted ascending like `subModelPartTree.ts`'s `unionIds` — the map is not monotonic when storage order was scrambled) and every `FieldData.ids` (relabelled **in place**, rows never move, so `values`/`fixed` stay aligned). **Constraints are a FOURTH id space** and are renumbered too (see `constraintsParser.ts`), folded into the existing `"entities"` target rather than given a `RenumberTarget` member of their own — `SubModelPartConstraints` sits beside the other four lists so they are entities in Kratos' sense, nobody wants "compact everything except the constraints", and a new enum member is a forward-only recipe-compat cost for nothing; `EntityKind` is deliberately **not** widened, since it is a rendering type consumed by `buildCellLayout`/`FieldData.kind`/`mesh_find_entity`. Node columns are relabelled BEFORE the constraint id space is built, because a constraint that loses a node is **dropped, not zero-filled**: connectivity can zero-fill (it is stride-fixed and `buildCellLayout` skips the cell) whereas a constraint with a `0` master is garbage to Kratos and its weight vector would silently misalign with the masters that remain. Two guards keep the old behaviour where it was right, and both are reported: a file that LISTS constraint ids while defining none is left alone (`constraintIdsLeftUndefined` — what is left of the retired non-goal, still literally true for that file and no longer the general case), and a **raw** row (one `constraintsParser` could not decompose, so it has no readable id) suppresses id renumbering entirely, since relabelling around it would break the SubModelPart correspondence for the one row nothing can check. A dangling reference is **zeroed in connectivity** (stride-fixed, so it cannot be dropped; `0` is unreachable because `start >= 1`, and `buildCellLayout` already skips an unresolvable cell) and **dropped from part/field lists**; identity maps hand the original model reference back so the op reports a noop. Deliberately **filesystem-free** — it takes `MergeSource {model, name}`, so path→stem naming stays in `operations.ts` (`smpNameFromPath`). **Welding runs once at the end, not once per source**: `mergeNodes` rebuilds its whole grid hash per call, and welding is transitive over the final coordinate grid, so one pass gives the same result set and one honest count. **Offsets are per id space** — nodes, Elements, Conditions, Geometries and constraints each continue their own run — which is what stops every merge re-opening the gap `renumber` exists to close. The constraint offset spans **defined ids ∪ SubModelPart lists**, not the lists alone: a base may define constraints that no part lists (`test_model_part_io_read.mdpa` does exactly that), and a list-only maximum would hand the incoming file a colliding id. An incoming `ConstraintBlock` carries BOTH shifts (its own id past the accumulator's run, its master/slave columns past the node run) and the wrapper part claims the shifted ids; a **raw** row cannot be shifted at all, so it is kept and named in a diagnostic rather than silently written against the base's nodes. Wrapper naming: `name` names the wrapper for a single source (today's contract) but the shared **parent** for several, whose children are the per-source wrappers and whose id lists are their union (the Kratos parent/child subset rule `subModelPartTree.ts` maintains by construction); names are de-duplicated with a `_2`… suffix against existing top-level paths. Fidelity losses are **reported as diagnostics rather than hidden**: a `(kind, variable)` collision with a mismatched `components` **skips** the incoming field (keeping both would put two entries under one `"<kind>:<variable>"` key, and `mdpaWriter` would emit two blocks of which the second silently wins on re-read — a duplicate is corrupted data, not retained data); both sides' own diagnostics are carried, the incoming ones prefixed `[stem] ` as `parseVtm` does; and a source's `Properties`/`ModelPartData` blocks plus the `propertyIds` they leave dangling are named (unfixable here — `MetaBlock` is a label and a line count, and `mdpaWriter` copies Properties verbatim out of the **base's** `sourceText`, so an incoming file's can never reach the output). Typed arrays concatenate through `.set()` helpers rather than spreads, which box every element. Before this, `PtController.run()` created a terminal, dropped the handle on the floor and posted `ptStatus{running}` that was never updated again; identity was a name string looked up globally over `vscode.window.terminals`, so two panels on same-named meshes in different folders fought over one terminal, and the command was string-interpolated into a shell (a `pythonPath` with a space broke it).
  - **Why `spawn` and not a terminal.** A run manager's product is *status*, and this codebase does not show a value it cannot stand behind. `onDidCloseTerminal` conflates terminal lifetime with process lifetime, so the ordinary case — solver finishes, user leaves the terminal open to read the log — yields **no event at all**. Shell integration (available since `engines.vscode` is `^1.134.0`, not the `^1.84.0` the roadmap used to claim) is better but explicitly best-effort: `TerminalShellExecutionEndEvent.exitCode` is `number | undefined` and `Terminal.shellIntegration` may never activate — least reliably in the Remote-SSH/WSL/conda setups Kratos actually runs in. `spawn` gives a guaranteed exit code, a real pid, a real output stream, working cancellation, and — because argv is an array with `shell: false` — fixes the quoting bug for free. `kratos.run.launchMode: "terminal"` keeps the interactive terminal for anyone who needs a prompt; such a run is still registered but marked **`detached`**, never claiming an exit code it does not have.
  - **The detached primitives** (`runProcess.ts`): `spawnRun` takes an optional **`logFile`** (a path, not an fd — whoever opens an fd must close it, and the right moment is "once spawn has dup'd it", a boundary the caller cannot see and one the synchronous-throw path returns straight past, leaking it; owning the open here also routes an unopenable log through the existing `spawn-error` channel) and an optional **`unref`**. `unref` is deliberately NOT implied by `detached` — the extension sets `detached` too, meaning only "do not kill this on window close" — and is only effective *with* `logFile`, because the stdio pipes are themselves ref'd handles. That is why the fd and the unref are one coherent change rather than two independent options. **`stopPid(pid, deps)`** is the cross-process ladder: `RunHandle.stop` can fire and forget because it has an exit event to settle it, while a pid read off disk has none, so this polls between rungs — which also lets it return early and report which signal worked. `RunManager`'s adopted-run branch uses it too, replacing an immediate SIGKILL that threw away the SIGINT rung. **On Windows there is no graceful rung at all** — signals are not real there, so `stop`/`stopPid` go straight to TerminateProcess. A Ctrl+Break rung (`GenerateConsoleCtrlEvent` P/Invoked through inbox `powershell.exe`) was tried and reverted: the first real run on `windows-latest` CI showed it does not fail soft the way a missing console/process group was expected to — `GenerateConsoleCtrlEvent`'s process-group scoping did not hold up under the nested pwsh→cmd.exe(npm.cmd)→node console chain a `run:` step actually spawns, so the break escaped its intended target and froze the whole job on a `Terminate batch job (Y/N)?` prompt instead of falling through to the kill. Two further facts, established when a second attempt was scoped, are what turned this from "open" into a recorded constraint: Node's `spawn` cannot request `CREATE_NEW_CONSOLE` at all (it and `DETACHED_PROCESS` are mutually exclusive, and a `cmd /c start` wrapper returns cmd's pid, breaking the sidecar's process identity), and `CTRL_BREAK_EVENT` reaches CPython as `SIGBREAK`, which does not raise `KeyboardInterrupt`. See the Non-goals entry in `doc/roadmap.md`. **`RunSidecar.stopRequested`** persists the latch, because `RunRecord.stopRequested` cannot cross a process boundary and the process holding the handle is the one that writes the terminal record — without it an MCP-issued stop of an extension-owned run always wore a failure badge. `RUN_VERSION` stays **1**: `parseRunJson` only warns on a *newer* version, so bumping would make every shipped reader warn for nothing.
  - **The delta hazard.** `computeKratosEnv` returns a **delta**, not an environment — right for `createTerminal({env})`, which merges, and catastrophic for `spawn({env})`, which replaces (no PATH, no HOME, python never starts). `runProcess.ts` spreads `{...process.env, ...delta}`; the doc comment and a `kratosEnv.test.ts` assertion both pin it.
  - **Ownership** mirrors `FlowgraphController`: constructed in `extension.ts`, pushed onto `context.subscriptions`, injected into the provider and on into `PtController` — because a run outlives the panel that started it while a `PtController` is disposed with its panel. `PtController` gains its first real disposable, a `runs.onDidChange` subscription driving the status line.
  - **Statuses are separate words on purpose.** `detached` means a process we are not attached to may still be alive (a terminal launch, or one adopted after a reload); `orphaned` means it was live when the window went away and no exit code was ever recorded. `reconcileStatus` **never** promotes a stale record back to `running`: pids are reused, so a live `process.kill(pid, 0)` probe downgrades to `detached` — a hedge, not a yes. On dispose, live runs are killed (a non-detached child is otherwise re-parented to init and keeps running with a broken stdout pipe) after being written out as `orphaned`; `kratos.run.stopOnWindowClose: false` opts out and detaches instead — via the pure **`windowCloseAction`** in `runCore.ts`, because spelling that decision inline in `stopAll` is exactly how it broke: the setting was read in ONE place (to set `detached` on the spawn) while `stopAll` killed every run regardless, so turning it off did nothing but relabel the corpse `orphaned` ("we do not know what happened") for a process the extension had just SIGKILLed. The opt-out branch calls the new **`RunHandle.release()`** (unref the stdio pipes AND the child — a ref'd pipe holds the host open just as a ref'd child does) and deliberately **writes no sidecar**: leaving the record `running` with its pid is what lets `reconcileStatus` report the truth from the OS next window, whereas writing `detached` would stick forever (it short-circuits there) and make `foreignLiveRun` prompt on every later run of that case. A detached run also **tees to `<stem>.kratosrun.log` instead of the Output channel**, the shape MCP already uses: those are pipes owned by this host, so the first `print` after the window closes would kill the solver with EPIPE.
  - **Cancellation** latches `stopRequested` *before* signalling, then `SIGINT` → 5 s → `SIGTERM` → 2 s → `SIGKILL` (python turns SIGINT into `KeyboardInterrupt`, so finalizers run and the last result file closes). The latch is what makes a deliberate stop read `cancelled` rather than `failed` — a failure badge on a run the user stopped is a lie the tree would keep telling. On Windows there is no graceful rung — an immediate terminate, reported as such rather than implying a clean shutdown. Partial output is never deleted, and because the vtk writer has no atomic rename the final step of a killed run may be truncated — so "open results" for a non-`finished` run targets the last *complete* step (`latestResultFile(names, {excludeNewest:true})`).
  - **Progress comes from `vtk_output/`, never from stdout** — see the Non-goal in `doc/roadmap.md`. A `createFileSystemWatcher` + 500 ms debounce (the VTK preview's own idiom) yields `{fileCount, stepLabel}` identically for a spawned run, a terminal run and an adopted orphan; stdout goes verbatim to the Output channel, and its only use is a tooltip line labelled "last output". One channel **per case**, reused across runs — VS Code lists every channel in the Output dropdown forever.
  - **`latestResultFile`** replaces `openResults()`'s `names.sort()[0]`, which was wrong three ways: the sort was LEXICOGRAPHIC (`_0_10` before `_0_2`), it then took the *first* entry, and its regex was narrower than `TIMELINE_EXTENSIONS` (missing `.vti`/`.vts`/`.vtr`). It reuses `groupVtkFiles`/`fileFor`, which already sort steps numerically. An already-open preview is **revealed and jumped** rather than duplicated, via `VtkEditorProvider.revealLatestFrame` behind an internal `kratos.vtk.openLatestResults` command that is registered but deliberately **absent from `contributes.commands`** (it takes arguments, and `extension.ts` is the only place holding both providers).
  - **The view is a dumb projection**: every label, description, icon id and context value comes from a pure `runCore.ts` function. That is the mitigation for a real gap — this repo has **no VS Code integration harness** (no `@vscode/test-electron`) and the screenshot harness drives the *webview*, so it cannot see a tree view, a menu or an Output channel at all. Keeping the decisions below the vscode line is what makes them testable. It contributes into the **Explorer** container: an activity-bar container needs an SVG icon, and `.vscodeignore` excludes `icons/**` and all of `images/**` bar two PNGs.
  - **MCP parity is filesystem-mediated** through `<stem>.kratosrun.json`, because the MCP server cannot own a run (stdout is its JSON-RPC transport and it exits with its client). `case_status` reads that sidecar with the same `runFile.ts` the extension writes it with, reconciles against the OS, and summarises `vtk_output/` with the same `latestResultFile` — so both sides answer "how far along is it" identically. **`case_run`/`case_stop` now ship too, and the distinction that makes them possible is *start* vs *own*.** The server still never owns a run: `case_run` always spawns **detached**, with both streams appended to `<stem>.kratosrun.log` and `unref()`ed, so the solver outlives the server by construction (proved end-to-end by SIGKILLing the server and watching the child keep writing). Three things follow. **`waitSeconds` is one knob, not `wait` + `timeout`** — two knobs for one dimension interact undefinably — and it **defaults to 10 s**, not to something tuned just under the typical 60 s client timeout: there is no server-side timeout anywhere, the client's is a number this process cannot observe, and a 55 s budget would still blow a client configured at 30 s *while believing itself safe*. **Expiry is not a failure**: it returns an ordinary `running` blob with the pid and log path, and the ABSENCE of `exitCode` is what says the run has not ended. And **the live-run refusal must run BEFORE the generate step**, since generating rewrites ProjectParameters.json underneath anything already reading it. Once the server exits nothing can record how a detached run ended — which is correct rather than a hole, because `reconcileStatus` already reports `orphaned` instead of inventing an exit code. Note the deliberate asymmetry this creates: the same live run reads `running` from `case_run` (which holds the handle) and `detached` from `case_status` (which has only a reusable pid); both tool descriptions say so, because it looks like a bug and is not. `case_stop` is the only thing here that signals a process it did not create, so it is guarded rather than trusting the pid — a run with an `endedAt` is never signalled, the `runId` must still match, and it re-reads after the ladder so a run that finished mid-stop is not resurrected as `running`. - `src/parser/mdpaParser.ts` — tolerant line-oriented state-machine. Uses a `stack: Frame[]` to handle nested `Begin`/`End` blocks. Merges repeated `Begin Elements <Name>` blocks into one `EntityBlock` so split files form a single layer. Parses `Begin NodalData`/`ElementalData`/`ConditionalData <VAR>` blocks into `FieldData` (scalar `id [is_fixed] value`, vector `id [N] (v1,…)`; flag-only nodal lines become value 1) while still recording the meta line-count. Also parses `Begin Properties <id>` VALUES (see `propertiesParser.ts`) by mirroring its own `FIELD_KINDS` branch — *keep the meta block AND additionally accumulate the values* — and carries a **trap door**: any block opened inside a Properties block is swallowed rather than dispatched, which is what stops a nested `Begin Table` becoming a stray top-level `MetaBlock` and (much worse) a nested `Begin SubModelPart` being parsed as a genuine SubModelPart, since `handleBegin` dispatches on the block type alone. A nested Table is attached to its owning `PropertySet`. `Begin Constraints` takes the identical shape — a branch placed BEFORE the `META_TYPES` one, which it shadows exactly as `FIELD_KINDS` already shadows it for `NodalData`, keeping the meta block and additionally parsing each row through `constraintsParser.ts`. `MetaBlock.lineCount` keeps its historical meaning exactly (a nested block's lines were never counted against the enclosing Properties and still are not) — the writer's verbatim path and `mergeMesh`'s reporting both depend on that number.
- `src/parser/propertiesParser.ts` — pure (no `vscode`/DOM/fs) parser for the VALUES inside `Begin Properties <id>`, and the `PropertySet`/`PropertyValue` model they land in (`MdpaModel.properties?`). Until it existed `MetaBlock` was `{label, lineCount}` — the parser counted a block's lines and discarded the text — which was enough for a lossless Save (the writer copies Properties verbatim from `sourceText`) but left the data unreachable. Two consumers wanted it: **beam rendering** (`CROSS_AREA` per cell, joined through the `propertyIds` an `EntityBlock` already carries per row) and **merge mesh**, which had been reporting the loss since 3.4.0. Handles every form that occurs in real Kratos files — scalars, Python-cased barewords (`False`), `[3] (…)` vectors (with or without the space), `[3,3] ((…),(…))` matrices, and a nested `Begin Table`. **Tolerance is asymmetric on purpose**: an unrecognised value is kept as a `string` *silently*, because `CONSTITUTIVE_LAW LinearElastic3DLaw` appears in essentially every real structural mdpa and a diagnostic per line would bury such a file in warnings; only a value that announces a structure and then fails to honour it is reported, and even then whatever parsed is kept. A missing/unreadable id is **refused, not defaulted to 0** (every example mesh opens with a real `Begin Properties 0`, which a malformed header would otherwise shadow); a duplicate id keeps the **first** block (last-wins would let a trailing empty block blank a real one). `propertyValue`/`propertyNumber` do own-property lookups because names come off disk, and `emptyPropertySet` uses `Object.create(null)` for the same reason. **The container is plain JSON, never a `Map`**: it rides to the webview on `MdpaModel`, and `scripts/screenshots/build-harness.mjs` re-serializes every message through `JSON.stringify`, where a `Map` becomes `{}` — i.e. it would work in production and fail only where the rendering is verified. The slot is optional, which carries a silent-loss trap: the ~20 `src/parser/` modules returning `{...model, …}` carry it free, but the 8 that build a full literal drop it with **no type error** — `mergeNodes`/`removeOrphanNodes`/`renumberMesh`/`linearToQuadratic`/`mergeMesh`/`subModelPartExtract` now carry it explicitly, while `extractSkin`/`modelBuilder` correctly do not (their blocks have no `propertyIds` to point with). The rule is "wherever `meta` goes, `properties` goes" — and since `constraints?` landed, "and `constraints` goes", though with a sharper qualification (see `constraintsParser.ts`: that slot must be *maintained or dropped*, never merely carried, past a node change). The **writer is deliberately untouched** — `mdpaWriter.ts` still copies Properties verbatim, which is what keeps the round-trip lossless and is now the only thing blocking merge from carrying them. Reported by MCP `mesh_info` as a conditional `properties` section (values unwrapped to plain JSON). Unit tests: `src/test/propertiesParser.test.ts`.
- `src/parser/constraintsParser.ts` — pure (no `vscode`/DOM/fs) parser for the ROWS inside `Begin Constraints <name> <variables…>`, the `ConstraintBlock`/`ConstraintRow` model they land in (`MdpaModel.constraints?`), **and** every operation that keeps them valid while a mesh is edited. The direct sibling of `propertiesParser.ts`, one step further: a Constraints block was kept only as a `MetaBlock` label + line count and 3.11.1 carried it through a Save as verbatim source text — which stopped it vanishing and was explicitly a stopgap, since verbatim text is keyed by NODE id and any op that renumbers or removes nodes leaves it naming ids the written mesh no longer has. Layout `id constant [weights] slave… master…`; the trailing integer run is split **from the END** (the last `weights.length` ids are the masters), which is deliberately robust to either reading of Kratos' column order and irrelevant to maintenance anyway, because `constraintNodeIds` returns all of them and *every one is a node id*. The parse works on the STRING, never on `/\s+/` tokens, since that split shatters `[0.25, 0.25]` — the same re-join `parseFieldRecord` does for `(v1, v2)` — and the bracket span is found by **depth**, so a nested `[[…],[…]]` relation matrix is refused rather than mis-split. **Tolerance differs in kind from the Properties parser's**: an unrecognised row is kept **verbatim** (`kind: "raw"`) rather than coerced, per ROW not per block (one bad row among cube.mdpa's forty must not strand the other thirty-nine, and "every row raw" then *is* the whole-block-verbatim case with no second code path). A raw row round-trips byte-for-byte but **cannot be maintained**, so every consumer counts them apart and says so instead of renumbering around an id it could not find. `constraintNum`/`formatConstraintRow` live here rather than using `writerCommon`'s `num()`, which renders an integer as `"0"` where every Kratos file carries `0.0 [1.0]`. Plain JSON, never a `Map`, for `propertiesParser.ts`'s reason; rows stay flat because an MPC-heavy mesh carries a hundred thousand of them and the whole model is re-posted on every render. The shared maintenance helpers — `mapConstraintNodes` (drop, never zero-fill, a constraint whose node has no mapping), `filterConstraintsByNode`/`filterConstraintsById`, `remapConstraintIds`, `offsetConstraints`, `pruneSubModelPartConstraints`, `undefinedConstraintIds` — exist so the seven maintenance sites cannot drift. Those sites and their decisions: `mdpaParser` (source) · `removeOrphanNodes` counts a constrained node as USED and exports `meshUsedNodeIds` (the same question WITHOUT constraints) for the modules below — this was the highest-risk site, since it was deleting the referent · `mergeNodes` welds the columns and drops a constraint the weld made self-referential, pruning its id from every part (duplicated masters are left alone: summing their weights would be inventing numbers) · `renumberMesh` (see its bullet) · `mergeMesh` offsets both spaces · `cropMesh`/`linearize`/`deleteSubModelPart` decide which constraints die FIRST and only then clean up, since a constraint kept across a crop boundary would hold a node alive outside the very region the user removed · `subModelPartExtract` slices them, which fixed a shipped defect (`exportSubModelPart` hands the writer the WHOLE source file as `sourceText`, so a verbatim block landed in a file holding a fraction of its nodes) · `extractSkin` drops them AND zeroes `narrowParts`' `constraintIds`, which fixed the mirror defect. `remesh`/`levelset` drop them with a stated warning (MMG renumbers everything, so there is nothing to maintain against); `meshioConvert` drops them without one, since no other format has the concept and a warning would fire on every foreign import. Reported by MCP `mesh_info` as a conditional `constraints` section, whose `undefinedIds` is the one field that catches a file Kratos cannot read back. - `src/parser/meshQuality.ts` — pure (no `vscode`/DOM/vtk) geometric mesh-quality metrics inspired by Kratos' `ComputeMeshQualityProcess`: aspect/edge ratio, min/max angle (dihedral for volume cells, interior corner angles for surface cells), and per-node size gradation. Classifies every element into good/acceptable/bad/unacceptable bands (thresholds mirror the Kratos defaults) and returns per-metric histograms + the ids of bad elements. BC/flag-dependent checks (dead-tetra, gap/hole detection) are intentionally omitted — undefinable for a purely geometric mesh. - `src/parser/watertight.ts` — pure (no `vscode`/DOM) `watertightReport(model)` / `watertightSummary(r)` over meshio++'s `surfaceWatertightCheck` (>= 10.4.0): boundary edges (holes), non-manifold edges (three-or-more-face junctions), inconsistently wound face pairs and zero-area faces. It lives NEXT TO `meshNormals.ts` rather than inside it because that module already answers half the question natively and better — two faces sharing an edge are consistently wound exactly when they traverse it in opposite directions, a **relative** test needing no wasm, and the one that draws the red inverted-element overlay. What it cannot say is whether the surface is CLOSED, which is a different defect with a different fix. Splitting them is also what lets `meshNormals.ts` stay pure, synchronous and wasm-free — it is bundled into the **webview**, which has no access to the wasm at all. The counts are surfaced individually rather than collapsed into a boolean for the same reason `meshQuality.ts` reports histograms instead of a verdict: "not watertight" is not actionable, three boundary edges is a pinhole and three thousand is a surface that was never closed. - `src/parser/fieldIntegrate.ts` — pure (no `vscode`/DOM) `integrateFields(model, variables?)` over meshio++'s `dataIntegrate` (>= 10.8.0): the cell-measure-weighted total and mean of the Elemental/Conditional fields — a density field's total mass, a flux field's total power, an occupied volume. **Read-only**, so it is not an `OpRecord` and leaves no history entry; it belongs with `meshQuality.ts`/`meshSize.ts`. The per-region breakdown comes **free**: `modelToMeshio`'s `buildRegions` already emits one `Cell` region per `EntityBlock` and per SubModelPart, and upstream reports every integral independently per named region, so asking at all yields total-mass-per-part. Two behaviours are stated rather than left to surprise: regions are **not a partition** (a cell in two of them contributes fully to both, so region totals need not sum to the domain total), and a cell whose measure is not computable — or a component whose value is non-finite — is excluded from that component's numerator **and** denominator rather than given a fallback weight of 1, which is why `measure` can differ between two components of one array. - `src/parser/dataTable.ts` + `src/parser/writers/xlsxWriter.ts` + `webview/dataTablePanel.ts` — the **Data table** (Advanced ▸ *Data table…*): every node/element/condition/geometry as a row of plain values, and its CSV/XLSX export. Nothing is computed — `coords`, `EntityBlock.connectivity` and every `FieldData` are already keyed by id the moment a file is parsed — so this is layout and serialization over finished data, and the row-at-a-time version already exists as **Inspect**.
  - `dataTable.ts` is **pure and bundled into BOTH runtimes**, and that is load-bearing rather than incidental: the panel and the host exporter build their table from the same `prepareTable(model, kind, opts, membership?)` and the same serializable `TableOptions`, so "what I see" cannot drift from "what I exported" — the alternative was shipping the rows across postMessage, which is hundreds of MB on a real mesh. `TableView` exposes `columns`/`columnTypes`/`rowCount` plus `row(i)` and an allocation-free `rowInto(i, out)` (the export path would otherwise allocate one short-lived array per row, millions of times); every id→index map is built once at prepare time (the same map `webview/fieldData.ts`'s `buildFieldInfo` builds) and the entity kinds resolve a row through a `blockStarts` prefix sum plus a "last block used" cursor, so sequential access — scrolling and export alike — is O(1). **`csvChunks` is the primary serializer and `toCsv` the convenience wrapper**, not the reverse: a multi-million-row table is over a gigabyte of text, past V8's maximum string length, so the write path streams. Three rules are stated rather than left to surprise: a **vector field splits by width** (1 → `VAR`, 2-3 → `VAR_X/_Y/_Z`, >3 → `VAR_0..VAR_n`) — `fieldCalc.ts`'s naming, but deliberately *not* its `Math.min(components, 3)` cap, which is right for an expression scope and would silently drop six of `fieldHessian`'s nine columns; a field's columns appear **by overlap with the requested kind, not by field kind** ("Geometries carry no fields" is false — `partition` writes ONE Elemental `PARTITION_INDEX` whose ids span Elements, Conditions and Geometries alike — and the same test de-noises a table that would otherwise carry permanently blank columns); and an absent value is a **blank, never 0**. Serialization precision is split three ways on purpose: `row(i)` returns raw values (display precision belongs to the panel, file precision to the writers, so they cannot disagree about the number), `f64`/`id` cells use `String(v)` (the shortest decimal that round-trips a double), and **`f32` cells use `f32str`** because `MdpaModel.coords` is a `Float32Array` — reading an element widens it to a double, so `String(v)` for a stored `0.1` prints `0.10000000149011612`, fabricated digits in every coordinate of every exported file. One pre-existing ambiguity is documented rather than "fixed": Kratos gives each kind its own id space, so a field spanning several kinds resolves last-write-wins for a colliding id — exactly as the Field panel and Inspect already do, and a table disagreeing with the panel beside it would be worse than the shared quirk. Unit tests: `src/test/dataTable.test.ts` and `src/test/xlsxWriter.test.ts`; the panel's screenshot is `scripts/screenshots/capture-data-table.mjs` → `images/data-table.png`.
  - `xlsxWriter.ts` is **host-only** (it pulls `zip.ts` → `node:zlib`) and is the from-scratch ZIP writer's second consumer, which is what proves that module reusable beyond the problem archive. Five OOXML parts, **inline strings** (`t="inlineStr"`) rather than a shared-string table, bare `<v>` numbers, no styles — a spreadsheet is a delivery format here, not a document. The sheet XML is assembled as concatenated `Buffer` chunks for the same max-string-length reason the CSV path streams. Excel's **1 048 576 rows × 16 384 columns** are enforced by `xlsxCapacity` (split out so the caps can be asserted without serializing a million rows) and **reported as `truncated`** rather than silently applied — CSV stays the format for a table larger than a worksheet holds, which is why both ship. A non-finite value is written as text: Excel has no NaN literal, and a zero would be a lie.
  - `dataTablePanel.ts` is the first **windowed list** in the webview, and it **paginates before it virtualizes**. One spacer sized `rowCount * ROW_H` runs into the browser's maximum layout height (Chromium ≈ 33.5M px, Firefox ≈ 17.9M px): at 24 px a row that is somewhere past a million rows, after which `scrollTop` stops mapping to a row index and the tail of a large mesh is silently unreachable — the worst failure available, because it looks like it worked. `PAGE_ROWS = 100_000` keeps the spacer two orders of magnitude inside every engine's limit. Unlike `main.ts`'s `NODE_LABEL_LIMIT`, which refuses because five million DOM labels cannot be drawn at all, a paginated table stays completely usable at any size. It reuses the `.meshsize-*` header chrome but needs its own `.dt-*` family: `.meshsize-table` is a fixed-layout `<table>` with a hardcoded first-column width, and a `<table>` cannot host the absolutely-positioned window. `#data-table-panel` is docked to the **lower half** of the canvas rather than filling it, because clicking a row highlights that entity in the scene (a `table:marker` layer, the same two lines the Inspect pick uses) and a full-bleed panel would hide the thing it just highlighted. Framing is a separate **Frame** button, the same click/Frame split `inspectPanel.ts` makes — scanning down a column would otherwise throw the camera at a different entity per row — and `frameTableSelection()` follows `frameLayer` with a half-view-height shift along the camera's up vector, because `resetCamera(bounds)` centres in the WHOLE canvas and the lower half of it is behind the panel. For the same reason the panel calls `syncNavOffset()`, which lifts the nav card via the existing `NavControls.setBottomOffset` (the VTK timeline bar was its first client): left alone the card is buried under the panel and its buttons stop taking clicks at all. it owns its scrolling internally (`.dt-scroll`, with a `position: sticky` header inside it) and is therefore deliberately **not** part of the `#meshsize-panel` CSS family, whose `overflow-y: auto` would nest a scroller inside a scroller and break the sticky header. Export always writes the **whole** table, never the visible page.
- `src/parser/fieldSeries.ts` + `src/parser/fieldSeriesScan.ts` + `webview/seriesPanel.ts` — **time-series field plotting**: one node's or element's value for one variable across every step of a VTK time series, the "what was it three steps ago" counterpart of the Data table's "what is it here". Launched by a **Plot over time** button on the Inspect panel (VTK preview only — an `.mdpa` carries no time dimension).
  - The scan runs on the **host**, and that is the whole design. The webview holds exactly ONE frame — `model`/`fieldInfos`/`prepared` are replaced wholesale by every `vtkFrame` — and **nothing in the repo caches a parsed frame**, so the alternative was walking the timeline through `vtkRequestFrame`: a re-parse, an edit-history replay, a full `buildScene` and a viewport flicker per step, to read one number.
  - The **split between the two parser modules is exactly "does the webview need it"**: `fieldSeries.ts` is pure (types, `sampleFieldAt`, `seriesToCsv`) because the webview imports `seriesToCsv` for the export; `fieldSeriesScan.ts` reads files (`collectFieldSeries`, `stepsFromGroup`, `stepsFromInFile`, `discoverSeriesSteps`) and is shared by the provider and the MCP server, so both run the identical scan. Getting this wrong is not subtle — a `node:fs` import in the webview half fails the esbuild browser build outright.
  - Three data rules are load-bearing rather than incidental. **A gap is `null`, never `undefined`**: `JSON.stringify` DROPS an undefined array element, which would shift every later step by one on the MCP path (the same lesson `mesh_export_table` already learned). **"No value" is split into `missingField` and `missingId`** — "the variable is not written at this step" and "the id is absent at this step" are different problems with different fixes, and one merged counter diagnoses neither. **A step that fails to parse is recorded in `errors` and skipped, never fatal** — a half-written file from a running solver is the normal case, and one bad file must not lose the other ninety-nine.
  - `topologyChangedAt` is the one silent-lie guard: if a later step's node/cell counts differ from the first sample's, the id still resolves but need not be the same entity, so the panel says so. Detection is two integers per step.
  - **The scan reads the files as they are on disk; applied edit operations are NOT replayed per step.** Replaying would rebase a shared, mutable `OperationHistory` from a read-only path and cost roughly what scrubbing the timeline by hand costs — so when `history.appliedCount() > 0` the reply carries a `historyNote` and the panel renders it, rather than letting the numbers quietly disagree with what Inspect shows.
  - Provider rules (`vtkEditorProvider.ts`'s `runFieldSeries`): **snapshot `currentGroup`/`currentRank`/`inFileTimeValues` before the first `await`** (a watcher-driven `discover()` reassigns them on a 500 ms debounce, so a solver writing new steps would otherwise swap the list out mid-scan); **never call `postFrame`/`postInFileFrame`/`adoptFrame`** (they rebase the history and overwrite `lastModel`/`lastFrame`); skip `mergeSubparts` (one extra full parse per subpart per step, and a field sample never reads `subModelParts`); one scan in flight per panel; and **abort on `onDidDispose`**, or closing a preview leaves the host parsing hundreds of files for nobody. `parseMeshFile` takes no `AbortSignal`, so cancellation is checked BETWEEN steps and returns the partial series rather than discarding it.
  - `webview/seriesPanel.ts` is the third hand-drawn chart, which is what finally justified extracting `setupChartCanvas` (+ `CHART_INK`/`CHART_FONT`) into `panelWidgets.ts` — the dpr-scaled-backing-store preamble was byte-identical in `qualityPanel.ts` and `meshSizePanel.ts`. It draws one line per component (names from `dataTable.ts`'s `componentColumnNames`, so a legend and a table column can never disagree — and a 9-component Hessian gets nine lines, not three), **breaks the line across every gap rather than bridging it** (a straight segment over a missing step is data the file does not contain), marks the step the scene is showing, and posts `vtkRequestFrame` when a point is clicked. `#series-panel` is a bottom strip (`bottom: 52px`, above `#timeline-bar` whose movement is the payoff; `right: 296px`, clearing the `#inspect-panel` that launches it) and joins `syncNavOffset`'s max.
  - **The CSV export goes the OPPOSITE way from the Data table's, deliberately**: the table is rebuilt host-side because a real mesh's CSV is hundreds of MB, whereas a series is a few hundred numbers the webview already holds and the host would have to re-run the entire multi-file scan to rebuild. So the webview posts the finished text (`menuExportSeries`) and `meshExport.ts`'s `exportSeriesCsv` saves it — the `screenshot` precedent. Do not "fix" this into symmetry.

The screenshot harness gained a **`HARNESS_MESH=<path>`** override for this work, because the default `double_arch.mdpa` has no fields at all and so cannot exercise a field-dependent panel.
- `src/parser/meshSize.ts` — pure (no `vscode`/DOM/vtk) mesh-size metrics. `computeMeshSize(model)` returns **nodal size** (`NODAL_H`, a faithful port of Kratos' `FindNodalHProcess`: per node, the minimum distance to any other node sharing an element — the all-node-pairs `r_geom` loop, so higher-order geometries include their mid-side nodes) as a Nodal `FieldData`, **element size** (mean edge length = characteristic length, edges from the same boundary-face tables as `meshQuality.ts`) as an Elemental `ELEMENT_H` `FieldData`, plus `boxStats` (min/Q1/median/Q3/max/mean + population `std` + Tukey `whiskerLo`/`whiskerHi = Q1∓1.5·IQR`) and the IQR-outlier `smallElementIds` (< whiskerLo) / `bigElementIds` (> whiskerHi). `attachMeshSizeToModel` stores the fields on `model.derived`; `writeMeshSizeFields(model, target)` is the pure transform behind the `writeMeshSizeFields` op (appends to `model.fields`, dedup by kind+variable). Unit tests: `src/test/meshSize.test.ts`.
- `src/parser/sphereElements.ts` — pure (no `vscode`/DOM/vtk), the single place that spells out what makes a cell a **sphere/particle**, so the reader, the writer, the `setElementRadius` op and the webview renderer cannot drift. There is no `sphere` cell type anywhere: Exodus `SPHERE` maps to meshio++'s `vertex` = VTK_VERTEX (1), a one-node cell, and what separates a particle from an ordinary point cloud is the RADIUS attached to it. `EXODUS_ATTRIBUTE_PREFIX`/`RADIUS_VARIABLE` are the shared spellings; `sphereBlocks`/`sphereCellCount`/`sphereAnchors` select the one-node blocks; `radiusField` finds the SCALAR Elemental (then Conditional) `RADIUS`; `hasSphereRadius`/`radiusCoverage` test/count by **intersection, not coverage** — a multi-block Exodus file merges all its SPHERE blocks into ONE `EntityBlock` and only some may declare the attribute, so requiring full coverage would reject a plainly-particle mesh. `defaultSphereRadius(model)` is the fallback the viewer draws when the mesh declares no radius at all (the common case — see the DCB fixture): half the median nearest-neighbour spacing over a <=2000-anchor sample through a coarse spatial hash (O(n), so a million-particle DEM file cannot turn a viewer default into an O(n^2) scan), degrading to 1% of the bbox diagonal and then to a finite constant — it may never return 0, NaN or Infinity or nothing draws. `computeMeshSize`'s NODAL_H is NOT reusable here: `meshSize.ts` skips point cells, so an all-particle model yields none. Bundled by BOTH runtimes (same arrangement as `writers/exportFormats.ts`). Unit tests: `src/test/sphereElements.test.ts`.
- `src/parser/setElementRadius.ts` — pure `setElementRadius(model, value, mode, target?)` behind the `setElementRadius` op: `absolute` sets (and CREATES the field when absent), `multiply` scales existing values and is a **noop without them** (defaulting a base would silently flatten the per-particle variation it exists to preserve). Creating matters because the file from issue #63 declares 504 `SPHERE` elements and not one Exodus `attrib` variable, so an edit-only op would be inapplicable to the very file that motivated it. `target` scopes to a SubModelPart and its subtree (reusing `findSubModelPart`) — not a luxury: a multi-block Exodus file merges into one `EntityBlock`, so the SubModelParts are the only handle left for giving bulk and boundary particles different radii. Returns `{model, changed, created}`. Tests: `src/test/setElementRadius.test.ts`.
- `src/parser/beamElements.ts` — pure (no `vscode`/DOM/vtk), the direct sibling of `sphereElements.ts` and the one place that says what makes a line cell a **structural member** rather than a boundary edge. The hard part is not finding line cells (`vtkCellType` LINE/QUADRATIC_EDGE) but telling beams from skins: a one-node cell is unambiguously a particle, whereas a line cell is *also* the shape a 2D boundary takes — this repo alone holds ~400 `WallCondition2D2N` in `cylinder_Fluid.mdpa`, ~120 `LineCondition2D2N` in `cylinder_Solid.mdpa` and `outline.vtp`, all of which must keep drawing as plain lines (each is a named regression test against the real file). So the discriminator is the same as the spheres': not the topology but the SECTION attached to it. `sectionAreaResolver` resolves **per cell** — the cell's own `propertyIds[c]` → the parsed Properties' `CROSS_AREA` → `radiusFromArea` = `sqrt(A/π)`; else an Elemental/Conditional scalar `CROSS_AREA` field; else undefined — and per-cell is load-bearing, since repeated `Begin Elements <Name>` blocks merge into ONE `EntityBlock` whose cells routinely sit on different properties. `CROSS_AREA` only (`AREA` is a different Kratos variable and would false-positive) and **strictly positive** (`Glyph3DMapper` clamps a zero scale component to 1e-10, so a zero area would draw an invisible sliver rather than fall back). `beamStats` reports `withSection` and the stricter `elementsWithSection`; **`hasBeamSection` — the auto-enable gate — reads the latter**, because a boundary condition legitimately references the same Properties id as the part it bounds and must never switch the whole rendering on by itself (conditions stay drawable via the panel's opt-in). `defaultBeamRadius` is a twentieth of the median element length and needs no spatial hash, unlike its sphere counterpart: a beam has explicit topology, so its own length is the measurement — and like that counterpart it may never return 0, NaN or Infinity. `buildBeamSegments` lives here rather than in the webview so the geometry is unit-testable (`tsconfig.test.json` covers `src/parser/**`, not `webview/**`); it emits midpoint anchors, the FULL endpoint vector (direction *and* length) and a per-cell radius, takes a `coordOf` override so the Deformed-shape warp can redirect it, and skips zero-length or dangling segments. Bundled by BOTH runtimes. Unit tests: `src/test/beamElements.test.ts`; fixture `src/test/fixtures/mdpa/beam_frame.mdpa` (shipped as `example/MDPA/portal_frame.mdpa`).
- `src/parser/isoSurface.ts` — pure (no `vscode`/DOM/vtk) scalar isosurface extraction (vtk.js has no unstructured-grid contour). Decomposes each volume cell into tetrahedra (tet→1, pyramid→2, wedge→3, hex→6, via the shared `cellDecomposition.ts` tables — also used by `simplexify.ts`) and runs sign-based marching tetrahedra; 2D / surface-only meshes fall back to marching triangles, yielding iso-lines (`is2D: true`). Crossing points weld across cells via an unordered node-id edge key. Returns plain typed arrays (`points`, `triangles`, `lines`). Unit tests: `src/test/isoSurface.test.ts`.
- `src/parser/meshFileParser.ts` — the format dispatcher, and the home of **`meshCompanionNames`/`statMeshSource`**: the single answer to "which files is this mesh actually read FROM?". Several formats keep their bytes BESIDE the opened file — an OpenFOAM `.foam` marker is 0 bytes, a GiD `.post.msh` sits beside a `.post.res` carrying every step, an XDMF names its heavy data in a sibling `.h5` — so anything sizing or cache-keying the opened file alone is wrong for them: the summary threshold could never fire (a 6 GB GiD case measured as 20 KB) and the MCP model cache served a stale model forever. `meshCompanionNames` also replaced the three copy-pasted staging blocks in this same file, which is the point — a family added to `meshioSiblingNames` now reaches the size and staleness paths for free. XDMF is the only format that pays a read (its companions are named inside the XML), bounded by a size cap above which the file is inline-ascii with no external data anyway. The dispatcher itself: `parseMeshFile(fsPath, onProgress?, opts?)` routes by lowercased extension. `.vtk` sniffs the 3rd header line (`BINARY` → whole-buffer `parseVtkLegacyBinary`, else the streaming ASCII parser); VTK XML extensions → `parseVtkXml`; `.vtm` → `parseVtm` (with `parseMeshFile` injected for children); `.stl`/`.obj`/`.ply` → their parsers; everything else falls through to the **meshio++** branch (`isMeshioReadExtension` → `readMeshioModel`, with the tetgen `.node`/`.ele` sibling read off disk here so `meshio.ts` never touches the filesystem and no import cycle forms — same reason `vtkMultiblock.ts` takes an injected child parser). `readFileWithProgress` keeps the loading bar working for buffer-based formats. `opts.meshioFormat` forces a meshio++ reader key (MCP `inputFormat`); `opts.timeStep` selects a step of a multi-step meshio++ file (Exodus, since meshio++ >= 8.6.0), ignored by every other parser. **`xdmfDataFiles(xml)`** (pure, exported for tests) scans an XDMF for the external files its `<DataItem Format="HDF"|"Binary">`s reference (`beam.h5:/data0` → `beam.h5`) so they are placed in MEMFS alongside it — without this an XDMF using HDF storage, which is what ParaView and meshio++ 8.0.0+ write by default, fails to open at all. Nested paths are skipped (MEMFS is flat). **`readMeshTimeSteps(fsPath)`** reads a meshio++ file's `MeshMetadata.timeValues` (`[]` for a format/file with no time concept) — `vtkEditorProvider.ts` uses it to size the in-file timeline before the first frame is parsed. - `src/parser/meshFormats.ts` — pure extension constants (it also re-exports **`COMPOUND_MESH_EXTENSIONS`/`meshExtname`/`meshStem`**, which live in `meshioFormats.ts` — the zero-import leaf that owns the `.post.*` registry entries needing them). **`meshExtname(fsPath)` is the single authority for "which format is this path?"** and replaces `path.extname` at every dispatch site (`meshFileParser.ts`, `meshExport.ts`, `mcp/tools.ts`, `operations.ts`; the timeline dispatch is no longer spelled at a call site at all — see `timelineKindFor` below, which exists because that parenthetical was once a claim rather than a fact and `vtkEditorProvider.ts` was the site it missed): it returns the longest registered COMPOUND extension a path ends with, else the ordinary last-dot one. the file itself for an in-file series — or BOTH halves for a GiD ascii pair, since the steps are appended to the `.post.res` while the opened tab is usually the `.post.msh`; `undefined` for a static format). Both now branch on the one helper, so "the way `discover()` does it" is enforced rather than asserted. There is **no VS Code integration harness in this repo**, so a decision made above the vscode line is a decision nothing can test — keeping it here is what makes it assertable (the `runCore.ts` doctrine). The single `kind` replacing two independent `includes` rests on the two lists being **disjoint**, which `meshFormats.test.ts` asserts rather than assumes.
- `src/parser/meshSummary.ts` + `webview/summaryPanel.ts` — the **header summary**: what is in a mesh file, without loading it. Above `kratos.preview.summaryThresholdMb` (default **250**, `0` = never) both providers post `meshSummary` instead of parsing, and the webview shows a card plus `#stats` rows with one action, **Open full mesh anyway**. **`SummaryCost` is the spine of the module and is four-valued, not a boolean**, because a "header summary" costs wildly different things per format and a UI implying "instant" would be lying about three quarters of the table: `"header"` is a bounded prefix read (VTK XML `<Piece>`/`Extent` attributes, a PLY `element` declaration, a binary STL's facet count at byte 80 — 84 bytes regardless of file size, and `.vtm`'s index), `"scan"` streams the file once building nothing (`.mdpa`, `.obj`, ascii STL), `"buffered"` holds the file **plus its siblings** resident AND copied into MEMFS (~2x — `readMeshMetadata` does `fs.readFile` then `FS.writeFile`, so the seven `HEADER_METADATA_EXTENSIONS` are cheap versus PARSING, not in I/O or peak memory), and `"read"` means meshio++ parsed the mesh to answer and discarded it. The last two still earn their place: they skip the JS typed arrays, the model and the structured-clone `postMessage`, which is the actual failure mode. `summaryCostFor(path)` is the a-priori estimate from the extension; `MeshSummary.cost` is the measured truth (ascii-vs-binary and inline-vs-appended are facts about bytes). **`bytesRead` is the offset the answer depended on, not the bytes pulled off disk** — the only falsifiable statement of cost, and what `meshSummary.test.ts` asserts against `fileSize`. **`unknown[]`** names what a format genuinely cannot report (`"bounds"` — never computed anywhere, since reading coordinates is the read this exists to avoid; `"cell types"` from a VTK XML header, which are a payload array; `"per-block counts"` for a `.vtm`), because a `0` or an empty list otherwise reads as "none", the same trap `MeshioMetadata` avoids by omitting `bboxMin` rather than nulling it. **`.mdpa` is always a `"scan"` and cannot be otherwise**: MDPA declares no counts anywhere — a block's size is implied by how many lines precede its `End` — so `MdpaSummaryScanner` (in `mdpaParser.ts`, beside `MdpaParserCore` so it can reuse `stripComment`/`ENTITY_KINDS`/`SUBLIST_KEYS`/`FIELD_KINDS`) streams the whole file with a data line costing `n++` and nothing else, and **replicates `handleBegin`'s Properties trap door** or a nested `Begin Table` would count as a block. VTK XML counts are **as declared**: `buildBlocksFromOffsets` normalizes poly-lines/polygons/strips on read, so a `.vtp` opens with more cells than its header states — reported as a note rather than left to disagree silently. The **gate is the pure `shouldSummarize(...)`**, and its check ORDER is the design: `userForcedFull` first (sticky for the panel's lifetime, deliberately not persisted), then `reason === "reload"` returning `summaryShown`, which is BOTH halves of the safety property — a solver's growing output can never flip a live preview into a summary, and a summarized 4 GB file can never silently become a full parse on a later watcher tick. Provider wiring: the gate sits **above** `timelineKindFor` in `vtkEditorProvider.discover()` (an in-file series returns from that branch without reaching the static path, and `readMeshTimeSteps` does its own full read) and before `parseMdpaFile` in `mdpaEditorProvider.postModel()`. The summary branch reaches none of `lastModel`/`adoptFrame`/`history.setBase`/`opState`, and **must never reach `applyPendingOps()`** — `takePendingOps` is consume-once, so touching it would permanently destroy a Load-problem edit recipe; `maybeInitPt()` IS called, being model-independent. `meshSummaryOpenFull` re-runs with `reason: "initial"` on purpose, because that run is the one that must pick the recipe up. MCP parity is a **sibling `summary: true` argument on `mesh_info`, not a widening of `metadataOnly`** (whose three refusals are asserted contract); it never refuses for ineligibility and reports `cost` instead. Unit tests: `src/test/meshSummary.test.ts`, whose per-format **oracle assertions** (every summarizer's counts equal the full parser's on a committed fixture) are the real gate — the failure this could introduce is not a crash but a quiet lie.

- `src/parser/meshioConvert.ts` — pure `meshioToModel(mesh, diagnostics)` / `modelToMeshio(model, diagnostics, opts?)`. Read: flat points+`dim` → interleaved xyz (z=0 when 2D), cells re-flattened into VTU-style (types, end-offsets, 0-based conn) and handed to **`buildBlocksFromOffsets`** rather than built directly — meshio's blocks are already homogeneous, but the helper also fans `polygon` into triangles, does 0→1-based, and returns the `expansion` map that is the only correct way to realign `cell_data` across that split (block names are restored afterwards from a `(vtkCellType, stride)` map, so layers read `triangle`, not `VtkCell_5`). `cell_data` is indexed via a `kept[]` list because meshio's arrays align with the **original** `mesh.cells` — a skipped block in the middle would otherwise shift every value. **Ragged (polygon/polyhedron) blocks** (`MeshioPolygonCellBlock`/`MeshioPolyhedronCellBlock`, crossing the wasm boundary since meshio++ 8.7.0 — previously rejected there outright) are now DRAWN rather than diagnosed-and-skipped, which is what stopped a polygonal or polyhedral file from opening empty. They take two different routes, and `isRectangularCellBlock`/`meshioBlockRowCount` still tell them apart: a 1-level ragged **polygon** block needs no work at all — its CSR is appended to the flat arrays as `VTK_POLYGON` and `buildBlocksFromOffsets` normalizes it into triangles/quads/a fan exactly as it does for a VTK PolyData polygon — while a 2-level ragged **polyhedron** block is decomposed into tetrahedra by `polyhedronDecompose.ts` in a PRE-PASS (before `coords` is sized, since it invents apex nodes). Because a polyhedron row fans into many flat cells while `regionsToParts` indexes `expansion` by SOURCE row, a `flatPerRow` tally folds `buildBlocksFromOffsets`' per-flat-cell expansion back onto rows — an identity for every mesh without a polyhedron. Nodal fields are extended at the apex nodes by the mean of their generators (the rule `refineMesh.ts` uses); cell data replicates through the same `expandCellField` path a fanned polygon already used. `sanitizeVariable` is load-bearing: `mdpaWriter.ts` emits variable names verbatim, so gmsh's injected `gmsh:physical` (kept — it *is* the physical-group id) becomes `gmsh_physical`. Read also honours the **`*_data_components`** maps (meshio++ >= 9.9.0, `{name: k}`, emitted only for non-scalars — absent means one component) in preference to dividing an array's length by the entity count, which is what catches an array whose declared width and length disagree; and `exodus:time` is filtered out of the "Dropped field_data" diagnostic (`INTERNAL_FIELD_DATA_KEYS`) because every Exodus read carries it since 9.9.0 and it is not the user's data. Write reuses the writer layer wholesale (`buildCellLayout`/`point`/`cellFieldArray`); Elemental+Conditional collide in meshio's single `cell_data` namespace and get a kind suffix; and it emits **three things beyond geometry**, each needed by a format that would otherwise silently lose it: `point_data_components`/`cell_data_components` for every field with `components > 1` (without them a `(n,3)` array re-enters C++ as `(3n,1)` — the root cause of MED's write-then-fail-to-read and of the corrupted-vector-field behaviour in meshio++'s own operations), `regions` (see below), and the `exodus:attr:` namespace. Cells are grouped by **SOURCE BLOCK IDENTITY** (`LaidOutCell.blockIndex`) rather than by `(meshioType, stride)` or by block NAME, so each `EntityBlock` stays a block of its own on the way out — name was not unique enough: `mergeMesh` appends the incoming mesh's blocks unrenamed, so two same-named same-type blocks FUSED into one while `meshioBlockOrder`'s parallel walk still counted two, and the three oracles that assign a flattened wasm result with a running cursor (`partitionMesh`/`errorEstimate`/`transferField`) silently attached each block's values to the other's cells; the `flat.length !== total` guard cannot see it, because fusion moves cells between blocks without losing any. **`meshioBlockOrder(model)` is that walk, exported here** because this file defines the correspondence, and the three modules that used to carry a byte-identical private copy now share it plus a block-count guard (`LaidOutCell.blockName`, added to `writerCommon.ts` for this) — that is what makes the `Cell` region emitted for a block cover exactly one meshio block, which is Exodus's rule for recovering an `eb_names` entry, and it also stops an `Elements` and a `Conditions` block that happen to share a cell type from being fused. **`buildRegions`** emits one `kind:"cell"` region per emitted block (named after the `EntityBlock`) plus one `cell` + one `point` region per SubModelPart, walking children recursively: cell entries resolve through `layout.elementIdToCell`/`conditionIdToCell`/`geometryIdToCell` (the last added to `CellLayout` for this, since no field kind needs it), point entries through `nodeIndexMap`; entries are global block-major indices, ascending; `dim` comes from `cellCategory` when the cells agree and is `-1` otherwise; a part's node and cell regions deliberately share ONE name (MED/Abaqus key a group by name and the read path merges same-named regions back into one part), a nested part uses its dotted path (a `/` would reach an HDF5 group name in MED), and names are de-duplicated with a `_2`… suffix so two unrelated groups never merge. Measured: this makes SubModelParts survive an export to `.med` (families) and `.inp` (`*NSET`/`*ELSET`), and block names survive to `.exo`; **gmsh 4.1 writes no `$PhysicalNames` at all** for a mesh with no `gmsh:dim_tags`, so `.msh` export carries no groups (upstream gap, **re-measured at 10.20.2 and still open**, and pinned by a test in `meshio.test.ts` so a future upstream fix fails loudly rather than leaving this note stale — MED and Abaqus do carry groups out). **Exodus per-element attributes** (meshio++ >= 9.3.0) are the sphere-radius carrier and get a rule of their own: on READ the `exodus:attr:` namespace is stripped before `sanitizeVariable`, so `exodus:attr:RADIUS` becomes plainly `RADIUS` (also a real Kratos variable, so a `.mdpa` export yields a `Begin ElementalData RADIUS` block) instead of the unusable `exodus_attr_RADIUS`; on WRITE `modelToMeshio`'s **`opts.exodusAttributes`** (set only for `fmt === "exodus"`, in `meshio.ts`) puts it back on every SCALAR Elemental/Conditional field. That is an **export-time rule, not model state** — no `MdpaModel` slot to keep alive through `remesh`/`levelset`/`linearToQuadratic`, and prefixing is strictly information-preserving because the Exodus writer DROPS all non-prefixed `cell_data`. Two details are load-bearing: (a) meshio++ NaN-fills the attribute for blocks that do not declare it, and `writerCommon`'s `num()` maps NaN to `"0"` — so `dropNonFinite` turns the field SPARSE at the read boundary (by value, not by block, since `buildBlocksFromOffsets` may already have merged several meshio blocks into one), and an all-NaN array is dropped entirely with a diagnostic rather than left as a permanently empty entry in the field pickers; (b) the write NaN-fills the cells a sparse field does not cover (via `coveredCells`, since `cellFieldArray`'s 0 is indistinguishable from a real 0) — that is what makes meshio++ omit a block's `attrib{k}` entirely and a partly-attributed file round-trip unchanged. A **vector** field is never prefixed, but since 9.9.0 that no longer loses it: an Exodus attribute is one value per element (upstream now RAISES rather than truncating, testing the product of all trailing dimensions), while ordinary `cell_data` is written as an element VARIABLE and survives whole — so the old "written as ordinary cell data (which the Exodus writer drops)" diagnostic is gone. The caveat that stays ours to know: upstream warn-and-skips an unprefixed `cell_data` array that does not cover EVERY block, so a sparse vector field can still be lost. What our own writer does about a partly-covered field is now **reported rather than silent**: the NaN-fill that makes meshio++ omit an uncovered block cleanly is the `exodusAttributes` **scalar** path only — a vector is deliberately left unprefixed, so it always takes `cellFieldArray`'s **zero**-fill branch, and a 0 there is indistinguishable from a real 0 on read. So whenever `fill === 0` and the field's `ids.length` is short of the layout's cell count for its kind, a diagnostic names the variable and the shortfall. The test is the id count rather than the exact `coveredCells` set on purpose: that set is sized with the mesh, and building one per field on every export would cost real memory where the array build is already the expensive part — and since covered cells are a subset of the ids, a short id list is a definite gap, which is the case that actually occurs (a field written for some blocks only). `mesh.regions` (meshio++ >= 8.1.0) is handed to `meshioRegions.ts`, whose SubModelParts and materialized side-facet Conditions blocks are appended before `finalizeModel`. Unit tests: `src/test/meshioConvert.test.ts` (no wasm needed).
- `src/parser/openfoamCase.ts` — reading an **OpenFOAM case**, which is a DIRECTORY (`<case>/constant/polyMesh/{points,faces,owner,neighbour,boundary}`) addressed through a 0-byte `<case>/x.foam` marker. The marker is not a convention we chose but a structural requirement: a VS Code custom editor **cannot bind to a folder**, so `filenamePattern`, the Explorer context menu, `viewTypeForMesh` and `recentMeshes` all need a file. It is also all upstream needs — **measured against the live 10.20.2 wasm**, `readMesh(p, "openfoam")` matches a `.foam` suffix **BY NAME**, so the marker is never staged at all: `stageFiles` puts `constant/polyMesh/*` under `/mio_in` and the read path is a synthetic `/mio_in/<name>.foam`. Also measured: **`points`/`faces`/`owner` are required** and `neighbour`/`boundary` optional (without `boundary` the boundary-face block vanishes entirely, so its absence is a diagnostic); `.gz` is **not** supported, hence the gunzip during staging; zones are never read — a claim that is now MEASURED rather than assumed (the old `existsSync` evidence was confounded by `collectOpenFoamCase` staging only five filenames, so a zone file never reached MEMFS; handing the reader one directly gives a byte-identical read, pinned in `meshio.test.ts` alongside a second assertion that the staged directory really is the one the reader opens); and `readMetadata` works but reports `fellBackToFullRead: true`, which is why `.foam` stays out of `HEADER_METADATA_EXTENSIONS`. **Patch names do not survive upstream** — a two-patch case returns `regions: []` with membership only as `cell_tags = -(patchIndex+1)` on the boundary block — so `parseOpenFoamBoundary` recovers them and `applyOpenFoamPatches` joins them on. That parser's one non-negotiable rule is **never skip an entry**: the join is POSITIONAL, so dropping a malformed entry would silently rename every patch after it, which is indistinguishable from success — a broken entry becomes a `synthesized` `patch_<i>` placeholder holding its index. The join runs on the finished model rather than inside `meshioToModel` (`regionsToParts` needs `kept`/`expansion` that exist only in there, yields `elementIds` where these are semantically Conditions, and offers no hook to drop the tag field); it classifies blocks **by tag, not by cell type** (a boundary mixing tris and quads is two blocks, and nothing measured fixes upstream's block order), flips all-boundary blocks to `Conditions` in a fresh id space while leaving surviving Elements' ids alone (sparse ids are legal, and assuming volume-blocks-first would be unearned), **deletes `cell_tags`** (after the flip it is an Elemental field keyed on ids that moved into the condition space, i.e. actively wrong), and **cross-checks `nFaces`** — the only thing standing between a tag convention we have not seen and every patch being silently misnamed. `openFoamCaseSize`/`openFoamCaseStamp` exist because the marker is 0 bytes with an mtime that never moves when `blockMesh` reruns: without them the MCP model cache would serve a stale mesh **forever** and `shouldSummarize` could never fire for a 4 GB case. `wouldOverwriteOpenFoamCase` compares **directories, not paths**, since exporting to `<case>/other.foam` rewrites the same polyMesh. Unit tests: `src/test/openfoamCase.test.ts` (pure); the round-trip and patch-name oracles are in `src/test/meshio.test.ts`, built on the temp-dir case its export test already writes.
- `src/parser/meshioRegions.ts` — pure (no `vscode`/DOM/wasm) **named regions → SubModelParts**. A meshio++ `Region` (since 8.1.0, riding on the mesh object so `readMesh` carries it with no extra call) is the uniform spelling of a gmsh physical group, an Abaqus `*NSET`/`*ELSET`/`*SURFACE`, an Exodus block or set, and — since meshio++ 9.6.0 — a **MED** `FAS`/`GRO` family group (`Point` from `NOEUD`, `Cell` from `ELEME`; `Side` has no MED equivalent): `{name, kind: "point"|"cell"|"side", dim, tag, entries}`. `regionsToParts(...)` maps **point** → `nodeIds` (index+1, matching `finalizeModel`'s synthesized ids), **cell** → `elementIds`, and **side** → materialized boundary facets emitted as `kind:"Conditions"` `EntityBlock`s (one per region, split per facet type only when a region spans two) plus the matching `conditionIds` — so an Abaqus `*SURFACE` is a visible, framable layer and a `.mdpa` export yields real Kratos Conditions. Regions **sharing a name merge into one part** (Abaqus routinely declares an `*NSET` and an `*ELSET` under one name; a gmsh name may be declared per dimension). Two index shifts have to be undone for cell/side entries, which are *global block-major cell indices over the ORIGINAL meshio blocks*: a block whose type has no VTK equivalent is dropped yet still consumes global indices, and `buildBlocksFromOffsets` may fan one cell into several entities — `expansion` (the same array that realigns `cell_data`) is what makes the second recoverable. The `FACETS` table mirrors upstream `detail/cell_faces.hpp` (3D) and `detail/cell_edges.hpp` (2D) — **the facet ORDER is what `side` regions index**, so a reordering upstream silently mislabels every side set. Unit tests: `src/test/meshioRegions.test.ts` (pure mapping + gmsh/Abaqus fixtures through the real wasm, incl. a geometric check that every materialized facet is a boundary edge of exactly one cell).
- `src/parser/meshio.ts` — the meshio++ loader + MEMFS I/O (no `vscode`; Node-testable). `loadMeshio()` returns a **fresh instance per operation** — `ALLOW_MEMORY_GROWTH=1` means a memoized one would pin the high-water mark of the largest mesh ever opened for the host's lifetime (the same reasoning behind MMG's per-run worker), and it needs no `FS.unlink` bookkeeping. `readMeshioModel(mainName, files, ext, format?, timeStep?)` writes the bytes into MEMFS via the shared **`stageFiles`** (a `/mio_in` scratch root mirroring `writeMeshioBytes`'s `/mio_out`, so a staged file named `tmp`/`dev` cannot collide with MEMFS's own entries) — `MeshioInputFile.name` is a relative PATH guarded by `isSafeEntryName`, not a basename, which is what lets an OpenFOAM case stage `constant/polyMesh/*` and what let `xdmfDataFiles` stop dropping a ParaView `data/beam.h5` reference; the three read functions share one staging call and one `errText` (an Emscripten `FS.ErrnoError` has `message === undefined`, so the obvious `e.message` yields the literal "undefined") and walks the candidate list, recording a diagnostic when a non-default wins and, on total failure, throwing one error naming **every** attempt; an explicit `timeStep` (meshio++ >= 8.6.0) routes through `readMeshSelective` instead of `readMesh`, an out-of-range value surfacing meshio++'s own error verbatim. Each candidate in `MESHIO_LENIENT_RETRY_FORMATS` (`med`) gets a second, **lenient** attempt (`ReadOptions::mLenient`, reaching wasm since meshio++ 9.9.0) before the next candidate is tried, with its own diagnostic: upstream's Python surface silently falls back to a pure-Python reader for the MED constructs its C++ core declines, and wasm has no such fallback, so through 9.8.0 a real Salome/Code_Aster file could not be opened here **at all**. Which constructs a lenient read skipped is not knowable from JS — upstream records them in a `MedInfo` the registry boundary discards. `readMeshioTimeValues(mainName, files, ext, format?)` is the `readMetadata(...).timeValues` counterpart, used to size the in-file timeline without a full read; **Exodus is still the only format it reports anything for** — MED honours a `timeStep` on read since 9.9.0 but is not one of upstream's metadata readers, so its step count is undiscoverable before a read and it stays out of `IN_FILE_TIMELINE_EXTENSIONS` (a `timeStep` passed explicitly, e.g. the MCP argument, still reaches a MED read). `readMeshioMetadata(mainName, files, ext, format?)` is the full-header counterpart (counts, block shapes, data-array names, `regions[]`, bbox) behind `readMeshMetadata(fsPath, format?)` in `meshFileParser.ts` (same tetgen/XDMF-companion staging as a read) and the MCP `mesh_info` `metadataOnly` fast path: the `MeshioMetadata` interface is the upstream `MeshMetadata` shape minus nothing the module reads, and `fellBackToFullRead` is the gate — callers refuse on true rather than serving a full read at header price. Measured per format at 10.20.2 (`HEADER_METADATA_EXTENSIONS` in `meshFormats.ts`: `.xdmf`/`.xmf`, `.msh`, the GiD `.post.*` set; Exodus/MED/CGNS/medit/abaqus/nastran/su2/unv all fall back, and `.vtu` is deliberately unlisted since those extensions parse natively with no registered read candidates); native header paths report no bbox and no regions, omitted/empty rather than null so "not computed" cannot misread. `writeMeshioBytes` returns `{data, companions}` (always bytes for `data`: gmsh 4.1 and ansys are **binary**) — since meshio++ 8.0.0 the wasm XDMF writer emits a companion `<stem>.h5` referencing it by name, so the MEMFS path carries the caller's `stem` (`opts.stem`, defaulted via `memfsStem`) rather than a fixed `out`, and anything the writer left behind in MEMFS beyond the named file is returned as a companion for the caller to write alongside it. `configureMeshio` is an escape hatch only: unlike mmg, `{wasmBinary}` is **silently ignored** here (Emscripten pruned it from this build's `INCOMING_MODULE_JS_API`), so the loader passes `locateFile` itself in both layouts — and since meshio++ 8.8.0 that `locateFile` must be **name-aware**. The package now ships TWO native artifacts (sequential `meshioplusplus_wasm.{mjs,wasm}` + OpenMP/pthreads `meshioplusplus_wasm_mt.{mjs,wasm}`) and `loadMeshioPlusPlus(overrides, {variant})` picks between them itself: `resolveVariant` returns `"mt"` whenever `crossOriginIsolated` is undefined, i.e. under Node, i.e. in the extension host. Returning a fixed path hands the mt glue the sequential binary and **every meshio format** dies with `Aborted(LinkError: WebAssembly.instantiate(): Import #0 module="a" function="a" ...)`, an error naming neither the file nor the variant — `meshio.test.ts` pins the invariant (the name `locateFile` is asked for matches the loaded `parallelBackend()`). `loadMeshio` also falls back to `{variant:"seq"}` once if the threaded build cannot instantiate (no SharedArrayBuffer, locked-down container), caching the DECISION in a module flag and never the instance. The `_mt` pair is ~6.2 MB of the `.vsix`; it earns its keep now that the extension calls into meshio++'s own mesh OPERATIONS — `smooth`/`reorder`/`partitionLabels` (see the "Additional mesh operations" section above) run measurably faster threaded on a large mesh, whereas earlier this variant selection existed only for parity with upstream's default (the extension called meshio++ for I/O only). `MeshioModule`'s TypeScript interface carries these operations' signatures alongside the read/write ones, plus **`gradient`** (>= 9.10.0, the fourth oracle — see `gradientField.ts`) and **`hasCgnslib()`** (>= 9.22.0). Nothing branches on the latter — the wasm build has carried cgnslib since 9.22.0 and still does at 10.20.2, which is what makes ADF-backed containers and the CGNS 3.x section layout readable — but `meshio.test.ts` asserts it, because a build that silently dropped the dependency still reads every file meshio++ writes itself and the regression would surface only on a user's ADF file. Tests: `src/test/meshio.test.ts` (real wasm).
- `src/parser/writers/` — the **writer layer** (inverse of the parsers): serialises an `MdpaModel` back to file text for Save/Export. `writerCommon.ts` holds the shared helpers — `nodeIndexMap` (connectivity stores node **ids**, so index-based formats remap id→0-based), `buildCellLayout` (flattens all blocks into one ordered cell list + element/condition/**geometry** id→cell maps; every `LaidOutCell` also carries its source `blockName`, so a writer can regroup by original block rather than only by (type, stride) — `meshioConvert.ts` is the consumer of both, for the named groups it emits), `surfaceTriangles` (surface cells + volume **boundary** faces via a once-seen face map; `{ volumeOnly }` option), and `point/cellFieldArray` (positional field arrays). Per-format writers: `mdpaWriter.ts` (id-based; copies `Properties`/`ModelPartData`/`Table` blocks verbatim from the original source text when given `{ sourceText }`, else emits a default `Properties 0`. `Constraints` is **emitted from `model.constraints`, not copied** (`writeConstraints`, rows indented two spaces like every other row this writer produces, a raw row re-emitted as its own text) — the verbatim `TRAILING_VERBATIM_BLOCKS` group and its `warnIfNodesMissing`/`sourceNodeIds` staleness heuristic are gone, because an edit now maintains the constraints instead of leaving copied text keyed to node ids it has replaced. What survives that change unaltered is the **ORDERING** rule, which is load-bearing: `VERBATIM_BLOCKS` is emitted BEFORE `Begin Nodes`, while `Constraints` must be emitted AFTER the nodes and the entity blocks (and before the SubModelParts naming their ids), because Kratos' `ModelPartIO::ReadConstraintsBlock` resolves a constraint's master/slave columns against nodes it has already read — emitting them early writes a file Kratos cannot read. Two `onWarning` checks replace the old one, both computed from the MODEL: constraints the `sourceText` declared that the model no longer carries are **named and OMITTED rather than copied** (the only way to reach that state is an op that deliberately dropped them — remesh, level-set, a foreign-format round trip — where the copied text is provably wrong), and any `SubModelPart.constraintIds` entry no block defines is reported, which is the original defect class and needs no source text at all. **The defect the verbatim group originally closed** is worth keeping in mind: `writeSubModelPart` has always written the `SubModelPartConstraints` id lists, so before either fix a Save produced a file naming constraints it no longer contained, and real Kratos files carry them (`LinearMasterSlaveConstraint` in both committed fixtures). `MeshWriteOptions extends MdpaWriteOptions`, so `onWarning` reaches `meshExport.ts` (a `showWarningMessage` after the save succeeds — advisory, never a failure) and the MCP `mesh_transform`/`mesh_convert` `warnings` arrays unchanged. Tests: `src/test/mdpaConstraints.test.ts`), `vtkLegacyWriter.ts` (ASCII UNSTRUCTURED_GRID + FIELD data), `vtkXmlWriter.ts` (`writeVtu`/`writeVtp`, inline ASCII DataArrays), `stlWriter.ts`/`objWriter.ts`/`plyWriter.ts` (surface formats; volume cells → boundary triangles). `meshWriter.ts` is the dispatcher, with **two entry points**: sync `writeMeshFile(model, ext, opts?)` → `string` for the native formats, and async **`writeMeshFileAsync(model, ext, opts?)` → `Promise<MeshWriteResult>`** (`{data, companions}`) for any exportable format, delegating to `writeMeshioBytes` for the meshio++ ones. The split exists because **gmsh (4.1) and ansys write BINARY** — the old string-only path plus `writeFile(…, "utf8")` corrupted them; callers now pass `result.data` to `fs.writeFile` with **no encoding** (strings still default to utf8, a Uint8Array writes raw). `companions` carries files the writer emitted BESIDE the named one and every caller must write them next to the destination, **creating directories as needed** — a companion's `name` is a relative PATH, not a basename. Two shapes reach it: since meshio++ 8.0.0 the wasm XDMF writer keeps its heavy arrays in a sibling `<stem>.h5` and leaves only `<stem>.h5:/data0` references in the XML, so the XML alone is a dangling file; and since meshio++ 9.20.0 the OpenFOAM writer emits a whole `constant/polyMesh/` TREE while leaving the named `.foam` path a 0-byte marker, so there the companions ARE the mesh and a caller that skipped them would write nothing. `writeMeshioBytes` therefore writes into a scratch MEMFS directory and harvests it RECURSIVELY (rather than diffing `/`, which would have to know which of MEMFS's own entries to ignore), guarding each name with `isSafeEntryName` — the same zip-slip policy `problemZip.ts` applies, reused rather than restated. That is also why the MEMFS name carries the destination stem (`opts.name`) rather than a fixed `out` — the stem reaches file content verbatim. It re-exports the format registry from the dependency-free `exportFormats.ts` — `NATIVE_EXPORT_EXTENSIONS` (`.mdpa/.vtk/.vtu/.vtp/.stl/.obj/.ply` — structured `.vti/.vts/.vtr` and `.vtm` are **excluded**, an unstructured model can't reconstruct them), `EXPORTABLE_EXTENSIONS` (native + `MESHIO_EXPORT_EXTENSIONS`, spread as `as const` so it stays the `ExportableExtension` type source and `EXPORT_FORMAT_LABELS` stays exhaustively checked at compile time), `EXPORT_MENU_GROUPS` (menu-only grouping — ~30 formats in one flat dropdown is unusable, and it drops the alias extensions `.nas/.fem/.tec/.dato/.xmf` that repeat their primary format), `EXPORT_FORMAT_LABELS`, `isExportableExtension`, `isNativeExportExtension` (kept in their own module so the webview bundle can import the list without pulling in the writers). Pure/Node-testable; round-trip tests (`parse → write → re-parse`) in `src/test/writers.test.ts`.

### Webview (browser IIFE, `webview/`)
- `webview/main.ts` — entry point. Owns the VTK.js scene. On receiving a `model` or `vtkFrame` message it calls `buildScene(resetCam?)`, which creates one `vtkActor` layer per `EntityBlock` (visible — except volume blocks when covering surface blocks exist; `MMG_Interface*` blocks don't count as covering, so a level-set's split domains stay visible) and one per `SubModelPart` (hidden by default). For `vtkFrame` and for in-place op re-renders (`model` with `keepCamera`), `snapshotVisibility()` records the current layer toggles and `buildScene` consumes them (`nextVisOverride`) so surviving layers keep their state — outline checkboxes included — while new layers get the defaults (camera is also preserved by passing `resetCam=false`). Node-id labels are capped at 1 000 nodes. The `Quality` toolbar button / `computeQuality` message runs `computeMeshQuality` and toggles the quality panel; "Highlight bad" builds a red overlay layer (`quality:highlight`) from a metric's bad-element ids by reusing `addLayer`/`buildPolyData`. The `Field` toolbar button / `field` message toggles the field panel (see below). The `Find` toolbar button / `locateEntity` message opens a search bar: the matched entity is highlighted in yellow (`find:highlight` layer) and all other layers are forced to wireframe for contrast; closing the bar restores the prior wireframe state. The View ▾ menu's **Screenshot…** item (also the `kratos.mdpa.screenshot` palette command / Ctrl+Alt+P via the `takeScreenshot` host→webview message) calls `takeScreenshot()`, which uses `apiRW.captureNextImage()` (falling back to `canvas.toDataURL()`) and sends a `screenshot` message with the base64 PNG to the extension host. On `vtkGroup`, a `TimelineControl` bar is shown at the bottom of the viewport. Module-scope maps `elementById`, `conditionById`, `geometryById` are populated in `buildScene()` and shared by the quality panel, the find feature, and quiver cell-centroids.
- `webview/meshBuilder.ts` — converts `MdpaModel` nodes + `Cell[]` into `vtkPolyData`. Handles point clouds (no cell type) as vertex cells. Optionally takes a `FieldAttach`: nodal scalars are pushed into the point-data array *inside* `localOf` as each local point is born (so they stay aligned with the local remap), and cell scalars are collected per emitted cell in VTK's verts→lines→polys order — volume boundary faces inherit their owning cell's value via a face-owner map. `buildPolyData`'s optional `{wantPickMaps: true}` additionally returns `pointGlobalIds` (local point index → global node id, the same `localOf`-birth-order array as the point-scalar path) and `cellEntityIds` (one entry per emitted cell, same verts→lines→polys order as the cell-scalar path, -1 for an entity-less cell) — the data the Inspect click-to-probe feature (see below) resolves a `vtkCellPicker` hit against; skipped by default since the extra arrays cost real memory on a mesh that will never be clicked on.
- `webview/outline.ts` — renders the sidebar tree of checkboxes (toggle layer visibility) and labels (frame/zoom to layer). SubModelPart rows (`exportPath` set) also get an export button that deploys a body-attached format dropdown (`OutlineExportUI` = icon + `EXPORTABLE_EXTENSIONS` from the pure `writers/exportFormats.ts`), posting `menuExportPart {format, path}` via the `onExport` handler, **plus an organize (`tree` icon) button** that opens a dropdown offering *New child* (an inline name input, the same no-native-prompts convention as the rename input), *Move under*, *Merge into* and **Edit membership** — posting `createSubModelPart`/`moveSubModelPart`/`mergeSubModelParts`/`addSubModelPartEntities`/`removeSubModelPartEntities` via `onCreateChild`/`onMove`/`onMerge`/`onAddEntities`/`onRemoveEntities`; the destination lists come from `OutlineExportUI.allPaths` and exclude the part itself and its own subtree, since the core would only refuse those. *Edit membership* is a kind `<select>` (`SmpEntityKind`, imported from `subModelPartTree.ts` — pure, so the webview bundle can pull it in directly) plus a free-text id-list field (`"1,2,5-10"`, parsed by the module's own `parseIdRangeList`, exported for reuse: comma-separated ids and inclusive ranges, malformed tokens silently skipped) and Add/Remove buttons; an empty/unparseable result is a client-side no-op — the menu stays open rather than posting nothing meaningful. One dropdown rather than four more buttons on an already-crowded row, the same reasoning that put ~30 export formats behind a single icon. **Plus a delete (X, `close` icon) button** that posts `applyOp {op:"deleteSubModelPart", path}` via `onDelete`, **a rename (pen, `edit` icon) button** that swaps the row label for an inline text input (Enter/blur to commit, Escape to cancel) and posts `applyOp {op:"renameSubModelPart", path, newName}` via `onRename`, and **when the node carries `counts`, an info (`info` icon) button** that opens a dropdown listing recursive (subtree) entity counts by kind; only one dropdown/rename-input is open at a time (outside-click / Escape / scroll dismiss).

- **Video recording** (`src/parser/recordPlan.ts` + `webview/videoRecord.ts` + `webview/recordPanel.ts` + `src/mediaExport.ts`) — View ▾ ▸ **Record…** captures the viewport as a **WebM video** or a **numbered PNG sequence**, from either a VTK **time-series playthrough** or a **camera turntable** (so a mesh with no time series, which includes every `.mdpa`, gets an animation too).
  - **The capture surface is an offscreen 2D canvas, not the WebGL canvas, and that is load-bearing.** vtk.js requests its context with `preserveDrawingBuffer: false`, so the drawing buffer is valid only until the task that rendered it yields. **Measured, not assumed**: a `drawImage(vtkCanvas)` in the same task as `render()` copies ~40k lit pixels, and the identical call one task later copies **zero** — so the roadmap's original suggestion (`captureStream(0)` + a `requestFrame()` after an await) would have recorded black frames. `captureStep` therefore does `render()` then `drawImage` back-to-back and synchronously; anything inserted between those two statements breaks it silently.
  - Routing through a 2D surface settles three more things at once: the loading overlay sets `#app { display: none }` on every frame parse, so anything sampling the live canvas on a timer records blanks (a `recordingActive` flag suppresses it as well, belt and braces); the split-view **pane separators are a DOM overlay** invisible to a canvas copy, and are redrawn onto the surface from the same `paneCssRect` percentages; and burning in a legend becomes plain `ctx` calls rather than `compositeLegend`'s PNG decode + re-encode per frame.
  - **`captureStream(0)`** — a *zero* frame rate, so the stream is driven entirely by `requestFrame()`. That is what a per-frame disk re-parse needs: a real-time capture would record whatever happened to be on screen when the clock ticked.
  - **The recorder awaits each frame.** `vtkRequestFrame` carries no correlation id and the host answers it `void postFrame(...)`, fire-and-forget on both sides, so overlapping requests race and the last parse wins. `pendingFrame` in `main.ts` is resolved at the end of the `vtkFrame` handler — the only point in the codebase that knows a requested frame is actually on screen. It also calls `TimelineControl.stopPlayback()` first (added for this): the play loop is a bare `setInterval` that would interleave its own requests.
  - **The CSP forbids the obvious blob code.** `default-src 'none'` with no `connect-src` means `fetch(URL.createObjectURL(blob))` is **blocked**; use `blob.arrayBuffer()`. No `media-src` either, so an in-webview `<video>` preview is impossible — the bytes go to the host and become a file. The video crosses `postMessage` as a **`Uint8Array`**, which structured clone carries natively, skipping the 33% inflation the base64 screenshot path pays.
  - **mp4 is not offered**: `MediaRecorder.isTypeSupported("video/mp4;codecs=h264")` is false in this Chromium, so the format list is vp9 → vp8 → default WebM, and the PNG sequence is the documented route to mp4 (the save message prints the exact `ffmpeg -i <stem>_%04d.png` line). Frame names are zero-padded so a glob and `%04d` agree — the same lexicographic trap `latestResultFile` exists to avoid.
  - PNG frames are **streamed to the host as they are captured** rather than accumulated in the webview, and buffered per-panel on the host until one save dialog at the end. The turntable spins the **focused pane** only, matching every other camera action; spinning all panes would destroy the comparison a split view exists for, and the panel says so.
  - `src/mediaExport.ts` is the hoist the roadmap asked for once a third copy appeared: `saveScreenshot` lived in both providers, near-identical but **not** byte-identical (the MDPA copy reached `fs` through an inline `require("node:fs")`), and now lives here with `saveVideo`/`saveFrameSequence`. Unit tests: `src/test/recordPlan.test.ts` (the pure plan — turntable closure, timeline ordering, clamping, padded names). The rest is verified through the screenshot harness, which unusually **can** drive this end to end: it is Chromium, so `MediaRecorder` works there and a real WebM comes back (checked by parsing the container — DocType `webm`, codec `V_VP9`, Tracks and Cluster present — since no ffprobe is available here). - **Split view** (`src/parser/paneLayout.ts` + `src/parser/paneView.ts` + the pane block in `webview/main.ts` + `#pane-chrome` in `webview/style.css`) — the **View ▾ ▸ Layout** rows put the mesh in 1, 2 or 4 viewports, each with its own **camera, field settings and clip plane**. - `src/parser/meshNormals.ts` — pure (no `vscode`/DOM/vtk) `computeMeshNormals(model)` behind Advanced ▸ **Face normals**: per-face centroid + unit normal for every surface cell and every volume-cell **boundary** face (interior faces deduped away, same rule as `surfaceTriangles`, which is what keeps the arrow field readable). Normals come from **Newell's method** — robust for a non-planar quad, where a cross-product of two edges is not. The point is finding an **inverted element**: winding decides both the arrow direction and the sign of the Jacobian, so a flipped cell is a solver error that is invisible in the numbers and obvious on screen. `inconsistent`/`inconsistentIds` are the machine-checkable half: two faces sharing an edge are consistently wound exactly when they traverse it in OPPOSITE directions, so the same directed edge seen twice means one is flipped — a **relative** test, so a uniformly inside-out mesh reports zero and the arrows stay the check for global orientation. Volume boundary faces get their winding from `volumeFaces`' tables rather than the file, so the test bites on surface meshes (shells, skins, imported STL/OBJ), which is where flipped elements actually come from. Reuses `cellCategory`/`cornerCount`/`volumeFaces`/`nodeIndexMap` from `writers/writerCommon.ts`; rendered by `main.ts` through `quiver.ts`'s `buildGlyphActor` (which gained an optional `flatColor` — normals are unit length, so a magnitude colormap would paint the whole field one hue), with the flipped cells overlaid in red. Unit tests: `src/test/meshNormals.test.ts`.
- `webview/sphereGlyph.ts` + `webview/spherePanel.ts` + the Spheres wiring in `main.ts` (toolbar button / `spheres` message, both providers) — **particle rendering**. A one-node cell has no extent, so `meshBuilder` puts it in vtkPolyData's `verts` and it draws as a fixed-pixel GL point; that is wrong for a peridynamics/DEM particle whose radius is physical data and must scale with the camera and the mesh. `sphereGlyph.ts` is modelled on `quiver.ts` (the other `vtkGlyph3DMapper` user): a UNIT `vtkSphereSource` + a 1-component `"radius"` scale array + `setScaleModeToScaleByMagnitude()` — `norm(tuple,1)` is the value itself, so the drawn radius is exactly `scaleFactor * radius`; no orientation array, and `setScalarVisibility(false)` unless colouring by radius (the scale array would otherwise double as the colour array and tint every particle by its own size). `spherePanel.ts` reuses the Mesh-size panel's `.meshsize-*` chrome: scale, tessellation (8/16/32/48, with a >50k-glyph warning), the **constant radius** prefilled from `defaultSphereRadius`, optional colour-by-radius, and a **Write to mesh** button posting `applyOp{op:"setElementRadius",mode:"absolute"}` — the bridge from a preview-only constant to a real, exportable field. `main.ts` owns the `sphere:glyphs` layer, anchors it via `coordOfPrep` so it follows the Deformed-shape warp like quiver, and **auto-enables it when `hasSphereRadius(model)`** (that IS the mesh, not an analysis overlay; a radius-less point cloud stays GL points so an ordinary point cloud does not silently become a ball pit). Two distinct base-layer concerns, deliberately separated: the layer is **excluded from the field-overlay set** and counted by `isOverlayLayer` so it neither triggers base dimming nor gets dimmed itself (wireframe spheres are unreadable), and `syncSphereBaseHiding()` HIDES the source one-node layers while the glyphs stand in for them (left visible they double-draw as points inside every sphere) restoring their prior visibility on teardown.
- `webview/beamGlyph.ts` + `webview/beamPanel.ts` + the Beams wiring in `main.ts` (Advanced ▸ **Beams…**) — **1D member rendering**, the line-cell counterpart of the sphere work. A line cell draws as a `setLineWidth(1.5)` polyline, i.e. screen-space pixels carrying no cross-section, so a tie rod and a girder look identical at every zoom. **The glyph construction differs from the sphere one in a way that matters and was measured against the bundled vtk.js, not assumed**: a beam needs a direction, a LENGTH, and a RADIUS independent of that length, and `vtkGlyph3DMapper` exposes ONE scale array — so `setScaleModeToScaleByMagnitude()` (which copies one magnitude into all three axes) cannot express it. `SCALE_BY_COMPONENTS` can: `Rendering/Core/Glyph3DMapper/Constants.js:10` scales x/y/z independently from a **3-component** array (`Glyph3DMapper.js:60-63` errors out loudly on any other width), `:125-148` post-multiplies the scale AFTER the rotation so it applies in the glyph's own local frame, and `:110-121`'s `OrientationModes.DIRECTION` maps **+X** onto the direction vector. Hence a unit `vtkCylinderSource{direction:[1,0,0], height:1, radius:0.5}` anchored at each cell's MIDPOINT, oriented by the endpoint vector and scaled by `[length, 2r, 2r]` is an exact endpoint-to-endpoint tube — no `vtkTubeFilter`, no hand-built geometry. Two traps, neither loud: **`setScaleFactor` is NOT the thickness knob here** (under SCALE_BY_COMPONENTS it multiplies all three components alike, so a panel "thickness ×2" would make every tube twice as LONG as its element and detach it from its endpoints — the multiplier is baked into components 1 and 2 and the factor stays 1, the exact opposite of `sphereGlyph.ts`), and `import "@kitware/vtk.js/Rendering/OpenGL/Glyph3DMapper"` is mandatory or the actor silently draws nothing. `beamPanel.ts` reuses the `.meshsize-*` chrome (thickness, constant radius prefilled from `defaultBeamRadius`, tessellation 6/8/12/24, colour-by-section, and a **Line conditions** opt-in) and deliberately ships **no "Write to mesh" button** — a beam's section belongs in `Properties`, which the writer copies verbatim, so an op could only write an Elemental field and create a second source of truth Kratos would not read. `main.ts` owns the `beam:glyphs` layer, anchors it via `coordOfPrep` so it follows the Deformed warp, excludes it in `isOverlayLayer`, and **auto-enables it when `beams().elementsWithSection > 0`** — a narrower gate than the spheres' by design. **Unlike the sphere layer it does NOT suppress the base line layers**, for two reasons: `registerGlobalOverlay` forces `setPickable(false)`, so suppression would make an entire beam frame uninspectable and unfindable (a frame, unlike a particle cloud, IS the model you click on), and SubModelPart layers mix line/surface/volume cells in one actor so a whole-layer suppression could not remove just the lines anyway. Leaving them is safe because a line lies on its tube's axis, i.e. strictly interior, so the depth test hides it wherever the tube is wider than about a pixel — and where it is not, the line is exactly the fallback wanted. Screenshot: `scripts/screenshots/capture-beams.mjs` → `images/beams.png` (it refuses to write a shot unless the rendering is actually on, since the failure mode is silent); drive it with `HARNESS_MESH=src/test/fixtures/mdpa/beam_frame.mdpa`.

`media/` is the only allowed `localResourceRoots` for the webview. The extension-host build **aliases `@loumalouomega/mmg-wasm` to its CJS entry** (`esbuild.js`): bundling the ESM entry breaks because its `import.meta.url`-based wasm lookup becomes `undefined` in a CJS bundle. **`pyodide` is `external`**: its loader locates the .wasm/.zip siblings relative to its own file, so it must never be bundled — dev resolves it from node_modules, the packaged extension from `dist/pyodide/`. **`@meshioplusplus/wasm` is `external` too** (with a `"@meshioplusplus/wasm/*"` entry as well, because `meshio.ts`'s `require.resolve("@meshioplusplus/wasm/package.json")` is a literal esbuild would otherwise resolve at build time). So there is nothing to alias: it ships verbatim under `dist/meshio/` and `meshio.ts` pulls it in with **`new Function("u", "return import(u)")`** — a real dynamic import that survives both esbuild's and tsc's CJS downlevelling (a literal `import()` would be rewritten to `require()` and fail). Should upstream ever publish a CJS build, this collapses to the mmg shape (alias + bundle + `locateFile`).

### Documentation screenshots
- `scripts/screenshots/build-harness.mjs` + `capture.mjs` — repeatable, VS-Code-free screenshot tooling: the harness replicates the provider's webview HTML (real `media/webview.js` + `media/style.css`, stubbed `acquireVsCodeApi`, Dark-Modern `--vscode-*` variables) and posts the same `model`/`opState`/`ptCatalog`/`ptCase` messages the host would (typed arrays tagged + revived across the JSON boundary). **`HARNESS_MESH=<path>`** loads any readable mesh instead of the default `double_arch.mdpa`, which has no fields at all and so cannot exercise a field-dependent panel (added for the time-series chart; `capture-time-series.mjs` computes the plotted series with the REAL `fieldSeriesScan` module against `example/VTK/`, so the numbers in the shot are the ones in the files). `HARNESS_SCENE=spheres` swaps the mesh for the issue-#63 particle fixture (plus `HARNESS_RADIUS=none` to keep it radius-less and `HARNESS_VARY=1` to grade the radii), captured by `capture-spheres.mjs` → `images/spheres.png`. `capture.mjs` drives it with playwright-core (chromium, `--use-angle=swiftshader` so WebGL renders headless; playwright deliberately NOT a repo dependency — see the script header) at 1680×1000 @2x dark to match the existing 3360×2000 `images/*.png`. Prereqs: `npm run compile && npm run build:tests && node scripts/screenshots/build-harness.mjs` (→ `out/screenshot-harness/`).
- **Per-operation screenshots** (`scripts/screenshots/capture-op.mjs` + `opFixtures.mjs` + `HARNESS_SCENE=op HARNESS_OP=<name>`) — one `images/op-<name>.png` per additional mesh operation for `doc/guide/mesh-editing.md`. `opFixtures.mjs` builds the scene meshes synthetically (`hexGrid`/`jitteredPlane`, seeded PRNG so runs are reproducible) rather than curating fixture files, and its **`sideBySide(before, after)`** places the pre- and post-operation meshes in one view via `translateCoords` + `mergeModels`, renaming each half's blocks to `Before`/`After` so the outline labels them — a lone "after" of a smoothed sheet is just a sheet and demonstrates nothing. `build-harness.mjs`'s `buildOpScene(op)` runs the real op module for each and returns the model + the history label to show in the Edit section; geometry/topology ops get the side-by-side, field-producing ops (`partition`/`fieldCalc`/`averageField`) get the single result plus the Field panel opened on the new variable. `capture-op.mjs` is one parametrized script over an `OPS` table (subcategory to expand, `data-op` form, `field` key, `inputs` to fill the form with the *same* parameters `buildOpScene` used so the visible form matches the visible result, `nodeIds`/`wireframe` toggles), tilts to a three-quarter view via the nav-control rotate buttons, and **fails loudly** rather than writing a misleading shot if the Field panel didn't land on the expected variable or the history row is missing. Run all with `NODE_PATH=/tmp/pw/node_modules node scripts/screenshots/capture-op.mjs`, or one with a trailing op name.

### Packaging & CI
- `.github/workflows/package.yml` builds a `.vsix` on every `v*` tag push and creates a GitHub Release with it attached. Uses `./node_modules/.bin/vsce` (not `npx vsce`) to ensure the `@vscode/vsce` version from `devDependencies` is used.
- `vscode:prepublish` runs the production esbuild before `vsce package`.
- `.github/workflows/ci.yml` runs `npm run typecheck` + `npm test` on every push to `master` and on PRs.
- **`CHANGELOG.md`** (Keep a Changelog format) must gain a new `## [x.y.z] - YYYY-MM-DD` entry (plus its compare-link footnote) whenever `package.json`'s `version` is bumped for a new `v*` tag — do this in the same change that bumps the version, before the tag is pushed. Summarize the notable changes since the previous tag (feature PRs merged, not every dependency bump — dependency-only releases can say so briefly).
