# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run compile        # dev build (includes source maps)
npm run package        # production build (minified, no source maps)
npm run typecheck      # type-check only — never use tsc to emit shipped code
npm test               # compile tests then run with Node's built-in test runner
npm run build:icons    # regenerate src/toolbarIcons.ts from icons/tikz-ui/*.tex (needs pdflatex + pdftocairo)
npm run install-ext    # build + copy into ~/.vscode-server/extensions/ (bash install.sh)
npm run reinstall      # bump patch version, package a .vsix, install via `code --install-extension`, prune stale versions (bash scripts/reinstall-local.sh) — also available as the "Reinstall extension (local/Remote-SSH)" VS Code task
npm run mcp            # run the standalone MCP server (node dist/mcpServer.js; needs a compile first) — register with: claude mcp add kratos-mdpa -- node <abs repo>/dist/mcpServer.js
```

**esbuild owns all emit** — `tsc` is only for type-checking and test compilation. Do not run `tsc` to build the extension.

To run a single test file:
```bash
npm run build:tests && node --test out/test/mdpaParser.test.js
```

The documentation site is a **separate, isolated npm package** under `doc/` (its own `package.json`/`package-lock.json`, `"type": "module"`) so VitePress never touches the extension build or the packaged `.vsix`. Run its commands from inside `doc/`:
```bash
cd doc && npm install       # first time only
npm run docs:dev            # local dev server with HMR
npm run docs:build          # production build → doc/.vitepress/dist (fails on dead links)
npm run docs:preview        # serve the built site
```

## Architecture

**MCP server sync rule**: `src/mcp/tools.ts` mirrors the extension's mesh/problemtype capabilities as MCP tools. Whenever an extension feature is added or modified — a new/changed op in `operations.ts`, a new mesh format/writer, a new mesh inspection/quality capability, a problemtype-pipeline change, a new sidebar/palette action — update the MCP server in the same change: the tool surface in `src/mcp/tools.ts`/`src/mcp/register.ts`, its tests in `src/test/mcpTools.test.ts`, and the tool tables here and in README.md. (The Flowgraph embedding is deliberately **UI-only** — an interactive iframe editor with no headless equivalent — so it is intentionally **not** exposed as an MCP tool; the `flowgraph` builtin still appears via `problemtype_list`/`problemtype_describe`.)

**Flowgraph embedding** (`src/flowgraphServer.ts` + `src/flowgraphController.ts` + `webview/flowgraphPane.ts` + `src/flowgraphMessages.ts` + `flowgraph-bridge/vscode-bridge.js` + `src/problemtype/builtins/flowgraph.ts`): the **Flowgraph (node editor)** built-in problemtype (`view: "flowgraph"`) embeds the AGPL-3.0 [`@kratos-flowgraph/flowgraph`](https://www.npmjs.com/package/@kratos-flowgraph/flowgraph) litegraph editor. It is a Node/Express+EJS server app, not an importable browser bundle, so it is **run, not bundled**: `flowgraphServer.ts` (a third esbuild entry → `dist/flowgraphServer.js`) serves flowgraph's copied `public/`+`views/` (in `dist/flowgraph/`) on an ephemeral port — its own tiny Express wrapper (no `config` package, no `/upload_json`/`/run_simulation` routes; the EJS engine is registered explicitly via `app.engine("ejs", ejs.__express)` so esbuild bundles it past Express's dynamic `require`). `flowgraphController.ts` (the only new vscode-importing host module; one shared, ref-counted instance owned by `extension.ts`, injected into the MDPA provider) forks the server on the first `flowgraphStart`, resolves `vscode.env.asExternalUri` and hands the webview a `flowgraphReady{url,origin}`; the webview embeds it in an `<iframe>` in a split pane (`webview/flowgraphPane.ts`, split of `#viewport` into `#vtk-sub` + `#flowgraph-pane`, horizontal default, orientation toggle). Because the iframe is a **separate http origin** (its own absent CSP), flowgraph's jQuery/CDN/eval run unmodified; the webview CSP only relaxes `frame-src` (scoped to `http://localhost:*`/`127.0.0.1:*`/`https:` since the tunneled origin is resolved after the CSP is baked). The **two-way ProjectParameters bridge** rides cross-origin postMessage (`flowgraphMessages.ts` is the shared contract; `vscode-bridge.js`, injected into the served page, speaks the iframe half): on open, `PtController.getProjectParametersJson()` (compute-only, no disk writes) seeds the graph via `graph.configure_project_parameters`; flowgraph's Generate posts the exported ProjectParameters back, which `PtController.applyExternalProjectParameters` writes next to the mdpa. MDPA-provider only (problemtypes are MDPA-only); the VTK provider ships the same (inert) chrome so the shared `webview/main.ts` stays uniform.

The extension has two completely separate runtimes that communicate only via `postMessage`:

### Extension host (Node.js, `src/`)
- `extension.ts` — registers two custom editors (`kratos.mdpaPreview` for `.mdpa`, `kratos.vtkPreview` for the mesh formats `.vtk`/`.vtu`/`.vtp`/`.vti`/`.vts`/`.vtr`/`.vtm`/`.stl`/`.obj`/`.ply`) and commands. A shared `postToActive` helper forwards panel-level commands (reset camera, field, screenshot, etc.) to whichever provider currently has an active panel. `contributes.keybindings` gates the reference chord set (Ctrl+O/S/Shift+S/E and Ctrl+Alt+S/O/P) to the two preview tabs via `activeCustomEditorId`, so no global binding is clobbered. The `kratos.mesh.*` commands (open/save/saveAs/export) route through `dispatchMenu` (which calls each provider's `dispatchMenu`) for Command-Palette parity with the in-webview File menu. `activate` ends with a fire-and-forget `showWhatsNewIfNeeded(context)` (see `src/whatsNew.ts`); activation is gated on `onStartupFinished` so the check runs on every session.
- `src/whatsNew.ts` (vscode glue) + `src/whatsNewCore.ts` (pure) — the version-gated **"What's New"** popup. On startup `showWhatsNewIfNeeded` compares `context.extension.packageJSON.version` against the `"lastShownVersion"` globalState key (same one-time-gate pattern as `meshExport.ts`'s overwrite warning): on an upgrade it reads root `CHANGELOG.md` (`context.extensionPath`, `fs.existsSync`-guarded), shows the entries newer than the last-seen version in a static (no-script) `createWebviewPanel`, then advances the marker; a fresh install (undefined marker) is set silently with no popup, and a downgrade/missing-changelog just advances the marker. Honors the `kratos.showWhatsNew` setting (default true). `showWhatsNewCommand` backs the manual **Kratos MDPA: Show What's New** command (`kratos.mdpa.whatsNew`) and shows the full changelog. `whatsNewCore.ts` is the vscode-free, Node-testable core: `parseChangelog` (Keep-a-Changelog `## [x.y.z] - date` sections, excluding the intro + trailing link-def block), `compareSemver`, `selectNewEntries` (strictly-newer; `[]` for undefined lastShown), and `changelogToHtml` (HTML-escaped mini-markdown → bullets/`**bold**`/`` `code` ``/`[text](url)` links, never a `<script>`). Intentionally **not** an MCP tool — UI-only, like the Flowgraph embedding. Unit tests: `src/test/whatsNewCore.test.ts`.
- `src/meshExport.ts` — shared host-side File-menu handlers used by both providers: `openMesh` (showOpenDialog → `vscode.openWith` the matching viewType), `saveMesh` (re-serialise to the source's own format and overwrite it, one-time `globalState`-gated overwrite warning), `saveMeshAs`, `exportMesh`, `exportSubModelPart` (slices one SubModelPart out via `extractSubModelPart` and writes it to a chosen format), `exportSkin(ctx, targetExt?)` (extracts the boundary via `extractSkinModel` — `extractSkin.ts` — and writes it; `showQuickPick`s a format when `targetExt` is omitted, driving the Advanced-menu **Export skin…** entry / `kratos.mesh.exportSkin`), `pickMergeMeshFile()` (a `showOpenDialog` for the mergeMesh sidebar form's file field, listing `.mdpa` first — see `pickMeshFile`/`mergeMeshPicked` in the message protocol table), and `runMenu(msg, getCtx, extContext)` routing a `MenuMessage`. All serialization funnels through `serializeModelToPath`; the webview only posts the command (`menuOpen`/`menuSave`/`menuSaveAs`/`menuExport`/`menuExportPart`/`menuExportSkin`, plus `menuSaveProblem`/`menuLoadProblem` routed to `src/problemArchive.ts` — load, like open, needs no ExportContext). Each provider caches the last parsed model (`lastModel`) and registers a per-panel `activeMenuHandler` so palette commands reach the active preview; `ExportContext.ops` carries the applied edit ops for Save problem. (Mesh operations no longer live here — see `src/opHistory.ts` / `src/parser/operations.ts`.)
- `src/problemArchive.ts` — host side of File ▸ **Save problem… / Load problem…** (`menuSaveProblem`/`menuLoadProblem`, also the `kratos.problem.{save,load}` palette commands — load needs no active panel). Save collects via the shared `collectProblemFiles` and writes `<stem>.kratosproblem.zip`; Load picks a zip + destination folder, extracts (modal overwrite confirm; unsafe entry names skipped; the manifest itself is not extracted), registers the parsed ops recipe in the module's **pending-ops map** and opens the mesh with `vscode.openWith` in the matching preview. Both providers call `takePendingOps(fsPath)` right after `history.setBase` and replay via their local `replayWithProgress` (the same cancellable notification the `loadOps` path uses); the case state is restored by the panel's normal `<stem>.kratoscase.json` loading.
- `src/problemFiles.ts` — shared vscode-free disk collector `collectProblemFiles(meshFsPath, opsJson?)`: the mesh's pristine bytes + the caller-supplied recipe text (stored as `<stem>.ops.json`) + `<stem>.kratoscase.json` + the generated case files that exist (ProjectParameters.json, MainKratos.py, `<stem>_case.mdpa`, and the materials file(s) found by `materialsFileNamesFrom`). Used by `problemArchive.ts` (live-history ops) and the MCP `problem_pack` tool (recipe file ops).
- `src/parser/problemZip.ts` — pure problem-archive core: the `kratosproblem.json` `ProblemManifest` (mesh/ops/case/generated entry names), `buildProblemZip`, `parseProblemZip` (recipe-style tolerance — a missing/malformed manifest degrades to extension-based `detectMeshEntry` with warnings, ops fall back to the conventional `<stem>.ops.json`), `isSafeEntryName` (zip-slip guard, same policy as the .vtm child-path check) and `materialsFileNamesFrom` (deep search of ProjectParameters.json for `materials_filename` values — the name is problemtype-specific). Tests: `src/test/problemZip.test.ts`.
- `src/parser/zip.ts` — pure, dependency-free ZIP writer/reader on `node:zlib` (`createZip`/`readZip`): store + deflate, UTF-8 names, CRC-32 verified; encrypted/ZIP64/other-method archives rejected with descriptive errors. Interop-tested against a committed Python-`zipfile` fixture (`src/test/fixtures/zip/`). Tests: `src/test/zip.test.ts`.
- `src/opHistory.ts` — host-side **operation history** (undo/redo/partial-revert + JSON recipe I/O) shared by the Edit + Mesh Modification sidebar sections. `OperationHistory` is a **replay-from-base** stack: `setBase(model)` (called on every parse/frame load — so history resets on reparse/frame change), **async** `applyNew(rec)` (truncates the redo tail, records unless the op is a noop), `undo`/`redo`/`clear`/`revertTo(n)`, **async** `current()` = `replayOpsAsync(base, ops[0..cursor))`, `load(records)`, and `state()` for the webview. Prefixes ending in an MMG op are **snapshotted** (`Map<prefixLen, OpApplied>`) so undo/redo of later ops never re-runs the remesher; `current()` replays from the nearest snapshot ≤ cursor (snapshots past the cursor are invalidated on truncation; cleared on `setBase`/`load`/`clear`, so loading a recipe re-runs MMG). Op params are entered in the sidebar (interactive forms) and ride along on the `applyOp` message — the host builds the record with `opRecordFromMessage` (no native prompts). `saveOps`/`loadOps` are the showSaveDialog/showOpenDialog + `fs` recipe writers/readers. Each provider owns one instance; `lastModel` always equals `current().model`, so File ▸ Save/Export serialize the edited mesh. Pure replay/dispatch/JSON live in `src/parser/operations.ts`.
- `src/parser/operations.ts` — pure (no `vscode`/DOM/vtk) operation core: the serializable `OpRecord` union (`linearToQuadratic` | `removeOrphanNodes` | `mergeNodes{tolerance}` | `scale{sx,sy,sz}` | `translate{dx,dy,dz}` | `rotate{axis,angle,cx?,cy?,cz?}` | `deleteSubModelPart{path}` | `renameSubModelPart{path,newName}` | `writeMeshSizeFields{target}` (append `NODAL_H`/`ELEMENT_H` fields — see `meshSize.ts`) | `setElementRadius{value,mode,target?}` (set/scale the sphere-element `RADIUS` — see `setElementRadius.ts`) | `remesh{mode,factor?,hsiz?,sizeExpr?,sizeParts?,hmin?,hmax?,hausd?,hgrad?,angleDetection?,nosurf?,noinsert?,noswap?,nomove?,module?}` (mode `expr` carries `sizeExpr` + optional per-SMP `sizeParts` — see `sizeExpr.ts`/`remesh.ts`) | `levelset{variable,isovalue?,isosurf?,+tuning}` | `smooth{method?,iterations?,lambda?,mu?,fixBoundary?,preserveFeatures?,featureAngle?,guardInversion?}` (meshio++ Taubin/Laplacian smoothing as an **oracle** — see `smoothMesh.ts`) | `reorder{method}` (`rcm`\|`morton`\|`hilbert` — see `reorderMesh.ts`) | `partition{nparts,method?,createParts?}` (attaches an Elemental `PARTITION_INDEX` — see `partitionMesh.ts`) | `linearize` (inverse of `linearToQuadratic` — see `linearize.ts`) | `refine{levels?}` (uniform subdivision — see `refineMesh.ts`) | `simplexify` (hex/wedge/pyramid/quad → tets/triangles — see `simplexify.ts`) | `crop{kind:"bbox"|"plane",…,mode?}` (see `cropMesh.ts`) | `fieldCalc{expr,location,output}` / `averageField{variable,direction,target?,output?}` (see `fieldCalc.ts`) | `mergeMesh{path,weld?,tolerance?,name?}` (see `mergeMesh.ts`)), `applyOp(model, rec)` (sync ops only — **throws** for the async ops, MMG and Group-A meshio++ oracles alike), `applyOpAsync`/`replayOpsAsync` (run everything incl. MMG and the meshio++ oracles; take `MmgRunOptions {onProgress?, signal?}` — cancellation/worker failure surfaces as a noop outcome with a message, and an aborted signal stops a replay between ops), the swappable **`MmgRunner`** (`configureMmgRunner` — default runs in-process for tests; the extension installs the worker client), `isAsyncOp(op)` (backed by an `ASYNC_OPS` Set — `remesh`/`levelset`/`smooth`/`reorder`/`partition`/`mergeMesh` — drives the providers' progress UI + history snapshotting), `opRecordFromMessage(msg)` (validates a raw `applyOp` webview message + its sidebar params into an `OpRecord`), `OP_LABELS`, and `serializeOps`/`parseOpsJson` (versioned JSON recipe with unknown-op/param validation → warnings). `mergeMesh`'s `path` is dispatched to `parseMdpa` for a `.mdpa` file and `parseMeshFile` (meshFileParser.ts) for everything else — `pickMergeMeshFile` (meshExport.ts) lists `.mdpa` first in its dialog, so the extension-specific format has to be handled explicitly rather than falling through to the *other-formats* dispatcher. Node-testable; drives `OperationHistory`. Unit tests: `src/test/operations.test.ts`.

## Additional mesh operations (`src/parser/{smoothMesh,reorderMesh,partitionMesh,linearize,refineMesh,simplexify,cropMesh,fieldCalc,extractSkin,mergeMesh,cellDecomposition}.ts`)

Surface meshio++'s bundled operations plus a few native ones, added to the Mesh Modification sidebar / `mesh_transform` / `mesh_extract_skin` on top of the original op set. The instruction that shaped this: **where an operation conflicts with something the extension already does natively, keep the native one** (ruled out `transform`, `clean`, `convertCells "elevate"`, `attachQuality`, `stats`, `isosurface`, `split by regions`, `dataInfo` — all superseded by existing features).

The finding that shapes the split into two groups: routing our model through `modelToMeshio`/`meshioToModel` is lossy — `propertyIds`, the Elements/Conditions/Geometries **kind** of a block, and every original entity id are gone on the way back. Two of the losses that originally motivated the split have since been closed and the rationale is **narrower than it was**: `modelToMeshio` now emits `regions`, so SubModelParts do cross (see below), and meshio++ 9.9.0's `*_components` maps fixed the boundary bug whereby **a vector field was silently corrupted by any operation that changes the point count** (a `(n,3)` array re-entered C++ as `(3n,1)`, failed the operation's `rows == num_points` test and took a pass-through branch, returning stale values of the wrong length). What remains — kinds, property ids, entity ids — is enough on its own, so the split stands. Hence:

- **Group A — meshio++ as an oracle** (`smoothMesh.ts`, `reorderMesh.ts`, `partitionMesh.ts`): the wasm computes something whose shape survives losslessly — moved coordinates (same count/order), a node permutation, or a per-cell label array — and we apply that result onto our OWN `MdpaModel`; meshio++'s returned mesh is never adopted. All three are async (`ASYNC_OPS`), inheriting the MMG-style progress/cancel UI automatically.
  - `src/parser/smoothMesh.ts` — `smoothModel(model, params, diagnostics)`: Taubin (default, shrink-free) or Laplacian smoothing via meshio++'s `smooth`. Sends geometry only (no fields/regions — nothing else is read), copies the moved coordinates back onto a clone, and **throws if the returned point count doesn't match** (a safety invariant — smoothing must never add/remove points). Reports `numNodesMoved`/`maxDisplacement`/`numSkippedInversion`. Unit tests: `src/test/oracleOps.test.ts`.
  - `src/parser/reorderMesh.ts` — `reorderModel(model, method, diagnostics)`: `rcm` (bandwidth), `morton`/`hilbert` (spatial locality) via meshio++'s `reorder`. Never touches the returned mesh — applies the returned `nodePermutation` (old→new index map) directly to `nodeIds`/`coords`/connectivity/SubModelPart id lists/field ids natively, and reports `bandwidthBefore`/`bandwidthAfter` via `computeBandwidth`. Unit tests: `src/test/oracleOps.test.ts`.
  - `src/parser/partitionMesh.ts` — `partitionModel(model, params, diagnostics)`: domain decomposition via meshio++'s `partitionLabels`, attached as an Elemental `PARTITION_INDEX` field (a real Kratos variable) covering every cell kind (Elements/Conditions/Geometries — `KIND_ORDER`), optionally also creating one `Partition_N` SubModelPart per part (`createParts`). **The WASM build has no KaHIP**: `"kahip"` throws by name, `"auto"` resolves to `"sfc"` — only the Hilbert space-filling-curve method is available, so parts are balanced by cell count, not edge cut. Unit tests: `src/test/oracleOps.test.ts`.
- **Group B — native**, reusing primitives the extension already owns (edge/face tables, block/field slicing, `sizeExpr.ts`'s evaluator) rather than repairing a lossy round-trip:
  - `src/parser/cellDecomposition.ts` — the volume/surface→tetrahedra/triangle decomposition tables (`TET_TETS`/`PYRAMID_TETS`/`WEDGE_TETS`/`HEX_TETS`/`TRI_TRIS`/`QUAD_TRIS`, `decompositionFor(cellType)`), extracted out of `isoSurface.ts` (which used them for marching tetrahedra) so `simplexify.ts` can reuse the identical tables.
  - `src/parser/linearize.ts` — `linearize(model)`, the missing inverse of `linearToQuadratic.ts`: drops mid-side nodes via a `QUADRATIC_TO_LINEAR` lookup, renames blocks/types/strides, then `removeOrphanNodes`. Unit tests: `src/test/linearize.test.ts`.
  - `src/parser/refineMesh.ts` — `refineModel(model, levels=1)` (capped at `MAX_LEVELS=4`): uniform subdivision (line→2, tri/quad→4, tet/hex/wedge→8) via per-cell-type local-index child templates (`childTemplates(cellType)`), sharing `linearToQuadratic.ts`'s shared-edge/face dedup approach (`nodeFor(parentNodeIds)` keyed by sorted-parent-id string) so a shared edge/face midpoint is one node, never a hanging node. Interpolates Nodal fields exactly at new nodes (mean of generating parents), replicates Elemental/Conditional fields to children, extends SubModelPart node membership. Unit tests: `src/test/refineMesh.test.ts` (incl. rigorous tetrahedral-decomposition volume-conservation checks for hex/wedge/tet).
  - `src/parser/simplexify.ts` — `simplexifyModel(model)`: hex→6 tets, wedge→3, pyramid→2, quad→2 tris (via `cellDecomposition.ts`); the first child keeps the parent's id, siblings get fresh ids past `maxEntityId(model)`, replicating Elemental/Conditional fields and SubModelPart membership. A mesh with nothing to split (already all-simplex) is a noop with `skippedBlocks` naming why. Unit tests: `src/test/simplexify.test.ts`.
  - `src/parser/cropMesh.ts` — `cropModel(model, params)`: keeps cells whose nodes are inside a bbox or on the normal side of a plane (`mode: "all"|"any"`), reusing `sliceBlock`/`sliceField` (exported from `subModelPartExtract.ts`) to rebuild blocks/fields around the survivors, narrows SubModelPart node lists by the inside-test (not cell survival) and entity lists by the keep sets, then `removeOrphanNodes`. Throws if nothing survives or a plane's normal is the zero vector. Unit tests: `src/test/cropMesh.test.ts`.
  - `src/parser/fieldCalc.ts` — `fieldCalcModel(model, params)`: a new field from a formula evaluated by `sizeExpr.ts`'s own recursive-descent parser (never `eval` — expressions arrive from saved recipes, i.e. untrusted disk input), with the scope extended from the MMG sizing names to `x,y,z` plus every existing field at the target location (a vector field split into `name_x`/`name_y`/`name_z`; **all lowercased**, working around `sizeExpr.ts`'s own lowercasing of bare identifiers, so an UPPERCASE Kratos variable like `TEMP` is still reachable). A bad formula is rejected before anything is applied; NaN (an unavailable field) drops the row, Infinity (e.g. `1/0`) is kept. `averageField(model, params)` moves a field between Nodal and Elemental/Conditional by averaging: `nodalToElemental` = mean over a cell's own nodes, `elementalToNodal` = mean over incident cells (uniform, not measure-weighted). Unit tests: `src/test/fieldCalc.test.ts`.
  - `src/parser/extractSkin.ts` — `extractSkinModel(model)`: the boundary skin of the volume cells (+ any pre-existing surface cells) as a standalone `MdpaModel`, via the same boundary-face walk as `meshNormals.ts`/`writerCommon.ts`'s `surfaceTriangles` (a face seen by exactly one cell is boundary). Ships as an **export** (like `extractSubModelPart`), never an in-place edit — a skin is a different mesh with fresh entity ids. SubModelParts narrow to node membership only (element/condition ids cannot follow — the new blocks have no correspondence); only Nodal fields carry over. Native rather than meshio++'s `extractSurface`/`extractSkin` because those drop every region on the way out. Reachable from the Advanced toolbar menu (**Export skin…**) and the `mesh_extract_skin` MCP tool. Unit tests: `src/test/extractSkin.test.ts`.
  - `src/parser/mergeMesh.ts` — `mergeModels(base, other, params)`: appends a second mesh's nodes/cells with id offsetting (same approach as `vtkMultiblock.ts`'s `parseVtm`), concatenating same-kind+variable fields, wrapping the merged-in geometry in a new SubModelPart, optionally welding coincident nodes across the seam by calling the existing `mergeNodes()` on the concatenated result. The `mergeMesh` op is async (reads a second file — see `operations.ts`'s `parseMergeSource`) and reports a missing/unreadable file as a noop rather than throwing. Unit tests: `src/test/mergeMesh.test.ts`.
- **Group C — researched and deliberately excluded**: **Decimate** (quadric-error surface simplification) is the one selected-but-excluded operation — it rewrites topology with no JS-reachable back-map, drops `side` regions, forces all-triangle output, refuses volume meshes, and blends every field (including integer tags) as float64; doing it right needs a full fidelity/round-trip-repair layer, so it is deferred to a possible future "generate a decimated surface **copy**" export where lossiness is the stated intent. Slice/isosurface-as-real-meshes and `interpolate`/`diff`/`convertSurfaceOps` were also researched and left out — no viewer use case not already covered by Clip / the Field panel's iso overlay / `extractSubModelPart`.

Cross-cutting plumbing shared by every op above: `webview/meshMod.ts`'s `SYNC_BUILDERS`/`ASYNC_BUILDERS` registries (keyed by `data-op`, so adding an operation's sidebar wiring is a markup line + a builder entry, not a bespoke click handler) and its generalized `setMeshModProgress()` (walks `asyncApplyButtons()` — `.edit-apply-mmg[data-op]` — rather than a hard-coded per-op ternary, so a third/fourth async op needs no changes here). `src/webviewChrome.ts`'s `SIDEBAR_HTML` carries one `.edit-form` per operation, grouped into six collapsible `.sb-subsection` subcategories (**Element order & topology**, **Remeshing (MMG)**, **Smoothing & renumbering**, **Selection & combination**, **Fields**, **Sphere elements** — collapse wiring in `webview/sidebar.ts`, each header carrying its own `cat*` icon from `toolbarIcons.ts`) rather than one flat list; `ADVANCED_MENU_HTML` carries **Mesh Size**, **Spheres…**, **Face normals** and **Export skin…**. `src/mcp/register.ts`'s `OPS_HELP` documents every op as prose for `mesh_transform` (no zod schema per op — validated at runtime by the same `opRecordFromMessage` the webview uses).
- `src/parser/remesh.ts` — **MMG remeshing** via `@loumalouomega/mmg-wasm` (MMG v5.8.0 as WASM; async, Node-testable, no `vscode`/DOM). `remeshModel(model, params)` — modes `factor` (per-node scalar metric = mean incident-edge length × factor), `hsiz` (`DPARAM_hsiz`), `optimize` (`IPARAM_optim`), and **`expr`** (per-node target size from a user formula via `expressionSizes()`: scope `h` = Kratos NODAL_H, the **global** NODAL_H stats `mean/std/min/max/median/q1/q3/iqr` (from `computeMeshSize`), and coords `x,y,z`; per-SubModelPart `sizeParts` overrides swap the expression — not the stats — for a part's nodes, first match wins, resolved on the *input* mesh via `origIds` since MMG renumbers; a non-positive/NaN result keeps the node's current size + warns; a bad formula fails fast before MMG runs); tuning `hmin/hmax/hausd/hgrad`, `angleDetection` (≤0 → `IPARAM_angle` off), `nosurf/noinsert/noswap/nomove`. `levelsetModel(model, params)` — nodal field (vector → magnitude, full coverage required) → `h.ls` scalars, `IPARAM_iso`/`isosurf` + `DPARAM_ls`, plus a **size-preserving metric in `h.met`** (without it the split re-densifies the whole mesh); output regroups into `MMG_Domain_Inside`/`_Outside` + `MMG_Interface`(`_Edges`) blocks, and every ls-created region is **also emitted as a top-level SubModelPart** of the same name (node closure included; paths de-duplicated with `_2`… suffixes against surviving parts from an earlier split). Module auto-detect: tets → `mmg3d` (prisms pass through; tris/quads/edges = boundary), else planar (z ≈ const) → `mmg2d` (2-double coords, z restored) else `mmgs`; hex/pyramid/quadratic/point-only meshes → noop + message. **Ref encoding is how blocks + SubModelParts survive**: each cell gets a dense ref for its (block, sorted SMP-path list) signature; the harvest regroups by ref. Caveats baked in: MMG tags internally-created boundary faces with the adjacent domain cell's ref, so a ref only maps back when the cell family matches (ref 0 / family mismatches are dropped as internal boundary), and level-set refs start at 100 because ls mode rewrites domain refs to MG_MINUS/MG_PLUS (2/3). Node + entity ids are freshly renumbered; SMP node lists = connectivity closure of their cells; fields dropped with a warning; `free(h)` in `finally`; `IPARAM_verbose` −1. **`hausd` defaults to 0.5% of the bbox diagonal** when not given (MMG's built-in default is the ABSOLUTE 0.01 — it explodes on large domains: the bunny level-set went from 464 s + failure to 23 s); MMG return codes ≠ SUCCESS/LOWFAILURE and empty harvests (`np ≤ 0`) throw instead of surfacing as cryptic getter errors. `configureMmg(opts)` injects Emscripten overrides once — `extension.ts` passes `{ wasmBinary: readFileSync(__dirname/mmg-core.wasm) }` at activation; plain Node (tests) self-resolves. **Progress**: `remeshModel`/`levelsetModel` take an optional `onProgress(message)` — stage messages plus MMG's own log (Emscripten `print`/`printErr` route through a module-level listener fixed at initialize time; `IPARAM_verbose` 3 when a callback is given, −1 otherwise; banner noise filtered by `progressLine`). - `src/parser/meshioConvert.ts` — pure `meshioToModel(mesh, diagnostics)` / `modelToMeshio(model, diagnostics, opts?)`. Read: flat points+`dim` → interleaved xyz (z=0 when 2D), cells re-flattened into VTU-style (types, end-offsets, 0-based conn) and handed to **`buildBlocksFromOffsets`** rather than built directly — meshio's blocks are already homogeneous, but the helper also fans `polygon` into triangles, does 0→1-based, and returns the `expansion` map that is the only correct way to realign `cell_data` across that split (block names are restored afterwards from a `(vtkCellType, stride)` map, so layers read `triangle`, not `VtkCell_5`). `cell_data` is indexed via a `kept[]` list because meshio's arrays align with the **original** `mesh.cells` — a skipped block in the middle would otherwise shift every value. **Ragged (polygon/polyhedron) blocks** (`MeshioPolygonCellBlock`/`MeshioPolyhedronCellBlock`, crossing the wasm boundary since meshio++ 8.7.0 — previously rejected there outright) are detected via `isRectangularCellBlock` and diagnosed-and-skipped with an accurate count from `meshioBlockRowCount`, rather than silently contributing zero cells (`nodesPerCell` is `undefined` on a ragged block, so treating it as rectangular would compute `nCells=0` and drop it with no diagnostic — worse than the pre-8.7.0 wasm throw). `sanitizeVariable` is load-bearing: `mdpaWriter.ts` emits variable names verbatim, so gmsh's injected `gmsh:physical` (kept — it *is* the physical-group id) becomes `gmsh_physical`. Read also honours the **`*_data_components`** maps (meshio++ >= 9.9.0, `{name: k}`, emitted only for non-scalars — absent means one component) in preference to dividing an array's length by the entity count, which is what catches an array whose declared width and length disagree; and `exodus:time` is filtered out of the "Dropped field_data" diagnostic (`INTERNAL_FIELD_DATA_KEYS`) because every Exodus read carries it since 9.9.0 and it is not the user's data. Write reuses the writer layer wholesale (`buildCellLayout`/`point`/`cellFieldArray`); Elemental+Conditional collide in meshio's single `cell_data` namespace and get a kind suffix; and it emits **three things beyond geometry**, each needed by a format that would otherwise silently lose it: `point_data_components`/`cell_data_components` for every field with `components > 1` (without them a `(n,3)` array re-enters C++ as `(3n,1)` — the root cause of MED's write-then-fail-to-read and of the corrupted-vector-field behaviour in meshio++'s own operations), `regions` (see below), and the `exodus:attr:` namespace. Cells are grouped by **`(meshioType, stride, SOURCE BLOCK)`** rather than `(meshioType, stride)`, so each `EntityBlock` stays a block of its own on the way out (`LaidOutCell.blockName`, added to `writerCommon.ts` for this) — that is what makes the `Cell` region emitted for a block cover exactly one meshio block, which is Exodus's rule for recovering an `eb_names` entry, and it also stops an `Elements` and a `Conditions` block that happen to share a cell type from being fused. **`buildRegions`** emits one `kind:"cell"` region per emitted block (named after the `EntityBlock`) plus one `cell` + one `point` region per SubModelPart, walking children recursively: cell entries resolve through `layout.elementIdToCell`/`conditionIdToCell`/`geometryIdToCell` (the last added to `CellLayout` for this, since no field kind needs it), point entries through `nodeIndexMap`; entries are global block-major indices, ascending; `dim` comes from `cellCategory` when the cells agree and is `-1` otherwise; a part's node and cell regions deliberately share ONE name (MED/Abaqus key a group by name and the read path merges same-named regions back into one part), a nested part uses its dotted path (a `/` would reach an HDF5 group name in MED), and names are de-duplicated with a `_2`… suffix so two unrelated groups never merge. Measured: this makes SubModelParts survive an export to `.med` (families) and `.inp` (`*NSET`/`*ELSET`), and block names survive to `.exo`; **gmsh 4.1 writes no `$PhysicalNames` at all** for a mesh with no `gmsh:dim_tags`, so `.msh` export carries no groups (upstream gap, measured at 9.9.0). **Exodus per-element attributes** (meshio++ >= 9.3.0) are the sphere-radius carrier and get a rule of their own: on READ the `exodus:attr:` namespace is stripped before `sanitizeVariable`, so `exodus:attr:RADIUS` becomes plainly `RADIUS` (also a real Kratos variable, so a `.mdpa` export yields a `Begin ElementalData RADIUS` block) instead of the unusable `exodus_attr_RADIUS`; on WRITE `modelToMeshio`'s **`opts.exodusAttributes`** (set only for `fmt === "exodus"`, in `meshio.ts`) puts it back on every SCALAR Elemental/Conditional field. That is an **export-time rule, not model state** — no `MdpaModel` slot to keep alive through `remesh`/`levelset`/`linearToQuadratic`, and prefixing is strictly information-preserving because the Exodus writer DROPS all non-prefixed `cell_data`. Two details are load-bearing: (a) meshio++ NaN-fills the attribute for blocks that do not declare it, and `writerCommon`'s `num()` maps NaN to `"0"` — so `dropNonFinite` turns the field SPARSE at the read boundary (by value, not by block, since `buildBlocksFromOffsets` may already have merged several meshio blocks into one), and an all-NaN array is dropped entirely with a diagnostic rather than left as a permanently empty entry in the field pickers; (b) the write NaN-fills the cells a sparse field does not cover (via `coveredCells`, since `cellFieldArray`'s 0 is indistinguishable from a real 0) — that is what makes meshio++ omit a block's `attrib{k}` entirely and a partly-attributed file round-trip unchanged. A **vector** field is never prefixed, but since 9.9.0 that no longer loses it: an Exodus attribute is one value per element (upstream now RAISES rather than truncating, testing the product of all trailing dimensions), while ordinary `cell_data` is written as an element VARIABLE and survives whole — so the old "written as ordinary cell data (which the Exodus writer drops)" diagnostic is gone. The caveat that stays ours to know: upstream warn-and-skips an unprefixed `cell_data` array that does not cover EVERY block, so a sparse vector field can still be lost. `mesh.regions` (meshio++ >= 8.1.0) is handed to `meshioRegions.ts`, whose SubModelParts and materialized side-facet Conditions blocks are appended before `finalizeModel`. Unit tests: `src/test/meshioConvert.test.ts` (no wasm needed).
- `src/parser/meshioRegions.ts` — pure (no `vscode`/DOM/wasm) **named regions → SubModelParts**. A meshio++ `Region` (since 8.1.0, riding on the mesh object so `readMesh` carries it with no extra call) is the uniform spelling of a gmsh physical group, an Abaqus `*NSET`/`*ELSET`/`*SURFACE`, an Exodus block or set, and — since meshio++ 9.6.0 — a **MED** `FAS`/`GRO` family group (`Point` from `NOEUD`, `Cell` from `ELEME`; `Side` has no MED equivalent): `{name, kind: "point"|"cell"|"side", dim, tag, entries}`. `regionsToParts(...)` maps **point** → `nodeIds` (index+1, matching `finalizeModel`'s synthesized ids), **cell** → `elementIds`, and **side** → materialized boundary facets emitted as `kind:"Conditions"` `EntityBlock`s (one per region, split per facet type only when a region spans two) plus the matching `conditionIds` — so an Abaqus `*SURFACE` is a visible, framable layer and a `.mdpa` export yields real Kratos Conditions. Regions **sharing a name merge into one part** (Abaqus routinely declares an `*NSET` and an `*ELSET` under one name; a gmsh name may be declared per dimension). Two index shifts have to be undone for cell/side entries, which are *global block-major cell indices over the ORIGINAL meshio blocks*: a block whose type has no VTK equivalent is dropped yet still consumes global indices, and `buildBlocksFromOffsets` may fan one cell into several entities — `expansion` (the same array that realigns `cell_data`) is what makes the second recoverable. The `FACETS` table mirrors upstream `detail/cell_faces.hpp` (3D) and `detail/cell_edges.hpp` (2D) — **the facet ORDER is what `side` regions index**, so a reordering upstream silently mislabels every side set. Unit tests: `src/test/meshioRegions.test.ts` (pure mapping + gmsh/Abaqus fixtures through the real wasm, incl. a geometric check that every materialized facet is a boundary edge of exactly one cell).
- `src/parser/meshio.ts` — the meshio++ loader + MEMFS I/O (no `vscode`; Node-testable). `loadMeshio()` returns a **fresh instance per operation** — `ALLOW_MEMORY_GROWTH=1` means a memoized one would pin the high-water mark of the largest mesh ever opened for the host's lifetime (the same reasoning behind MMG's per-run worker), and it needs no `FS.unlink` bookkeeping. `readMeshioModel(mainName, files, ext, format?, timeStep?)` writes the bytes into MEMFS and walks the candidate list, recording a diagnostic when a non-default wins and, on total failure, throwing one error naming **every** attempt; an explicit `timeStep` (meshio++ >= 8.6.0) routes through `readMeshSelective` instead of `readMesh`, an out-of-range value surfacing meshio++'s own error verbatim. Each candidate in `MESHIO_LENIENT_RETRY_FORMATS` (`med`) gets a second, **lenient** attempt (`ReadOptions::mLenient`, reaching wasm since meshio++ 9.9.0) before the next candidate is tried, with its own diagnostic: upstream's Python surface silently falls back to a pure-Python reader for the MED constructs its C++ core declines, and wasm has no such fallback, so through 9.8.0 a real Salome/Code_Aster file could not be opened here **at all**. Which constructs a lenient read skipped is not knowable from JS — upstream records them in a `MedInfo` the registry boundary discards. `readMeshioTimeValues(mainName, files, ext, format?)` is the `readMetadata(...).timeValues` counterpart, used to size the in-file timeline without a full read; **Exodus is still the only format it reports anything for** — MED honours a `timeStep` on read since 9.9.0 but is not one of upstream's metadata readers, so its step count is undiscoverable before a read and it stays out of `IN_FILE_TIMELINE_EXTENSIONS` (a `timeStep` passed explicitly, e.g. the MCP argument, still reaches a MED read). `writeMeshioBytes` returns `{data, companions}` (always bytes for `data`: gmsh 4.1 and ansys are **binary**) — since meshio++ 8.0.0 the wasm XDMF writer emits a companion `<stem>.h5` referencing it by name, so the MEMFS path carries the caller's `stem` (`opts.stem`, defaulted via `memfsStem`) rather than a fixed `out`, and anything the writer left behind in MEMFS beyond the named file is returned as a companion for the caller to write alongside it. `configureMeshio` is an escape hatch only: unlike mmg, `{wasmBinary}` is **silently ignored** here (Emscripten pruned it from this build's `INCOMING_MODULE_JS_API`), so the loader passes `locateFile` itself in both layouts — and since meshio++ 8.8.0 that `locateFile` must be **name-aware**. The package now ships TWO native artifacts (sequential `meshioplusplus_wasm.{mjs,wasm}` + OpenMP/pthreads `meshioplusplus_wasm_mt.{mjs,wasm}`) and `loadMeshioPlusPlus(overrides, {variant})` picks between them itself: `resolveVariant` returns `"mt"` whenever `crossOriginIsolated` is undefined, i.e. under Node, i.e. in the extension host. Returning a fixed path hands the mt glue the sequential binary and **every meshio format** dies with `Aborted(LinkError: WebAssembly.instantiate(): Import #0 module="a" function="a" ...)`, an error naming neither the file nor the variant — `meshio.test.ts` pins the invariant (the name `locateFile` is asked for matches the loaded `parallelBackend()`). `loadMeshio` also falls back to `{variant:"seq"}` once if the threaded build cannot instantiate (no SharedArrayBuffer, locked-down container), caching the DECISION in a module flag and never the instance. The `_mt` pair is ~6.2 MB of the `.vsix`; it earns its keep now that the extension calls into meshio++'s own mesh OPERATIONS — `smooth`/`reorder`/`partitionLabels` (see the "Additional mesh operations" section above) run measurably faster threaded on a large mesh, whereas earlier this variant selection existed only for parity with upstream's default (the extension called meshio++ for I/O only). `MeshioModule`'s TypeScript interface carries these three operations' signatures alongside the read/write ones. Tests: `src/test/meshio.test.ts` (real wasm).
- `src/parser/writers/` — the **writer layer** (inverse of the parsers): serialises an `MdpaModel` back to file text for Save/Export. `writerCommon.ts` holds the shared helpers — `nodeIndexMap` (connectivity stores node **ids**, so index-based formats remap id→0-based), `buildCellLayout` (flattens all blocks into one ordered cell list + element/condition/**geometry** id→cell maps; every `LaidOutCell` also carries its source `blockName`, so a writer can regroup by original block rather than only by (type, stride) — `meshioConvert.ts` is the consumer of both, for the named groups it emits), `surfaceTriangles` (surface cells + volume **boundary** faces via a once-seen face map; `{ volumeOnly }` option), and `point/cellFieldArray` (positional field arrays). Per-format writers: `mdpaWriter.ts` (id-based; copies `Properties`/`ModelPartData`/`Table` blocks verbatim from the original source text when given `{ sourceText }`, else emits a default `Properties 0`), `vtkLegacyWriter.ts` (ASCII UNSTRUCTURED_GRID + FIELD data), `vtkXmlWriter.ts` (`writeVtu`/`writeVtp`, inline ASCII DataArrays), `stlWriter.ts`/`objWriter.ts`/`plyWriter.ts` (surface formats; volume cells → boundary triangles). `meshWriter.ts` is the dispatcher, with **two entry points**: sync `writeMeshFile(model, ext, opts?)` → `string` for the native formats, and async **`writeMeshFileAsync(model, ext, opts?)` → `Promise<MeshWriteResult>`** (`{data, companions}`) for any exportable format, delegating to `writeMeshioBytes` for the meshio++ ones. The split exists because **gmsh (4.1) and ansys write BINARY** — the old string-only path plus `writeFile(…, "utf8")` corrupted them; callers now pass `result.data` to `fs.writeFile` with **no encoding** (strings still default to utf8, a Uint8Array writes raw). `companions` carries files the writer emitted BESIDE the named one and every caller must write them next to the destination: since meshio++ 8.0.0 the wasm XDMF writer keeps its heavy arrays in a `<stem>.h5` and leaves only `<stem>.h5:/data0` references in the XML, so the XML alone is a dangling file. That is also why the MEMFS name carries the destination stem (`opts.name`) rather than a fixed `out` — the stem reaches file content verbatim. It re-exports the format registry from the dependency-free `exportFormats.ts` — `NATIVE_EXPORT_EXTENSIONS` (`.mdpa/.vtk/.vtu/.vtp/.stl/.obj/.ply` — structured `.vti/.vts/.vtr` and `.vtm` are **excluded**, an unstructured model can't reconstruct them), `EXPORTABLE_EXTENSIONS` (native + `MESHIO_EXPORT_EXTENSIONS`, spread as `as const` so it stays the `ExportableExtension` type source and `EXPORT_FORMAT_LABELS` stays exhaustively checked at compile time), `EXPORT_MENU_GROUPS` (menu-only grouping — ~30 formats in one flat dropdown is unusable, and it drops the alias extensions `.nas/.fem/.tec/.dato/.xmf` that repeat their primary format), `EXPORT_FORMAT_LABELS`, `isExportableExtension`, `isNativeExportExtension` (kept in their own module so the webview bundle can import the list without pulling in the writers). Pure/Node-testable; round-trip tests (`parse → write → re-parse`) in `src/test/writers.test.ts`.

- `src/parser/vtkLegacyParser.ts` — pure (no `vscode`/DOM/vtk) parser for legacy VTK files (`DATASET UNSTRUCTURED_GRID`). Emits `MdpaModel` so the entire webview pipeline is reused unchanged. ### Webview (browser IIFE, `webview/`)
- `webview/main.ts` — entry point. Owns the VTK.js scene. On receiving a `model` or `vtkFrame` message it calls `buildScene(resetCam?)`, which creates one `vtkActor` layer per `EntityBlock` (visible — except volume blocks when covering surface blocks exist; `MMG_Interface*` blocks don't count as covering, so a level-set's split domains stay visible) and one per `SubModelPart` (hidden by default). For `vtkFrame` and for in-place op re-renders (`model` with `keepCamera`), `snapshotVisibility()` records the current layer toggles and `buildScene` consumes them (`nextVisOverride`) so surviving layers keep their state — outline checkboxes included — while new layers get the defaults (camera is also preserved by passing `resetCam=false`). Node-id labels are capped at 1 000 nodes. The `Quality` toolbar button / `computeQuality` message runs `computeMeshQuality` and toggles the quality panel; "Highlight bad" builds a red overlay layer (`quality:highlight`) from a metric's bad-element ids by reusing `addLayer`/`buildPolyData`. The `Field` toolbar button / `field` message toggles the field panel (see below). The `Find` toolbar button / `locateEntity` message opens a search bar: the matched entity is highlighted in yellow (`find:highlight` layer) and all other layers are forced to wireframe for contrast; closing the bar restores the prior wireframe state. The View ▾ menu's **Screenshot…** item (also the `kratos.mdpa.screenshot` palette command / Ctrl+Alt+P via the `takeScreenshot` host→webview message) calls `takeScreenshot()`, which uses `apiRW.captureNextImage()` (falling back to `canvas.toDataURL()`) and sends a `screenshot` message with the base64 PNG to the extension host. On `vtkGroup`, a `TimelineControl` bar is shown at the bottom of the viewport. Module-scope maps `elementById`, `conditionById`, `geometryById` are populated in `buildScene()` and shared by the quality panel, the find feature, and quiver cell-centroids.
- `webview/meshBuilder.ts` — converts `MdpaModel` nodes + `Cell[]` into `vtkPolyData`. Handles point clouds (no cell type) as vertex cells. Optionally takes a `FieldAttach`: nodal scalars are pushed into the point-data array *inside* `localOf` as each local point is born (so they stay aligned with the local remap), and cell scalars are collected per emitted cell in VTK's verts→lines→polys order — volume boundary faces inherit their owning cell's value via a face-owner map. `buildPolyData`'s optional `{wantPickMaps: true}` additionally returns `pointGlobalIds` (local point index → global node id, the same `localOf`-birth-order array as the point-scalar path) and `cellEntityIds` (one entry per emitted cell, same verts→lines→polys order as the cell-scalar path, -1 for an entity-less cell) — the data the Inspect click-to-probe feature (see below) resolves a `vtkCellPicker` hit against; skipped by default since the extra arrays cost real memory on a mesh that will never be clicked on.
- `webview/outline.ts` — renders the sidebar tree of checkboxes (toggle layer visibility) and labels (frame/zoom to layer). SubModelPart rows (`exportPath` set) also get an export button that deploys a body-attached format dropdown (`OutlineExportUI` = icon + `EXPORTABLE_EXTENSIONS` from the pure `writers/exportFormats.ts`), posting `menuExportPart {format, path}` via the `onExport` handler, **plus a delete (X, `close` icon) button** that posts `applyOp {op:"deleteSubModelPart", path}` via `onDelete`, **a rename (pen, `edit` icon) button** that swaps the row label for an inline text input (Enter/blur to commit, Escape to cancel) and posts `applyOp {op:"renameSubModelPart", path, newName}` via `onRename`, and **when the node carries `counts`, an info (`info` icon) button** that opens a dropdown listing recursive (subtree) entity counts by kind; only one dropdown/rename-input is open at a time (outside-click / Escape / scroll dismiss).

- `src/parser/meshNormals.ts` — pure (no `vscode`/DOM/vtk) `computeMeshNormals(model)` behind Advanced ▸ **Face normals**: per-face centroid + unit normal for every surface cell and every volume-cell **boundary** face (interior faces deduped away, same rule as `surfaceTriangles`, which is what keeps the arrow field readable). Normals come from **Newell's method** — robust for a non-planar quad, where a cross-product of two edges is not. The point is finding an **inverted element**: winding decides both the arrow direction and the sign of the Jacobian, so a flipped cell is a solver error that is invisible in the numbers and obvious on screen. `inconsistent`/`inconsistentIds` are the machine-checkable half: two faces sharing an edge are consistently wound exactly when they traverse it in OPPOSITE directions, so the same directed edge seen twice means one is flipped — a **relative** test, so a uniformly inside-out mesh reports zero and the arrows stay the check for global orientation. Volume boundary faces get their winding from `volumeFaces`' tables rather than the file, so the test bites on surface meshes (shells, skins, imported STL/OBJ), which is where flipped elements actually come from. Reuses `cellCategory`/`cornerCount`/`volumeFaces`/`nodeIndexMap` from `writers/writerCommon.ts`; rendered by `main.ts` through `quiver.ts`'s `buildGlyphActor` (which gained an optional `flatColor` — normals are unit length, so a magnitude colormap would paint the whole field one hue), with the flipped cells overlaid in red. Unit tests: `src/test/meshNormals.test.ts`.
- `webview/sphereGlyph.ts` + `webview/spherePanel.ts` + the Spheres wiring in `main.ts` (toolbar button / `spheres` message, both providers) — **particle rendering**. A one-node cell has no extent, so `meshBuilder` puts it in vtkPolyData's `verts` and it draws as a fixed-pixel GL point; that is wrong for a peridynamics/DEM particle whose radius is physical data and must scale with the camera and the mesh. `sphereGlyph.ts` is modelled on `quiver.ts` (the other `vtkGlyph3DMapper` user): a UNIT `vtkSphereSource` + a 1-component `"radius"` scale array + `setScaleModeToScaleByMagnitude()` — `norm(tuple,1)` is the value itself, so the drawn radius is exactly `scaleFactor * radius`; no orientation array, and `setScalarVisibility(false)` unless colouring by radius (the scale array would otherwise double as the colour array and tint every particle by its own size). `spherePanel.ts` reuses the Mesh-size panel's `.meshsize-*` chrome: scale, tessellation (8/16/32/48, with a >50k-glyph warning), the **constant radius** prefilled from `defaultSphereRadius`, optional colour-by-radius, and a **Write to mesh** button posting `applyOp{op:"setElementRadius",mode:"absolute"}` — the bridge from a preview-only constant to a real, exportable field. `main.ts` owns the `sphere:glyphs` layer, anchors it via `coordOfPrep` so it follows the Deformed-shape warp like quiver, and **auto-enables it when `hasSphereRadius(model)`** (that IS the mesh, not an analysis overlay; a radius-less point cloud stays GL points so an ordinary point cloud does not silently become a ball pit). Two distinct base-layer concerns, deliberately separated: the layer is **excluded from `FIELD_LAYER_IDS`** and counted by `isOverlayLayer` so it neither triggers base dimming nor gets dimmed itself (wireframe spheres are unreadable), and `syncSphereBaseHiding()` HIDES the source one-node layers while the glyphs stand in for them (left visible they double-draw as points inside every sphere) restoring their prior visibility on teardown.
- `webview/orientationCube.ts` — sets up a `vtkAnnotatedCubeActor` (Kratos face labels: RIGHT/LEFT/TOP/BOTTOM/FRONT/BACK; uniform blue faces + axis-arrow colours copied from the sibling CAD-Preview so the family matches) plus a `vtkAxesActor` (prominent X/Y/Z colored arrows with letter labels) inside a `vtkOrientationMarkerWidget` in the top-left corner. - `webview/navControls.ts` — `NavControls` class that injects a `#nav-controls` DOM overlay into `#viewport`. `media/` is the only allowed `localResourceRoots` for the webview. The extension-host build **aliases `@loumalouomega/mmg-wasm` to its CJS entry** (`esbuild.js`): bundling the ESM entry breaks because its `import.meta.url`-based wasm lookup becomes `undefined` in a CJS bundle. **`pyodide` is `external`**: its loader locates the .wasm/.zip siblings relative to its own file, so it must never be bundled — dev resolves it from node_modules, the packaged extension from `dist/pyodide/`. **`@meshioplusplus/wasm` is `external` too** (with a `"@meshioplusplus/wasm/*"` entry as well, because `meshio.ts`'s `require.resolve("@meshioplusplus/wasm/package.json")` is a literal esbuild would otherwise resolve at build time). It is the *opposite* of the mmg case: the package is **ESM-only** — no CJS build, no `exports` map — while the host bundle is CJS, and its Emscripten glue reads `import.meta.url` (`createRequire`, `_scriptName`), which an esbuild ESM→CJS rewrite turns into `undefined`. So there is nothing to alias: it ships verbatim under `dist/meshio/` and `meshio.ts` pulls it in with **`new Function("u", "return import(u)")`** — a real dynamic import that survives both esbuild's and tsc's CJS downlevelling (a literal `import()` would be rewritten to `require()` and fail). Should upstream ever publish a CJS build, this collapses to the mmg shape (alias + bundle + `locateFile`).
